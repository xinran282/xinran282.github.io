# 今日知识点：稀疏注意力：长文档如何减少全局注意力开销

> 一句话：只让每个 token 关注局部窗口和少量全局位置。

**分类**：基础原理　**难度**：4　**资料截至**：2020-04-10

## 它解决什么问题

标准自注意力让序列中每个 token 与所有其他 token 计算注意力，时间和显存复杂度随序列长度平方增长。短文本尚可，长合同、论文、司法卷宗或代码库就会变成瓶颈。稀疏注意力的核心观察是：长文档中大多数 token 对并不需要直接交互——相邻词承担局部语义，只有少量关键位置需要承担全局信息。Longformer 用滑动窗口注意力和少量全局注意力替代完整注意力矩阵，使长文档处理在计算上可行。

## 工作机制

Longformer 的注意力模式由两类组成：

1. **滑动窗口注意力**：每个 token 只关注左右各 w/2 个相邻 token，复杂度随长度线性增长；
2. **dilated 窗口**：类似空洞卷积，窗口内间隔取 token，扩大感受野而不等比增加计算；
3. **全局注意力**：为少数任务关键 token（如分类 token，或问答中的问题 token）设置全局连接：这些 token 关注所有位置，所有位置也关注它们；
4. **模式可配置**：分类任务可让 [CLS] 全局；问答任务可让整个问题片段全局；文档级任务可按任务设计关键节点。

这与 RoPE 的区别是：RoPE 定义位置如何进入 query/key 计算；稀疏注意力定义哪些位置之间允许计算注意力。

## 一个具体例子

一份 8192 token 的合同，若完整注意力，每层约需 8192² 次注意力交互；若窗口 w=256，每个 token 只看邻近 256 个位置，交互约为 8192×256，随长度线性增长。再选“争议解决”“违约责任”等标题 token 作为全局位置，使它们能汇聚全文信息。回答“违约后的通知期限是什么”时，问题 token 全局关注正文，相关条款再通过局部窗口保留上下文。

## 它和什么容易混淆

- **标准注意力**：所有 token 对都参与计算，表达能力最强但成本高；
- **FlashAttention**：减少内存读写和注意力 kernel 开销，但通常仍计算完整注意力；
- **RoPE**：位置编码方式，不决定哪些位置相连；
- **分块预填充**：推理服务的调度技术，不改变模型内部注意力结构；
- **RAG**：把外部文档片段放入上下文，先检索再生成；稀疏注意力扩展单次上下文能处理的文档长度。

## 局限与实践建议

- **全局连接选择是任务相关的**：选错全局 token 会削弱跨文档信息聚合；
- **并非所有长程依赖都可通过窗口叠加捕获**：多层窗口能扩大感受野，但传递路径可能变弱；
- **实现复杂**：稀疏 mask、kernel 和张量并行会带来工程挑战；
- **与位置编码外推耦合**：训练长度、窗口大小和推理长度需一致评估；
- **先问是否需要全文**：若只有少量段落相关，RAG 可能比超长注意力更便宜。

## 为什么现在值得关注

稀疏注意力是长上下文模型的基础设计之一，也帮助区分“注意力结构节省计算”和“推理调度节省延迟”“检索减少输入长度”三类不同优化。
