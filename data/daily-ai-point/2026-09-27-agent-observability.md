# 今日知识点：Agent 可观测性：用轨迹追踪定位失败

> 一句话：把 Agent 的每步输入、工具和输出串成可查询轨迹。

**分类**：工程与产品　**难度**：3　**资料截至**：2026-09-27

## 它解决什么问题

单轮问答出错时，通常只需看 prompt 和回答。Agent 则会在一次任务中规划、检索、调用工具、读观察结果、再决定下一步；最终失败可能来自早期错误、工具返回异常、权限判断错误或上下文被旧信息污染。如果日志只有“任务失败”，几乎无法定位。

Agent 可观测性把一次执行拆成有因果关系的树形轨迹：谁调用了谁、输入是什么、输出是什么、耗时多少、错误在哪一步传播。它解决的是调试、回归、成本审计和责任追踪问题。

## 工作机制

OpenTelemetry 对分布式追踪的通用模型是：一次请求对应一个 trace，trace 由多个 span 组成；每个 span 记录操作名、开始/结束时间、属性、事件和状态，并通过 parent span 形成树。Agent 可观测性可以复用这套结构：

1. **任务 span**：记录用户目标、系统提示版本、模型配置、预算和会话标识。
2. **推理 span**：记录每次模型调用的输入摘要、输出、token 用量、延迟、温度和停止原因。
3. **工具 span**：记录工具名、参数摘要、返回摘要、HTTP 状态或错误类型；敏感字段应脱敏。
4. **子任务 span**：规划、检索、重排、验证、人工审批等子流程分别建 span。
5. **关联与采样**：通过 trace_id 把所有 span 串起来；成功请求可低比例采样，失败和高风险请求应保留完整轨迹。

关键不是“多打日志”，而是保留因果关系：每个观察结果能回到产生它的行动。

## 一个具体例子

用户要求：“查一下上周退款订单中金额异常的记录，并给客服主管写摘要。”

轨迹可能是：

- `agent.run`：任务开始，输入版本 `policy_v3`；
- `plan`：计划先查数据库，再校验金额，再生成摘要；
- `tool.db_query`：SQL 摘要、返回 120 行、耗时 300ms；
- `model.summarize`：输出摘要；
- `guardrail.validate`：发现摘要泄露完整手机号，任务被阻止。

如果只看最终输出为空，无法判断是数据库、模型还是权限问题。轨迹显示：检索成功、摘要生成成功、失败来自隐私校验。修复方向就是把手机号脱敏后再摘要。

## 它和什么容易混淆

- **trace vs 普通日志**：日志是离散事件；trace 通过 parent-child 关系表达调用链。
- **可观测性 vs 评估**：可观测性描述某次执行发生了什么；评估在数据集上统计成功率。两者互相供给。
- **记录 vs 监控**：记录用于回放和调试；监控汇总为指标和告警。
- **Agent trace vs 模型内部思维链**：前者是系统行为记录，可由外部执行器保证；后者是模型自述，未必忠实。

## 局限与实践建议

- **隐私和敏感数据风险**：日志可能把用户输入、工具返回和密钥记录下来，必须脱敏、加密和设置保留期。
- **体积和成本**：每次工具调用都完整记录会膨胀，需要字段白名单和采样策略。
- **非确定性让回放不完美**：模型温度、外部工具状态和时间都会变化。
- **必须有版本字段**：没有 prompt、工具、模型版本，轨迹难以用于回归分析。
- **防止只看平均指标**：尾延迟、失败率、工具错误率和人工升级率应分维度报告。

实践上，从最小 trace 开始：任务、每次模型调用、每次工具调用、错误和最终输出；再逐步加入成本、质量标签和人工审核结果。

## 为什么现在值得关注

Agent 从演示走向生产时，失败定位和责任边界变得比“看起来聪明”更重要。可观测性是把 Agent 从黑盒流程变成可维护系统的工程基础。
