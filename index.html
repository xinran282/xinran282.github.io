System 1 决策引擎：给软件用的快判断

发表于 2026-09-23 分类于 AI

System 1 决策引擎要解决的不是「写一段像样的回复」，而是：给定当前状态，在你规定好的答案空间里，很快给出一个程序能直接用的判断，并带上概率。

这个名字借自 Kahneman《思考，快与慢》里的 System 1：快、直觉、不逐步推理。TypeSafe 在文档里写明了借用关系，同时把重点收窄成「快、聚焦的判断」。它不是在复现人类认知科学，只是拿这个对比来说明：模型不做慢思考，也不写解释。

产品形态已经有两家能对上看。TypeSafe 把这类模型叫 System One，旗舰是 Jev，走 POST /v1/systemone。Laya 自称非自回归 System 1 决策引擎，协议故意兼容同一套接口。下面按这个共同形状写，不把某一家的延迟数字当成定律。

它不是分类器，也不是 Agent

传统软件把决策写成 if/else。规则清楚时这最稳，也最便宜。一碰到邮件正文、工单、对话记录，规则就开始漏。

常见补法是丢给大模型：「读完这段，用 JSON 告诉我该分给哪个组。」模型会写字。你再解析。字段名会飘，枚举会发明，偶发的一句解释会把解析器弄死。Agent 更进一步，自己决定下一步调什么工具。TypeSafe 把这种架构和「代码掌控流程、模型只在需要常识的地方出现」分开：后者才是它说的 AI-powered software。

System 1 决策引擎站在中间。它懂自然语言，但输出被钉在你给的选项上：

  • 这段话该给 billing、technical 还是 account
  • 客户有多着急，落在你定义的几档上
  • 「有没有明确要求退款」为真的概率是多少

它不写回复，不写代码，不生成推理过程。Jev 目前只吃文本：字符串、JSON、文本数组，不吃图、音频、视频。这是 TypeSafe 文档里的限制，不是我的推断。

和经典分类器的差别在输入侧。分类器通常要你先标一堆数据、固定标签集。这里的问题是运行时用自然语言描述的：instructions 写判断本身，criteria 写选项或量表。标签可以按业务改，不必先训一个新头。代价是：描述写糊了，输出的概率就不好解释；领域一偏，仍然要微调或至少在自己的数据上校准。

三种原语

TypeSafe 和 Laya 用同一套问题类型。选哪种，看你的代码接下来要干什么，不看哪一个听起来更「智能」。

Choice：从无序集合里挑一个。工单分部门、文档类型、编程语言。返回选中项、每项概率、以及描述分布有多尖的 confidence。列表可能盖不住时，自己加 other 或 none。

Score：落在你定义的有序档位上，返回值可以落在两档之间。紧急程度、受挫程度、技能深浅。档位必须能独立读懂，写具体情境，不要只写「低 / 中 / 高」。

Noul：是或否，返回 0 到 1 的 P(true)。有没有要退款、像不像钓鱼、简历有没有写过分布式。Noul 没有单独的 confidence。0.5 表示是和否差不多，不表示「中等强度」。TypeSafe 特意警告：不要用 Noul 去问「这个候选人 Python 强不强」——「强」没定义时，0.5 无法当中级水平用。要程度就用 Score，要是否就写清条件。

同一份 state 上可以一次问很多道，题与题互相看不见答案。这是设计，不是缺陷。你要的是可拆开检查的信号，不是模型在内部把几件事揉成一句「建议」。

问题 ID 只给你的代码用，不会送给模型。判断必须完整写在 instructions 里。state 是结构化对象时，用反引号路径指到字段，例如 `ticket.messages[0].text`。

工作流怎么拆

TypeSafe 的构建指南可以压成几条，和产品无关。

能用代码就算的，不要问模型。逾期天数、订单是否已关闭、金额是否相等，用日期和数字。模型出现的位置应当是：这段非结构化文本在说什么。

state 只放当前这批问题需要的上下文。退款政策、相关交易、客户原话可以放；三年工单历史不要整包塞进去。当前事实来自你的知识库时，不要指望权重里「记得」政策。

问题要窄。TypeSafe 把「把判断拆开」写成指南里最重要的一条。「这是不是垃圾邮件」里面至少叠了：要不要密码、有没有意外奖金、是否制造紧迫、发件人显示名和域名是否冲突。拆开以后，每道题可以单独看错在哪，权重可以在代码里改，不必重写一整段 prompt。

同一份 state 上能一起问的，就一起问。并行几乎不增加等待，多出来的主要是题面 token。可能用得上的题也可以先问，代码按分支决定用哪几个答案——他们叫 speculative fan-out。只有后一步必须先拿到前一步答案才能构造 state、拉证据、或决定下一题的选项时，才发第二次请求。

概率和置信度用来分流，不用来证明「这次一定对」。校准是对一批预测说的，单条没有保证。阈值要在你的数据上对着准确率画，cookbook 里的 0.8 只是例子。Noul 接近 0.5 该升级；Choice 的低置信度也可能只是几个可接受选项把概率摊开了，不一定等于判断失败。

现成实现差在哪

Jev / TypeSafe。 闭源 API。文档写大多数查询大约 100 ms，训练目标是校准过的决策（他们称为 RLCD）。你定义 state 和 questions，代码组合答案。适合已经按 System One 协议写客户端、不想自己伺候编码器的人。价格、配额以 Models 为准，这里不抄可能过期的数字。

Laya。 Apache 2.0，ModernBERT / mmBERT 编码器，一次前向，不生成文本。作者在 T4 上测过单问大约 33 ms。带 Router：非拉丁文字走多语言模型，避免英文权重在高棉语上准确率 0 却自信 0.95 那种事故。HTTP 服务兼容 /v1/systemone。它自己承认：基座在 typed-decisions 上接近随机，0.766 来自微调后的 checkpoint；选项一多、score、英文 noul 都有已知坑。把它当特化基座，不要当开箱裁判。

两者协议能对上，不代表同一道题分数相同。Laya README 里对 Jev 的对比，Jev 一侧来自第三方已发表数字，样本和提示并不相同。

再往外，BERT 分类头、交叉编码器重排、CALM 一类校准分类器，也能承担「快判断」。缺的是运行时用自然语言定义 choice / score / noul、以及和 System One 客户端的那层契约。有没有必要上专用引擎，看你是不是真的在组合很多这类判断，而不是偶尔抽一个字段。

不该交给它的事

需要逐步推理、工具循环、写给用户看的句子，这是 System 2 或普通 LLM 的工作。决策引擎最多提供「要不要升级到那边」的门闩。

选项特别多时，所有选项要挤进同一段上下文预算。Laya 在 Banking77 上默认设置会把每个标签压到三四个 token；Jev 声称开箱能到 255 个选项，仍然不是无限。分层 Choice，或先短名单再精排，是代码的事。

输出类型安全不等于真。模型不会发明列表外的标签，仍可能在列表内选错。领域一偏就要微调或至少做温度校准。Laya 出厂过自信；Jev 文档也写校准不保证单条正确。

当前这一代基本上是文本 in、结构 out。界面截图、语音工单，要先变成字，或等多模态版本。

什么时候值得用

你已经能画出业务流程图，只是某几处必须读懂人话：分诊、是否触发政策、候选证据里选一条、要不要人工。那些节点改成类型化问题，周围仍是普通代码。

你在用大模型抽 JSON，却把大量时间花在修解析和枚举漂移上。换决策引擎，是把「生成再解析」收成「在给定集合上打分布」。

你需要在请求路径里做判断，等不起一轮完整对话。具体毫秒数看部署：托管 API、本地 GPU、CPU 差一截。先测你的 p50，再决定它够不够当同步依赖。

反例也清楚。没有稳定的答案空间，每次问题都在变，那是聊天，不是决策引擎。没有人维护 instructions 和校准数据，上了也会在领域漂移里静默变差。一次只问一件小事、用正则就能做，不必为这个词专门加模型。

结论

System 1 决策引擎是给软件用的快判断层：读状态，在你规定的 Choice / Score / Noul 上返回概率，流程仍由代码收口。名字来自认知科学的快系统，产品承诺的是延迟和可组合的类型，不是「更像人」。

Jev 把这套做成 API。Laya 做成可自托管的编码器。要不要用，看你的痛是不是「非结构化输入上的窄判断」，以及你有没有把判断拆开、用代码组合的意愿。拆不开的大问题，仍然该给会慢慢想的模型，或者给人。

Laya：一次前向给出类型化判断

发表于 2026-09-23 分类于 工具

Laya 是一个非自回归的 System 1 决策引擎。你给它一段状态（邮件、工单、JSON、纯文本）和一组类型化问题，它做一次前向，返回 choice、score 或 noul（是否），不生成句子。仓库是 NandhaKishorM/laya，Apache 2.0，Convai Innovations 做的。权重在 Hugging Face。

到 2026 年 9 月 23 日，这个 9 月 18 日才公开的 Python 仓库大约 1.8 万 Star。宣传数字是 T4 上一问 33 ms，批量大约 7.2 ms/问。数字来自作者自己的测量，可以当数量级，不必当成你机器上的保证。

它想替代的，是「让大模型写一段 JSON，再自己解析」这条路。解析会失败，模型会编。Laya 的输出本来就是标签、分数和概率。

它回答哪三类问题

原语 返回什么 典型用途
choice 选中的标签、每项概率、置信度 工单分部门、意图分类
score 有序量表上的期望档位、分布、置信度 紧急程度、受挫程度
noul 校准过的 P(true)，0 到 1 是否退款、是否要流失、是否越狱

一次调用可以塞多道题，共用同一次前向。README 的客服例子里，同一封「三月收了两次费，今天退款否则取消」的邮件，同时问部门、紧急度、流失风险、是否明确要求退款。

作者说训练用了 RLCD：按严格真评分规则做强化学习。因此他们主张置信度可以拿来做门槛，高置信度自动处理，低的转人工。这是训练目标上的说法。后面会写到，出厂权重本身过自信，要用温度校准；action.act_probability 目前几乎不能用。

三个 checkpoint，加一个 Router

名称 编码器 参数量 上下文 用途
laya ModernBERT-large 421M 512 英文
laya-multilingual mmBERT-base 322M 1024 100 多种语言，更快
laya-typed-decisions ModernBERT-large 421M 1024 类型化决策工作流微调版

推荐入口是 Router。它先用纯 Python 做脚本和语言探测（作者写小于 0.5 ms），再决定走英文还是多语言模型。探测发生在前向之前。原因写在基准里：英文 checkpoint 在高棉语上准确率 0.000，置信度却是 0.952。错了还很笃定，靠模型自己的置信度挡不住。

路由证据（同一套问题，一块 T4，17416 题）：

  • MASSIVE 意图，英文：laya 0.783，多语言 0.657，Router 跟英文走 0.783
  • MASSIVE 意图，另外 13 种语言：英文 0.306，多语言 0.451，Router 跟多语言
  • XNLI 非英文 14 种语言：英文 0.521，多语言 0.731
  • 51 种语言里，高于 3 倍随机的：英文 23/51，多语言和 Router 都是 45/51

短拉丁文本经常看不出语种，比如 Quero cancelar。默认会进英文。流量主要不是英文时，设 Router(default="multilingual")。0.3.7 还修了被邮件客户端扒掉口音的西语、意语、葡语、法语，以及巴西葡语，让它们能进多语言模型。内置探测是无依赖的启发式，不准可以自己塞 lang_guess，接 fastText 或别的 LID。

生产环境别每次冷加载。作者测过：max_loaded=1 时语言一切换，CPU 中位重载 7.4 秒，T4 上 10.3 秒。默认 Router() 常驻英文和多语言两个；Router(preload=True) 三个都放内存，之后语言切换只付探测成本。预加载后他们报的延迟是 GPU 32.8 ms，CPU 193–464 ms。

和 Jev 比，数字怎么读

TypeSafe 的 Jev 是同类产品：类型化判断，走 System One API。Laya 的 HTTP 服务 laya-serve 故意兼容 POST /v1/systemone，现有 Jev 客户端改 baseUrl 就能打过来。impossibl 上也有免费托管，同样这套协议。

README 里有一张「Laya（经 Router）对 Jev」表。Laya 数字是作者自己测的；Jev 数字来自第三方已发表结果，作者写明没有 TypeSafe API 权限，样本和提示并不相同。当作方向，不要当成同一次对照实验。

作者列出的差异大致是：

  • typed-decisions 2000 条：Jev 0.727，Laya 0.766
  • AG News：0.910 对 0.950
  • DAIR Emotion：0.480 对 0.595；Jev 有 16% 样本给真标签的概率是 0
  • Banking77：Jev 0.870（72 类），Laya 默认 0.425（77 类）
  • ECE（越低越好，Laya 是温度校准后）：0.246 对 0.081
  • 单问 p50 延迟：Jev 第三方测到 236–276 ms，Laya 自测 32.8 ms
  • 权重：Jev 闭源 API，Laya Apache 2.0，自托管按他们的算法是 $0

Jev 仍强的地方，作者自己写了。选项超过大约 20 个时，Laya 把选项挤进固定的 head_max_len（英文默认 192，多语言 256）。77 个标签大约每个只分到 3 到 4 个 token，字面值会糊在一起。Jev 开箱能到 255 个选项。软分布匹配上 Jev 也更好（soft accuracy 0.580 对 0.471）。出厂未校准的 ECE，Laya 原始值并不更好，0.081 是拟合温度之后的数。

typed-decisions 那 0.766 来自专门微调的 laya-typed-decisions。两个基座在同一套基准上是 0.362 和 0.342，低于多数类基线 0.461，只略高于随机 0.318。作者原话：Laya 是一个很快的、用来特化的基座，不是开箱即用的零样本决策引擎。能力主要来自微调。

用之前先看限制

这些是仓库自己写的，不是外人挑刺。

选项很多时，加大 head_max_len / max_len，或者用 predict_shortlist 先按向量召回 top k 再打一次前向。Issue #102 有人报告 Banking77 短名单从 54.3% 到 60.8%，仓库没有复测。

score 是最弱的原语。SST-5 上英文 checkpoint 0.372。多语言模型在 score 上有位置偏差，很少选列表里第一档（#131）。英文分数题应指定 model="english"。

英文 checkpoint 的 noul 可能跟着 false: / true: 这两个选项词走，而不是跟着正文走（#156）。正例也会给出很自信的「否」。未换权重之前，用自己的数据检查；不行就改成两个中性 key 的 choice。

action.act_probability 几乎恒为 1.0，在 396 条标注上 AUROC 0.30，和正确性反着来（#185）。门控用 confidence，同一批 AUROC 0.77。

两个基座出厂都过自信。按题型和选项数在留出数据上重拟合温度后，平均 ECE 从 0.466 降到 0.081（英文），多语言从 0.314 到 0.106。多语言权重不带拟合温度，要用概率就自己拟合。加载时温度会被夹到 [0.5, 5.0]，非法值回退到 1.0，这只是避免加载失败，不代表已经校准。

0.3.7 把 laya.load() 在 CPU 上从大约 22 秒降到大约 2 秒，并绕开了 Windows + Python 3.14 的崩溃（#123）。微调笔记本的校准改到留出切片上拟合（#186）。

微调才是正路

Kaggle 免费 2xT4 上有完整笔记本：造数据、RLCD 训练、拟合温度、评估、推 Hub。大约 4 到 5 小时，4 个 epoch，约 3 万题。

一份完整特化记录在 docs/finetune_browser_agent.md：在 16 GB 单卡、不调用付费 API 的情况下，把 Laya 做成 browser-use/jev-ultrafast 的操作/目标决策头。约 45 个候选元素的 top-1 从零样本 0.10 到 0.66，真实任务成功率从 0% 到 62%，每步 17–23 ms。权重在 cklxx/laya-browser。

仓库还带几套现成问题模板：小模型/前沿模型路由、提示词护栏、内容审核、工单分诊。那是起点，不是替你完成领域适配。

怎么跑

Python 3.10+（huggingface_hub 1.x、transformers 5.x、torch 2.14 都卡在这）。

只跑一个权重时用 laya.load("convaiinnovations/laya")，多语言和 typed-decisions 走对应 subfolder。空问题字典会直接返回空答案，不做分词和前向。

自托管：

默认 0.0.0.0:8000。环境变量可配设备、预加载列表、CPU 线程上限、可选 Bearer。仓库是 Nix flake，也有 NixOS 模块。Docker 说明在 docs/docker.md。

不想管 GPU 可以用 impossibl 的免费托管。convaiinnovations/laya 走 Router；convaiinnovations/laya-multilingual 钉死多语言权重。托管侧 max_len 写的是 8192。注意：按脚本路由时，拉丁字母文本会进英文 checkpoint，西语葡语不会自己跑到多语言权重，所以才单独给了第二个 model id。

在线试：HF Space。作者在 Dev.to 写过来龙去脉。社区有 omp-laya-judge（oh-my-pi 插件）和 laya-adk-toolkit（Google ADK 工具）。

结论

Laya 把「分类 / 打分 / 是否」从文本生成里拆出来，用编码器一次前向给出带概率的结构化答案。Router 解决了英文权重在非拉丁文字上又错又自信的问题。协议上能接 Jev 那一类 System One 客户端。

它不是通用零样本裁判。基座在 typed-decisions 上接近随机；选项一多、score、英文 noul 都有已知坑。置信度要校准，act_probability 先别用。你有稳定的判断模式、愿意微调、还在意毫秒级延迟和可自托管，它值得试。你只是偶尔让 LLM 抽几个字段，上 Laya 多半是在给自己加一套训练和校准负担。

Orca：给并行 Agent 用的 ADE

发表于 2026-09-22 分类于 工具

Orca 不是又一个聊天窗口，也不是又一个绑定单一模型的 IDE。它把自己叫成 ADE：Agent Development Environment。仓库 stablyai/orca 的定位很直白：用你自己的订阅，同时跑一队编码智能体。桌面、手机、远程机器都能接进来。

到 2026 年 9 月 22 日，这个 TypeScript 仓库大约 7.5 万 Star，MIT 许可证，Stably 出品，Y Combinator 背景。官网是 onOrca.dev。宣传语写的是「面向 100x 构建者的 AI 编排器」，听起来夸张，产品本身倒不绕：把 Codex、Claude Code、OpenCode、Pi 这类 CLI 智能体并排跑起来，每个占一个 git worktree，状态集中看。

它到底解决什么

现在常见的用法是：开一个 Claude Code 终端，改一个仓库；卡住了再开 Cursor 或 Codex 重来一遍。文件在同一份 checkout 上互相覆盖，stash 和切分支很快变成体力活。

Orca 把单位从「一个仓库窗口」改成「一个任务一份磁盘副本」。文档写得很清楚：每个功能或 bug 对应一个 git worktree。智能体改的是自己那份文件，不会踩到旁边那个 agent 正在改的同一行。

这不是新发明。git worktree 一直能做到隔离。Orca 做的是把创建、分发提示、对比 diff、提交、开 PR、远程跑、手机盯进度，收进同一个桌面应用。

核心模型：一个任务一份 worktree

按官方文档，仓库有一个 base ref，通常是 origin/main。每个 worktree 再选自己的 start-from：base、本地分支、某个 SHA，或已有远程分支。每个 worktree 有自己的分支、磁盘目录和 agent 终端。

生命周期也按任务走：

  1. 创建：填任务名，选起点，可选挂上 GitHub / Linear / Jira / GitLab 链接。
  2. 干活：agent 终端、编辑器、浏览器、普通终端都绑在这个 worktree 上。
  3. 评审：对着 start-from 看 diff，可以在行上批注再丢回给智能体。
  4. 发出去：提交、push、开 PR、等检查，都在应用里完成。
  5. 归档或删除：确认后删掉目录和分支。

创建是后台进行的。对话框提交后立刻关掉，git fetch 和 git worktree add 继续跑。侧边栏会出现进度条，你可以先去别的 worktree。失败了能重试。

新 worktree 默认是干净 checkout。node_modules、缓存、.env 这类 gitignore 文件不会自动出现。Orca 用三套机制补：

  • 仓库设置里的 Worktree Shared Paths，从主 checkout 物化过来。macOS 上能走 APFS clone-copy，否则用符号链接。
  • orca.yaml 里的 worktree.sharedDirectories，适合 node_modules、.cache 这种可重建的大目录，共享而不是复制。
  • 仓库根目录的 .worktreeinclude，把 .env 这类文件复制进每个 worktree，各自一份。

这些 worktree 就是普通 git worktree。你在终端里 git rebase 或 git cherry-pick，Orca 下一次刷新会跟上。自己用 git worktree add 建出来的，默认先藏着，可以在 Non-Orca worktrees 里选「显示」。

并行跑，然后挑一个留下

README 里最显眼的能力是：把同一条提示发给五个智能体，各自隔离 worktree，比完再合赢的那份。文档里也有对应食谱，比如三个 agent 赛同一件事。

它宣称支持任何能在终端里跑的 CLI 智能体。名单很长，Claude Code、Codex、Grok、Cursor CLI、GitHub Copilot、OpenCode、Pi、Kimi、Qwen Code 都在上面，末尾还写了「+ any CLI agent」。这更像兼容层，不是官方认证清单。能不能用，取决于那个 CLI 自己能不能在你的机器上跑起来。

桌面端还带账号切换和用量追踪，至少覆盖 Claude 和 Codex：看用量、看限额重置时间，切账号不必重新登录。

桌面里还塞了什么

如果只是 worktree 管理器，它不会涨到这个体量。仓库 README 还列了这些：

手机 Companion。 桌面配对后，agent 跑完会推通知，你可以在外面补一句后续指令。iOS 上架 App Store，也有 TestFlight；Android 目前是 APK，英文 README 写到 0.0.50，中文 README 还停在 0.0.48，以 GitHub Release 为准更稳。

终端分屏。 自称 Ghostty 级，WebGL 渲染，无限分屏，滚动历史能熬过重启。

设计模式。 内嵌真实 Chromium。点页面上的某个元素，HTML、CSS 和裁好的截图直接进 agent 提示。修 UI 时比口头描述「那个按钮偏右一点」靠谱。

GitHub 和 Linear 原生界面。 应用里看 PR、issue、看板，从任务直接开 worktree。文档里还有 Jira 抽屉，创建 worktree 时也能贴 Jira 链接。

SSH worktree。 agent 可以跑在远程大机器上，文件编辑、git、终端都走过去，带自动重连和端口转发。无头 Linux 服务器另有 orca serve 指南。

给 AI diff 写批注。 某一行不行，评论丢回给智能体，评审、改、提交不用切出去。

编辑器。 用的是 VS Code 那套编辑器，自动保存。文件和图片可以拖进提示。Markdown、图片、PDF 能在工作区预览。

Orca CLI。 orca worktree create、snapshot、click、fill 这类命令让智能体反过来驱动 Orca。还有 Computer Use：需要真的点桌面应用时，走无障碍树、截图和受限制的 UI 操作。

快速打开可以搜 worktree、文件、智能体、命令和仓库上下文。通知系统会标出谁跑完了、谁卡住了，也可以标未读稍后再看。README 自己承认功能列表永远落后，真正的清单在 Releases，他们说每天都发。

安装

桌面支持 macOS、Windows、Linux。

  • 官网：onorca.dev/download
  • GitHub Release 直链：Apple Silicon dmg、Intel dmg、Windows exe、Linux AppImage
  • Homebrew：brew install --cask stablyai/orca/orca
  • Arch：AUR 上的 stably-orca-bin，源码包是 stably-orca-git

Windows 代码签名由 SignPath.io 赞助，证书来自 SignPath Foundation。

手机端需要先有桌面。iOS：App Store。Android APK 在 Releases 里，安装步骤见 Android 文档。

配对手机用的 relay 也在同一个仓库的 cloud/ 目录，单独一套 pnpm workspace。

和普通 AI IDE 差在哪

Cursor、Windsurf 这类产品把模型和编辑器绑在一起卖。Orca 反向：模型你自己订，应用负责编排。GitHub 简介写的就是「Run any coding agent with your own subscription」。

Claude Code 或 Codex 单独用，已经能改代码。缺的是同时跑多个、文件不打架、结果能并排看、远程机器和手机能接着管。Orca 押的是这个调度层。

它仍然是本地优先的桌面应用，不是云端把代码交出去代跑的服务。远程能力走 SSH 或自建 Orca Server。遥测文档说收集匿名使用数据，可以关掉。

使用时要注意

并行有成本。五个 worktree 就是五份磁盘，再加依赖目录。共享 node_modules 能省空间，也可能让两个 agent 同时改构建缓存时互相干扰。.env 这类文件官方建议复制，不要共享。

删除 worktree 会连分支一起删。如果 git 认为还有未合并提交，Orca 会留下分支并提示你复查，文件夹不会自动恢复。

Issue 数量不少。仓库公开 issue 有六千多，fork 大约五千。日更产品常见：功能来得快，边角会毛。合不合适，看你是不是真的在并行用多个 CLI agent。如果你一次只开一个 Claude Code，Orca 多半显得重。

中文社区有微信群。README 写的是第 9 群，二维码在仓库文档资源里。英文社区在 Discord，更新在 @orca_build。

结论

Orca 是一个开源桌面 ADE。它把「多个 CLI 编码智能体 + 每个任务一份 git worktree」当成默认工作方式，再补上终端、内嵌浏览器、评审、SSH 和手机监控。

值不值得装，取决于你有没有这种痛：同一个改动想让几个 agent 各写一版，或者一边修 bug 一边开新功能，还不想在同一份工作树上互相覆盖。有的话，从 GitHub 仓库 或 下载页 装一份就够判断。没有的话，它就是个功能很多的终端管理器，不必为了名单上的几十个 agent logo 专门换工具。

Oh My Pi：一个把 IDE 能力接进终端的编码 Agent

发表于 2026-09-16 分类于 AI 开发工具 ， 开源项目

Oh My Pi（OMP） 可以先用一句话概括：它是在 Pi 的基础上继续扩展的开源编码 Agent，仍把终端交互放在中心，却试图把编辑器里的语言服务、调试器和协作入口一起带到 Agent 工作流里。

它不是一个新的大模型，也不靠替换模型取胜。OMP 解决的是另一层问题：模型怎样读项目、改文件、运行命令、理解代码符号，并在需要时把任务交给别的 Agent 或编辑器。项目 README 把这一层称为 coding-first surface；更直白一点，就是给代码 Agent 准备一套比“聊天 + shell”更完整的运行环境。

它和 Pi 是什么关系

OMP 是 Pi 的 fork。Pi 本身强调可编程、可扩展的终端 Agent；OMP 保留了这些基础，同时加入了一批面向编码任务的内建能力，例如会话管理、子 Agent、斜杠命令、插件、模型路由和编辑器协议。

这层关系很重要。它意味着 OMP 并非从零定义一套 Agent 交互，而是在已有的终端 Agent 体验上做工程化加法。对于已经习惯 Pi 的人，迁移成本会低一些；对于从 Claude Code、Codex 或 Cursor 过来的人，则更容易把它理解成一个偏“可组合”的终端编码环境。

README 当前列出的技术构成也说明了这个取向：交互与 SDK 主要使用 TypeScript，性能敏感的底层能力则由 Rust 实现。项目声明其 Rust 核心约 8 万行，并提供多提供商模型接入、内建工具，以及 LSP 和 DAP 相关操作。这里的数量来自项目 README，适合作为能力范围的参考，不等同于第三方性能测评。

OMP 想补上的，正是终端 Agent 容易缺的那一段

纯终端 Agent 通常已经能读写文件、跑命令和调用模型，但它未必能稳定拿到编辑器掌握的语义信息。OMP 的设计重点，是把这些信息和操作放进同一个 Agent 回路。

让 Agent 使用语言服务和调试器

项目把 LSP 接到写入流程中。LSP 即 Language Server Protocol，编辑器依靠它提供跳转定义、查找引用、诊断和重命名等能力。对编码 Agent 来说，这意味着它可以少依赖字符串搜索，多利用符号和诊断来判断一次修改是否影响了别处。

OMP 也声明支持驱动真实调试器，并提供 DAP 相关操作。DAP 是 Debug Adapter Protocol。调试器接入不保证 Agent 自动找到所有运行时问题，但它给了 Agent 一条更接近开发者日常排障方式的路径：设置断点、观察变量、沿调用过程定位问题，而不只是在日志里猜。

子 Agent、审查和会话不再只是外围脚本

README 将子 Agent、第二模型审视每轮输出、代码审查、会话分支与恢复列为内建工作流的一部分。实际价值不在于“多 Agent”这个标签，而在于任务隔离：主 Agent 可以继续实现功能，同时让另一条会话检查风险、阅读文档或复现问题。

这类工作流适合问题边界清楚的任务，例如让一个子 Agent 审查补丁、让另一个调查测试失败。它仍然需要人来决定结论是否可信，尤其是在涉及权限、生产环境和合并发布时。

既能在终端跑，也能被别的宿主驱动

OMP 给出四种入口：交互式终端、一次性命令、Node/TypeScript SDK，以及基于标准输入输出的 RPC。后一种方式让非 Node 的宿主也可以通过 NDJSON 驱动 Agent。

另一个值得关注的是 omp acp。它实现 Agent Client Protocol（ACP），让编辑器可以作为客户端与 Agent 通信。编辑器若声明了对应能力，文件读写与终端操作能通过协议路由，写入操作还可由 session/request_permission 控制。对 IDE 作者或团队内部工具而言，这比模拟终端界面更适合作为集成点。

对已有配置的态度：尽量继承，而非强迫迁移

第一次启动时，OMP 会尝试发现本机已存在的规则、技能和 MCP 服务器配置，范围包括 .claude、.cursor、.windsurf、.gemini、.codex、.cline、.github/copilot 与 .vscode。项目的目标是减少“换一个 Agent 就重建一遍工作环境”的摩擦。

这项能力很方便，但也建议先检查继承到了什么。不同工具对规则优先级、命令权限和 MCP 配置的含义并不完全一致。把现成配置导入新工具之前，尤其要确认其中没有过宽的 shell 权限或不再需要的服务凭据。

扩展方式也相当直接：插件是 TypeScript 模块，可使用与内建功能相同的工具 API、斜杠命令注册表和终端 UI 原语。插件既可以只放在本地，也能打包发布到 marketplace 或 npm。这个设计适合有固定开发流程的团队，把约定做成可检查的工具，而不是反复贴进提示词。

哪些人值得试，哪些人可以先等等

如果你主要在终端中完成开发，又希望 Agent 能用 LSP、调试器、结构化编辑和可拆分的子任务，OMP 值得放进候选工具清单。它也适合需要把 Agent 嵌入自有编辑器、脚本或服务的开发者：SDK、RPC 和 ACP 覆盖了不同宿主的接入方式。

但如果你的需求只是偶尔让模型生成一段代码，OMP 的配置面和功能深度可能反而显得重。它提供的模型选择、插件、会话和工具策略需要花时间建立习惯。对个人项目而言，先用一个简单的终端 Agent 跑通“读代码—修改—测试”的闭环，再判断是否需要更复杂的 harness，通常更稳妥。

结语

Oh My Pi 最有意思的地方，不是又做了一个聊天入口，而是认真对待了代码 Agent 的运行环境：模型需要语义信息，需要调试路径，需要可控的权限和可复用的配置，也需要与编辑器、脚本和团队流程相连。

它选择的答案是保留终端的直接感，再把 IDE 与工程工具接进来。是否适合你，最终取决于你愿意把多少日常开发流程交给 Agent，以及你是否愿意为更强的可组合性承担相应的配置与验证成本。

CodexHost：在 Codex Desktop 里切换多种 Agent Harness

BytePioneer-AI/codex-host 做的事情很直接：把 Pi、Claude Code、OpenCode、Oh My Pi、Grok Build、DeepSeek Harness 等 Agent Harness 接进 Codex Desktop，让它们在同一个桌面窗口里运行。

它不是另一个聊天壳，也不是把所有模型包装成 OpenAI 兼容接口。项目的取舍是保留 Codex Desktop 的工作区、Thread、流式输出、工具状态、Diff、审批和提问界面，再把真正执行任务的 Harness 交给用户选择的原生程序。

先理解两个词

Agent 是执行任务的程序，例如 Claude Code 或 Pi。Harness 可以理解为 Agent 的运行框架：它负责读取项目、调用工具、修改文件、运行命令，并维护自己的会话状态。

CodexHost 把“显示界面”和“执行任务”拆开。Codex Desktop 负责统一呈现；被选中的 Harness 仍在自己的协议和权限模式下工作。这也是项目强调原生体验的原因：已有的工具审批、Diff 和登录状态，不必重新在一个第三方聊天框里模拟。

它是怎样接进去的

从仓库文档和代码结构看，CodexHost 大致分为四个部分：

  • Desktop 集成：通过 CDP / Electron Inspector 在官方 Codex Desktop 界面中增加 Agent 选择和会话入口，不重做整个聊天界面。
  • 协议适配：用 CLI Shim 与官方 app-server 对接，让 Codex 的请求可以透明转发到目标 Harness。
  • Harness 适配器：不同 Agent 按各自原生接口接入，例如 Pi 的 RPC、Claude Code 的 SDK/CLI；输出再映射回 Desktop 的流式文本、工具、Diff 和审批组件。
  • 会话编排：被委派的任务会创建独立 Native Session，并保存委派关系。发起方可以在 Codex Desktop 的会话列表里查看进度或继续对话。

DeerFlow 介绍：把复杂任务交给可编排的智能体

发表于 2026-08-28 分类于 人工智能 ， Agent 工程

DeerFlow 是一个开源的智能体运行框架。它的重点不是把聊天窗口做得更像人，而是把一个目标拆成计划、检索、代码执行、文件处理和结果交付等环节，再交给模型、工具和子智能体协同完成。

如果把大语言模型看成负责判断的“大脑”，DeerFlow 更像一套工作台：它负责准备上下文、调度工具、保存中间产物，并在需要时让多个智能体接力。这个定位决定了它更适合深度研究、代码任务和长流程内容生产，而不是只追求一次对话的即时回答。

DeerFlow 解决什么问题

简单问答通常只需要一次模型调用。复杂任务却会不断遇到相同的工程问题：资料要从哪里来，哪些操作可以自动执行，长任务如何保留上下文，子任务完成后怎样汇总，最终结果如何让人检查。

DeerFlow 把这些问题放到同一个运行环境里处理。以“写一份行业研究”为例，流程可以是：先明确研究问题，再搜索和阅读资料，随后让不同子智能体分别整理市场、技术和竞品信息，最后由主智能体合并结论并附上可追溯的来源。具体步骤取决于配置和接入的模型，框架本身不替使用者保证结论正确。

核心组成

主智能体与子智能体

主智能体负责理解目标、制定计划和汇总结果。子智能体则接手边界清晰的工作，例如检索资料、分析代码或整理文档。拆分之后，每个子任务拥有更小的上下文，主流程也更容易重试和调整。

多智能体并不等于“人越多越快”。如果任务边界没有写清楚，子智能体可能重复劳动，或者把未经核实的中间结论直接传给主流程。实际使用时，应明确输入、输出、权限和完成条件。

工具、MCP 与 Skills

DeerFlow 可以通过工具访问文件、网页、命令行和其他服务，也可以接入 MCP（Model Context Protocol）服务器。工具描述“能做什么”，MCP 约定“如何把能力提供给模型”，而 Skills 更接近一份可复用的工作流程说明。

这几层概念最好分开理解：一个网页搜索工具可以被多个流程复用；一个“调研报告”Skill 则可以规定先搜索、再去重、再核查来源，最后输出报告。这样做比把所有规则堆在一段提示词里更容易维护。

沙箱与长任务

需要运行代码、处理文件或安装依赖时，隔离环境很重要。沙箱可以限制工作目录、网络和可执行操作，降低误删文件或泄露凭据的风险。长任务则需要保存中间文件、日志和状态，便于暂停后继续，而不是每次从头开始。

这些能力带来便利，也带来成本：沙箱需要额外的资源配置，长任务需要设计超时、重试和清理策略。部署前应先确认运行环境是否满足项目当前版本的要求。

一次任务大致怎样运行

其中最容易被忽略的是“核查与重试”。工具调用成功，只能说明命令执行完成；它不代表网页内容可信、代码没有缺陷，或报告已经满足要求。把测试、来源检查和人工确认放进流程，才能让自动化结果更可靠。

适合哪些场景

  • 深度研究：围绕一个问题持续搜索、阅读、比较和汇总资料。
  • 代码任务：读取仓库、运行测试、修改文件，再提交带验证信息的结果。
  • 文档生产：把多种输入整理成报告、方案或结构化知识。
  • 内部自动化：连接企业 API、文件系统和知识库，处理有明确边界的重复工作。

如果需求只是“问一个事实”或“改一行配置”，直接调用模型或脚本通常更简单。DeerFlow 的价值在于流程较长、需要工具协同，并且希望保留中间过程的任务。

使用前要注意什么

第一，模型能力不是框架能力。DeerFlow 可以调度模型和工具，却无法自动消除幻觉；重要结论仍应保留来源并进行人工抽查。

第二，权限要从小开始。文件写入、命令执行、联网和外部 API 都应设置明确范围；涉及删除、发布或付费操作时，最好加入人工审批。

第三，成本需要量化。多轮推理、多个子智能体和长上下文会增加模型调用次数与运行时间。可以先用一个小任务测量 token、延迟和失败率，再决定是否扩大并发。

第四，版本变化要留痕。DeerFlow 的目录结构、配置项和推荐模型会随版本更新，部署时应以对应版本的 README 和示例配置为准，不要直接套用旧文章中的命令。

如何开始了解

最稳妥的路径是先阅读官方仓库的 README，确认当前版本的依赖、启动方式和模型配置，再运行一个只读的小任务。等检索、日志和结果交付都能正常工作后，再逐步开放代码执行、文件写入和外部服务访问。

  • 官方仓库：bytedance/deer-flow
  • 项目文档与示例：以仓库中的当前版本说明为准

结语

DeerFlow 的看点不在于“让一个模型变得无所不能”，而在于把复杂任务拆成可调度、可观察、可复用的步骤。它适合拿来搭建研究助手、代码代理和内部自动化流程；是否值得引入，取决于任务长度、工具数量、权限要求和可接受的运行成本。

把它当作一套工程基础设施来评估，会比把它当作一个新的聊天应用更准确。

AI 原生软件开发生命周期：从代码提速到流程重构

发表于 2026-08-27 分类于 软件工程 ， 人工智能

本文是对 Anthropic《The AI-Native SDLC playbook》的中文分享与提炼。原文页面标注发布日期为 2026 年 8 月 21 日、更新日期为 8 月 26 日。文中关于 Claude 产品和 Anthropic 团队实践的描述属于厂商自述，不等同于独立评测或普遍适用的工程结论。

代码变快之后，真正慢的是什么？

过去一年，代理式 AI 让“写代码”这件事明显提速。问题是，围绕代码的流程没有一起变快：需求还在等会议，设计还在等评审，安全检查还在排队，发布还要等下一个窗口。

这就是原文开篇想指出的反差：**当构建阶段从开发周期里塌缩出去，瓶颈就会转移到它的左边和右边。**计划、评审与测试、部署，仍然按人的速度运行。于是，团队可能得到更多代码，却没有得到更多可靠的软件。

原文没有提供跨组织的独立基准，不能据此断言“用了 Claude 就一定更快”。更准确的理解是：如果代理确实把代码产出推高，原来的人工闸门就可能变成新的排队点；SDLC 需要和实现阶段一样，重新设计。

AI 原生 SDLC：不是自动化一段流程，而是把流程变成回路

传统 SDLC 像一条接力赛：计划交给设计，设计交给构建，构建交给测试，测试交给发布，最后由运维看着线上。每一棒都有文档、工单和签字，但交接往往是手工的，信息也会在交接中变形。

Anthropic 所说的 AI 原生 SDLC，更像一个持续运行的回路：AI 嵌入每个阶段，阶段之间自动交接；旧流程要求的控制目标继续保留，但控制方式改成版本化文件、自动检查、钩子和分层授权。原文也把它称为 agentic SDLC 或 AI SDLC，名称不同，指的是同一类变化。

最容易被忽略的是“承诺产物”。每个阶段结束时，都要把一个下阶段可读取的东西提交到版本控制：计划阶段可能是 intent.md，设计阶段是 spec.md，构建阶段是 plan.md、代码和测试，测试阶段是评估结果，部署阶段是 PR 及其审查记录，维护阶段则是事故记录或 lessons 文件。下一个阶段从这些提交开始，而不是从一段没有上下文的聊天开始。

这样一来，提交历史本身就成了审计轨迹：谁提出了什么，代理生成了什么，哪些检查通过了，谁批准了高风险动作。人的责任没有消失，只是人的注意力从“把每一行都看一遍”，转向目标、例外和需要判断的地方。

六个阶段，变化到底在哪里？

阶段 传统做法 AI 原生做法（原文描述的方向）
计划 需求由会议、工作坊和签字逐层整理 从真实来源提炼痛点，写入人可读、机器可执行的 intent.md
设计 分析师写规格，设计师再解释规格 与代理在一次工作会话中压缩需求和设计，规范以 skills 维护并进入 Git
构建 代码、测试手写，文档常常事后补 AI 生成代码和测试，团队知识写入版本化的 CLAUDE.md 与 skills
测试 在阶段边界设置 QA 闸门 把持续评估（evals）织进实现过程，而不是最后才验收
部署 人工逐行审查，治理依赖周期性评审 代理分层审查；关键或受监管代码保留人工审查，hooks 作为批准闸门
维护 人盯着生产环境等问题出现 代理监控线上部署，越过控制带后诊断，并写回新的 intent.md

这不是要求所有组织立刻跳到右侧。原文把两列当作光谱的两端，多数团队会处于中间位置。重要的是右侧贯穿始终的那条线：每一阶段都留下可提交、可读取、可追踪的产物。

Plan：先写意图，再让代理行动

原文反复使用 intent.md，不是为了增加一个文档格式，而是为了让“为什么做这件事”进入后续自动化。一个可用的意图文件至少要说明问题或异常、证据、预期结果、受影响系统和仍未解决的问题。

它既能承载产品需求，也能承载监控异常和较大的安全发现。产品负责人和代理读的是同一份文件，后续的设计、实现和分诊不必重新猜测背景。

这里的人类工作不是替 AI 写得更详细，而是确认范围、约束和验收条件。意图不清楚时，自动化只会把模糊更快地放大。

Design：把组织知识变成代理能读的约束

传统设计阶段常见的问题，是规范停留在某个人的经验里，或者写完就过期。AI 原生做法是把架构决策、接口契约、非功能要求和编码规范，放进代理能检索的项目上下文，并通过 Git 管理变更。

原文提到用 skills 编码标准，用 CLAUDE.md 保存团队知识。它们的意义不在于“给模型更多提示词”，而在于把隐性的组织规则变成可复用、可审查的资产。涉及数据、权限和合规的决定，仍由负责团队确认；代理只能在给定约束里提出方案。

Build：从“生成代码”转向“生成可验证的变更”

Claude Code 在原文中扮演的不是自动提交机器人，而是能够读上下文、修改代码、生成测试、解释 diff、发起 PR 的协作者。真正的分界线在于：能写出来，不等于能合并。

构建阶段应该尽量让代理处理可拆分、可验证的工作；主干是否接受这次变更，则交给自动检查、分支保护和人工评审。代码越敏感，人的审查越应该靠近风险，而不是平均地把时间花在每一行上。

Test：把质量从最后一道门，移到整个过程里

如果测试只在构建完成后才开始，代理越快，最后的排队越长。原文建议把持续评估（evals）织进实现过程，持续验证功能行为、回归风险和安全边界。

这并不意味着减少测试，而是改变测试的时机和对象：除了检查代码行，还要检查代理是否遵守项目规范、是否覆盖关键行为、是否在边界条件下给出可接受的结果。一次事故修复后补充对应评估用例，才能把一次性的经验变成下一次仍会运行的保护措施。

Deploy：把治理做成代理行动时的约束

原文给出的方向是“分层代理审查”。低风险动作可以自动检查或只读诊断；涉及关键系统、受监管代码或生产变更时，保留人工批准。hooks、分支保护和预先批准的 runbook，负责把权限写成机器能执行的规则。

部署自动化不等于放弃审批。更现实的例子是：当异常超过既定控制带，代理可以打开一个 PR，或者调用已经批准的回滚流水线，但不能自己批准自己的修复。调用、诊断、批准和结果都进入带时间戳的记录。

Maintain：让线上反馈重新进入计划

维护阶段是这套方法最有意思的地方。监控、事故和安全扫描不再是 SDLC 之外的“运维杂事”，而是能重新触发计划的输入。

持续监控循环

原文用 bands.yaml 展示分层响应：先由确定性的规则判断指标是否偏离基线，再决定 Claude 可以做什么。示例中，1σ 只记录，2σ 允许只读诊断，3σ 才能提出 PR 或调用预批准 runbook。这个阈值是示例，不应直接当成通用最佳实践。

关键原则是：检测保持确定性，模型只在规则触发后被调用；响应等级写入版本控制；权限系统阻止代理直接获得生产写权限。异常处理完成后，诊断和证据可以整理成新的 intent.md，重新回到计划阶段。

定期安全扫描

一次安全扫描只代表某个时间点，而且代码和模型都会变化。原文建议按项目设定扫描计划，给每条发现附上验证结果和置信度，驳回时留下原因。

范围明确的问题可以生成补丁并走 PR；跨服务的架构弱点则写成 intent.md，从计划阶段开始。模型驱动的扫描补充 CI 中的静态分析和依赖检查，而不是替代它们。

事故频道也是工作流的一部分

原文还描述了 Claude Tag 在 Slack 中参与值班的场景：事故消息出现在频道里，Claude 以自己的身份读取上下文、验证指标是否恢复、协助提出修复，并把复盘写入版本控制的 lessons 文件。

这里真正重要的不是“让机器人待在 Slack”，而是让请求、诊断、人的授权和修复结果留在同一个可回看的地方。小而明确的修复走 PR，较大的问题重新写成 intent.md。频道因此成为反馈链的一部分，而不是一个临时的黑盒。

治理的底线：人不退出，人的位置改变

AI 原生 SDLC 不是“让代理自己上线”，而是把人的判断放到更值得投入的地方：定义目标，确认边界，批准高风险动作，处理例外，复核结果。

一套可执行的边界至少包括：

  • 代理默认只读，生产动作通过受限工具完成。
  • 阈值、工具白名单、skills、hooks 和 runbook 全部版本化。
  • 代理提出的变更不能由自己批准，必须经过 PR 和分支保护。
  • 调用、诊断、驳回、批准和发布都有审计记录。
  • 用交付周期、缺陷率、回滚率、安全发现处理时间和评审积压衡量结果，而不是只看生成了多少代码。

一个稳妥的落地顺序

先统一 intent.md 模板，把测试、监控和安全发现接入现有工单或 PR；再为代理设置只读权限和工具白名单；接着开放“提出变更”的能力；最后才考虑触发预批准 runbook。每扩大一层权限，就补上日志、评估和回滚方案。

这条顺序的好处是，团队可以先验证反馈链是否真的工作，再决定是否让代理承担更高风险的动作。没有审计和回退能力时，增加模型权限只是在放大未知风险。

原文精髓，可以压缩成三句话

第一，代码不再是唯一瓶颈，流程周围的人工速度会暴露出来。第二，AI 原生 SDLC 是一个由承诺产物连接起来的闭环，不是六个孤立的自动化工具。第三，人的判断不会被删除，而是从重复搬运转向目标、例外和责任。

本文是对 Anthropic《The AI-Native SDLC playbook》的中文分享与提炼。原文页面标注发布日期为 2026 年 8 月 21 日、更新日期为 8 月 26 日。文中关于 Claude 产品和 Anthropic 团队实践的描述属于厂商自述，不等同于独立评测或普遍适用的工程结论。

代码变快之后，真正慢的是什么？

过去一年，代理式 AI 让“写代码”这件事明显提速。问题是，围绕代码的流程没有一起变快：需求还在等会议，设计还在等评审，安全检查还在排队，发布还要等下一个窗口。

这就是原文开篇想指出的反差：当构建阶段从开发周期里塌缩出去，瓶颈就会转移到它的左边和右边。计划、评审与测试、部署，仍然按人的速度运行。于是，团队可能得到更多代码，却没有得到更多可靠的软件。

原文没有提供跨组织的独立基准，不能据此断言“用了 Claude 就一定更快”。更准确的理解是：如果代理确实把代码产出推高，原来的人工闸门就可能变成新的排队点；SDLC 需要和实现阶段一样，重新设计。

AI 原生 SDLC：不是自动化一段流程，而是把流程变成回路

传统 SDLC 像一条接力赛：计划交给设计，设计交给构建，构建交给测试，测试交给发布，最后由运维看着线上。每一棒都有文档、工单和签字，但交接往往是手工的，信息也会在交接中变形。

Anthropic 所说的 AI 原生 SDLC，更像一个持续运行的回路：AI 嵌入每个阶段，阶段之间自动交接；旧流程要求的控制目标继续保留，但控制方式改成版本化文件、自动检查、钩子和分层授权。原文也把它称为 agentic SDLC 或 AI SDLC，名称不同，指的是同一类变化。

最容易被忽略的是“承诺产物”。每个阶段结束时，都要把一个下阶段可读取的东西提交到版本控制：计划阶段可能是 intent.md，设计阶段是 spec.md，构建阶段是 plan.md、代码和测试，测试阶段是评估结果，部署阶段是 PR 及其审查记录，维护阶段则是事故记录或 lessons 文件。下一个阶段从这些提交开始，而不是从一段没有上下文的聊天开始。

这样一来，提交历史本身就成了审计轨迹：谁提出了什么，代理生成了什么，哪些检查通过了，谁批准了高风险动作。人的责任没有消失，只是人的注意力从“把每一行都看一遍”，转向目标、例外和需要判断的地方。

六个阶段，变化到底在哪里？

阶段传统做法AI 原生做法（原文描述的方向）
计划需求由会议、工作坊和签字逐层整理从真实来源提炼痛点，写入人可读、机器可执行的 intent.md
设计分析师写规格，设计师再解释规格与代理在一次工作会话中压缩需求和设计，规范以 skills 维护并进入 Git
构建代码、测试手写，文档常常事后补AI 生成代码和测试，团队知识写入版本化的 CLAUDE.md 与 skills
测试在阶段边界设置 QA 闸门把持续评估（evals）织进实现过程，而不是最后才验收
部署人工逐行审查，治理依赖周期性评审代理分层审查；关键或受监管代码保留人工审查，hooks 作为批准闸门
维护人盯着生产环境等问题出现代理监控线上部署，越过控制带后诊断，并写回新的 intent.md

这不是要求所有组织立刻跳到右侧。原文把两列当作光谱的两端，多数团队会处于中间位置。重要的是右侧贯穿始终的那条线：每一阶段都留下可提交、可读取、可追踪的产物。

Plan：先写意图，再让代理行动

原文反复使用 intent.md，不是为了增加一个文档格式，而是为了让“为什么做这件事”进入后续自动化。一个可用的意图文件至少要说明问题或异常、证据、预期结果、受影响系统和仍未解决的问题。

它既能承载产品需求，也能承载监控异常和较大的安全发现。产品负责人和代理读的是同一份文件，后续的设计、实现和分诊不必重新猜测背景。

这里的人类工作不是替 AI 写得更详细，而是确认范围、约束和验收条件。意图不清楚时，自动化只会把模糊更快地放大。

Design：把组织知识变成代理能读的约束

传统设计阶段常见的问题，是规范停留在某个人的经验里，或者写完就过期。AI 原生做法是把架构决策、接口契约、非功能要求和编码规范，放进代理能检索的项目上下文，并通过 Git 管理变更。

原文提到用 skills 编码标准，用 CLAUDE.md 保存团队知识。它们的意义不在于“给模型更多提示词”，而在于把隐性的组织规则变成可复用、可审查的资产。涉及数据、权限和合规的决定，仍由负责团队确认；代理只能在给定约束里提出方案。

Build：从“生成代码”转向“生成可验证的变更”

Claude Code 在原文中扮演的不是自动提交机器人，而是能够读上下文、修改代码、生成测试、解释 diff、发起 PR 的协作者。真正的分界线在于：能写出来，不等于能合并。

构建阶段应该尽量让代理处理可拆分、可验证的工作；主干是否接受这次变更，则交给自动检查、分支保护和人工评审。代码越敏感，人的审查越应该靠近风险，而不是平均地把时间花在每一行上。

Test：把质量从最后一道门，移到整个过程里

如果测试只在构建完成后才开始，代理越快，最后的排队越长。原文建议把持续评估（evals）织进实现过程，持续验证功能行为、回归风险和安全边界。

这并不意味着减少测试，而是改变测试的时机和对象：除了检查代码行，还要检查代理是否遵守项目规范、是否覆盖关键行为、是否在边界条件下给出可接受的结果。一次事故修复后补充对应评估用例，才能把一次性的经验变成下一次仍会运行的保护措施。

Deploy：把治理做成代理行动时的约束

原文给出的方向是“分层代理审查”。低风险动作可以自动检查或只读诊断；涉及关键系统、受监管代码或生产变更时，保留人工批准。hooks、分支保护和预先批准的 runbook，负责把权限写成机器能执行的规则。

部署自动化不等于放弃审批。更现实的例子是：当异常超过既定控制带，代理可以打开一个 PR，或者调用已经批准的回滚流水线，但不能自己批准自己的修复。调用、诊断、批准和结果都进入带时间戳的记录。

Maintain：让线上反馈重新进入计划

维护阶段是这套方法最有意思的地方。监控、事故和安全扫描不再是 SDLC 之外的“运维杂事”，而是能重新触发计划的输入。

持续监控循环

原文用 bands.yaml 展示分层响应：先由确定性的规则判断指标是否偏离基线，再决定 Claude 可以做什么。示例中，1σ 只记录，2σ 允许只读诊断，3σ 才能提出 PR 或调用预批准 runbook。这个阈值是示例，不应直接当成通用最佳实践。

关键原则是：检测保持确定性，模型只在规则触发后被调用；响应等级写入版本控制；权限系统阻止代理直接获得生产写权限。异常处理完成后，诊断和证据可以整理成新的 intent.md，重新回到计划阶段。

定期安全扫描

一次安全扫描只代表某个时间点，而且代码和模型都会变化。原文建议按项目设定扫描计划，给每条发现附上验证结果和置信度，驳回时留下原因。

范围明确的问题可以生成补丁并走 PR；跨服务的架构弱点则写成 intent.md，从计划阶段开始。模型驱动的扫描补充 CI 中的静态分析和依赖检查，而不是替代它们。

事故频道也是工作流的一部分

原文还描述了 Claude Tag 在 Slack 中参与值班的场景：事故消息出现在频道里，Claude 以自己的身份读取上下文、验证指标是否恢复、协助提出修复，并把复盘写入版本控制的 lessons 文件。

这里真正重要的不是“让机器人待在 Slack”，而是让请求、诊断、人的授权和修复结果留在同一个可回看的地方。小而明确的修复走 PR，较大的问题重新写成 intent.md。频道因此成为反馈链的一部分，而不是一个临时的黑盒。

治理的底线：人不退出，人的位置改变

AI 原生 SDLC 不是“让代理自己上线”，而是把人的判断放到更值得投入的地方：定义目标，确认边界，批准高风险动作，处理例外，复核结果。

一套可执行的边界至少包括：

  • • 代理默认只读，生产动作通过受限工具完成。
  • • 阈值、工具白名单、skills、hooks 和 runbook 全部版本化。
  • • 代理提出的变更不能由自己批准，必须经过 PR 和分支保护。
  • • 调用、诊断、驳回、批准和发布都有审计记录。
  • • 用交付周期、缺陷率、回滚率、安全发现处理时间和评审积压衡量结果，而不是只看生成了多少代码。

一个稳妥的落地顺序

先统一 intent.md 模板，把测试、监控和安全发现接入现有工单或 PR；再为代理设置只读权限和工具白名单；接着开放“提出变更”的能力；最后才考虑触发预批准 runbook。每扩大一层权限，就补上日志、评估和回滚方案。

这条顺序的好处是，团队可以先验证反馈链是否真的工作，再决定是否让代理承担更高风险的动作。没有审计和回退能力时，增加模型权限只是在放大未知风险。
