# 今日知识点：Toolformer：语言模型如何学会决定何时调用工具

> 一句话：让语言模型自己生成、执行并筛选 API 调用示例，再用这些示例微调，使“要不要用工具”成为模型可学习的决策。

**分类**：Agent 与工具　**难度**：3　**资料截至**：2026-09-15

## 它解决什么问题？

语言模型擅长从训练语料中预测文字，却不擅长精确计算、查询实时信息或执行确定性操作。传统做法是人工为每个任务编写工具规则，覆盖范围有限；仅靠提示词让模型调用 API，又常出现乱调用、参数格式错误或调用时机不对。Toolformer 研究的问题是：能否只用少量人工示例，让模型从海量无标注文本中学会何时调用工具、传什么参数，以及如何把返回结果接回句子。

## 工作机制

流程分为“生成—执行—筛选—微调”四步。首先给基础语言模型少量带 API 标记的示例，并在普通文本中采样可能的调用位置，例如 `问题是 17×24？<API>calculator(17*24)`。模型生成候选调用及参数后，程序真正执行 API，把返回值插回文本。

接着进行自动筛选：比较“包含 API 返回结果”和“不调用 API”时模型对后续文本的损失。如果返回结果让后续 token 更容易预测，说明这次调用提供了有用信息；若没有改善，或参数无效、输出不连贯，就丢弃该样本。最后用保留下来的文本（含 API 调用和结果）继续训练模型。模型因此学到 API 的调用语法、参数模式和触发条件，而不需要为每个样本人工写标签。

## 一个具体例子

句子“东京现在是几点？答案是”中，模型可能插入 `<API>time(Asia/Tokyo)`。执行器返回“09:00”，再把完整序列用于训练。遇到“100 美元约合多少欧元”时，模型可调用汇率 API；遇到普通闲聊则不调用。部署时仍由外部执行器负责权限、超时和结果校验，模型只提出调用请求。

## 容易混淆的概念

- **ReAct**是在推理过程中交替产生 Thought、Action、Observation，强调多步轨迹；Toolformer 的重点是用自监督数据训练“何时调用”和“如何调用”的能力。
- **函数调用微调**通常依赖人工或合成的明确调用标签；Toolformer 用 API 执行结果对候选样本做损失筛选，标签生成更自动化。
- **RAG**专门把外部文档检索回上下文；Toolformer 是更一般的工具使用框架，计算器、翻译器和搜索都可以成为工具。

## 局限与实践建议

自动筛选依赖基础模型的概率判断：模型可能因偶然降低损失而保留错误调用，也可能漏掉对长程任务有帮助的工具。API 返回值若过时、含噪或格式不稳定，会把错误模式写进训练集。论文中的工具集合和模型规模有限，不能直接保证在生产 API 上可靠。实践中应把工具白名单、参数 schema、速率限制和人工确认放在执行器侧；记录每次调用的输入、版本与返回值，离线评估调用准确率、无谓调用率、任务成功率和额外延迟，并为失败调用设计重试或回退路径。

## 为什么现在值得关注

Toolformer 论文发表于 2023-02-09，提出了一个仍具普适性的思路：把“工具是否有帮助”转化为可计算的训练信号，再让模型从数据中学习调用策略。随着 Agent 从单一函数调用走向搜索、代码执行和企业系统编排，这种数据构造方法有助于减少完全依赖人工轨迹的成本；但安全边界和执行权限始终不能交给模型概率自行决定。

## 自测

为什么 Toolformer 要比较“调用后续文本损失”而不是只检查 API 返回值是否正确？请说明这种筛选如何判断一次调用对语言生成是否真的有帮助。
