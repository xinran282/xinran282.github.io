# 今日知识点：连续批处理：大模型服务如何减少请求排队和 GPU 空转

> 一句话：让新请求在旧请求生成过程中动态加入批次，提高 GPU 利用率而不必等待整批结束。

**分类**：工程与产品　**难度**：4　**资料截至**：2026-09-07

## 它解决什么问题

大语言模型在线服务面对的是长度各异、到达时间不一的请求。传统静态批处理要等一批请求凑齐，再让它们一起生成；短请求结束后，批次里会留下空位，长请求却仍占着 GPU，导致排队时间和尾延迟上升。若完全逐条处理，GPU 又难以持续进行大规模矩阵运算。

连续批处理（continuous batching，也叫 iteration-level scheduling）把调度粒度从“一次完整生成”缩小到“一个或几个 token 的迭代”。每轮迭代结束后，服务端可以移除已经完成的序列，并把等待队列中的新序列加入下一轮，不必等整个批次结束。

## 工作机制

服务端维护一个运行队列和等待队列。每次调度大致执行：

1. 从运行队列挑选若干序列，结合 GPU 显存预算组成本轮 batch。
2. 模型为每个序列计算一次前向并生成下一个 token，同时更新各自的 KV Cache。
3. 已达到 EOS、长度上限或停止条件的序列立即退出并释放资源。
4. 根据空出的计算和 KV Cache 空间，把等待请求插入下一轮；必要时按优先级、到达时间或 token 预算做取舍。

Orca 论文将这种细粒度调度称为 iteration-level scheduling，并指出它能让不同长度请求共享执行过程。工程实现还要把“算力批大小”和“KV Cache 容量”一起考虑：批次太大可能显存不足，太小则吞吐不高；长上下文请求可能挤占短请求，需要设置最大 token 数或公平策略。

## 一个具体例子

假设请求 A 需要生成 100 个 token，B 需要 10 个，C 在 A、B 运行到第 5 轮时到达。静态批处理通常要等 A 完成，C 才能进入下一批；连续批处理则在 B 完成后立即移除 B，并在后续迭代把 C 加入，形成 A+C 的新批次。这样 C 不必等待 A 的剩余 90 个 token，GPU 也不会因为 B 提前结束而出现长期空槽。

实际系统会同时监控首 token 延迟（TTFT）、每输出 token 延迟（TPOT）、吞吐量和 P99 尾延迟。面向交互式请求时，可给新请求保留一部分调度预算；面向离线任务时，则可提高批次填充率。不同服务框架的参数名称和调度策略会随版本变化，应以具体版本文档为准。

## 它和什么容易混淆

连续批处理不是把多个请求简单拼成一个更大的静态 batch，也不是 speculative decoding。前者改变的是**请求何时加入或退出**；后者改变的是**每次如何提出和验证 token**。连续批处理通常还要配合 PagedAttention 或其他 KV Cache 管理方案，但两者是正交的：一个负责调度，另一个负责显存布局。

## 局限与实践建议

动态加入请求会增加调度复杂度和显存碎片风险。若只追求吞吐，长请求可能造成短请求饥饿；若过度照顾短请求，又会降低整体利用率。建议按业务目标设定最大 batch token 数、上下文长度和优先级，压测不同长度分布下的 TTFT、TPOT、吞吐与 P99，而不要只看平均延迟。发生 OOM 时，先检查 KV Cache 预算和并发上限，再考虑降低 batch；不要把增大 batch 当成唯一优化手段。

## 为什么现在值得关注

Orca 论文发表于 2023-06-01，连续批处理已经成为现代 LLM 推理服务的重要调度思想。随着长上下文和多租户请求增多，系统瓶颈常常不在单次矩阵乘，而在排队、缓存和尾延迟；理解迭代级调度有助于正确解读 vLLM 等服务框架的性能参数。
