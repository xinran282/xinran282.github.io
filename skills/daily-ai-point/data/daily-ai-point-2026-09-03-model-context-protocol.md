# 今日知识点：Model Context Protocol：Agent 如何用统一协议连接工具与数据

> 一句话：MCP 把“模型能看到什么、能调用什么”变成一套可协商的标准接口。

**分类**：Agent 与工具　**难度**：3　**资料截至**：2026-09-03

## 它解决什么问题

一个 Agent 往往同时需要文件、数据库、搜索、代码执行和业务 API。若每个应用都为每个服务单独写适配器，工具描述、参数格式、权限处理和错误语义都会重复实现，迁移成本很高。MCP（Model Context Protocol）提供了统一的连接方式，但它不是“把任意工具自动变安全”的魔法：协议只规定交互边界，应用仍要负责授权和隔离。

## 工作机制

MCP 将参与者分成三层：Host 是发起连接的 LLM 应用（例如 IDE 或聊天应用）；Client 是 Host 内部的连接器；Server 是提供上下文和能力的外部服务。它们通过 JSON-RPC 2.0 消息通信。一次典型会话可分为：

1. **初始化与协商**：Client 和 Server 交换协议版本及能力（capabilities），例如是否支持工具列表、资源订阅或采样。
2. **发现**：Client 请求 Server 暴露的 resources、prompts、tools。Resource 是可供模型参考的数据，prompt 是可复用的消息模板，tool 是模型请求执行的函数。
3. **调用与返回**：模型选择一个工具，Host 在用户授权后发送结构化参数；Server 返回结果或明确的错误。长任务还可以报告进度、接受取消请求并写日志。
4. **生命周期结束**：连接关闭时释放会话状态。由于连接是有状态的，双方不能只假定每次请求都独立。

这种分层让“模型决策”和“执行动作”分开：模型提出意图，Host 控制是否授权，Server 执行具体能力。部分客户端能力还包括 sampling（请求 Host 进行模型采样）、roots（声明可操作的 URI/文件系统边界）和 elicitation（向用户请求补充信息）。

## 一个具体例子

假设你在 IDE 中询问“统计本仓库过去一周的错误日志”。Host 连接日志 MCP Server 后，先发现 `search_logs` 工具及其参数 schema，再展示“读取日志并执行查询”的授权提示。你批准后，Host 发送类似下面的 JSON-RPC 请求（示意）：

```json
{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"search_logs","arguments":{"repo":"./app","since":"7d","level":"error"}}}
```

Server 返回结构化结果，模型再把结果归纳成报告。换一个支持 MCP 的 Host，只要它理解相同的发现和调用语义，Server 通常无需重写；但具体工具名称、参数和权限界面仍由服务提供者定义。

## 它和什么容易混淆

MCP 与普通 REST API 都能调用服务，但 REST 通常只描述业务端点，调用方还要自行约定工具发现、上下文资源、能力协商和 Agent 交互。MCP 也不同于函数调用（function calling）：函数调用是模型 API 中的输出格式，MCP 则覆盖 Host、Client、Server 之间的生命周期、发现和传输协议；一个 MCP Host 可以把发现到的工具转换成模型所需的函数 schema。

## 局限与实践建议

工具描述和返回内容都应当视为不可信输入，尤其不能仅凭描述就授予写文件、发消息或执行命令的权限。实现时应使用最小权限的 roots、按次确认高风险工具、限制网络和文件范围，并记录调用者、参数摘要和结果状态。Server 不应默认获得 Host 的全部提示词或用户数据；传输层还要配置认证、加密和超时。协议版本会演进，部署前应锁定并测试具体版本（本文依据 2025-06-18 规范页面），不要把不同 SDK 的扩展当成跨实现保证。

## 为什么现在值得关注

MCP 官方规范把工具、资源和提示模板放进同一个可组合协议，降低了 Agent 接入新数据源的重复工作，也使“发现—授权—执行—审计”成为可以单独评估的工程环节。真正的收益取决于 Host 是否提供清晰的同意流程，以及 Server 是否遵守最小权限原则。
