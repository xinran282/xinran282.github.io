# 今日知识点：ReAct：让 Agent 在思考与行动之间循环

> 一句话：ReAct 把语言模型的推理过程与工具行动交替组织，让每一步都能利用新观察修正计划。

**分类**：Agent 与工具　**难度**：3　**资料截至**：2026-09-11

## 它解决什么问题

只让模型“先想完整计划再执行”，遇到网页、数据库或 API 的真实返回值时容易走偏；只让模型不断调用工具，又可能缺少解释和目标约束。ReAct（Reasoning and Acting）提出一种交替轨迹：模型先生成当前思考和下一步行动，环境返回观察结果，模型再根据观察继续推理或采取行动。

这种方式适合多跳问答、网页操作和需要中途检查的任务。它不是一个具体工具库，而是一种提示与执行范式；安全、权限和停止条件仍由外部 Agent 框架负责。

## 工作机制

一条 ReAct 轨迹通常包含四类片段：

1. **Thought**：明确当前目标、已知事实和缺口；
2. **Action**：选择工具及结构化参数；
3. **Observation**：接收工具真实返回（结果、错误或空值）；
4. 循环，直到得到足够证据并输出 **Final**。

提示示例可以写成：

```text
Thought: 需要确认该版本的官方发布日期。
Action: search_docs({"query":"product v2 release date"})
Observation: 官方文档显示发布日期为 2026-08-30。
Thought: 已有一手来源，继续核对版本号后再回答。
Action: open_doc({"url":"..."})
```

关键点是 Observation 必须来自环境，而不是模型自己编造。执行器应解析 Action、校验参数、检查权限，再把结果作为下一轮上下文。若工具报错，模型可以修改查询或选择替代路径；若证据充分，则停止循环，避免无意义调用。

## 一个具体例子

问题：“比较两个 API 版本的限流变化，并给出官方出处。”模型先检索版本说明，再打开两份文档，提取限流数字，最后按字段对比。假设第一次搜索只找到博客，模型可以根据观察结果判断来源等级不足，继续寻找官方 changelog，而不是立即生成结论。

工程上应限制最大步数和总 token，记录每轮 Thought、Action、Observation 与耗时，并在最终答案中保留引用。对于发邮件、写数据库等副作用工具，Action 进入执行器前还应有用户确认或策略审批。

## 它和什么容易混淆

ReAct 与 Chain-of-Thought 都涉及推理，但 Chain-of-Thought 通常在回答前生成内部或显式思路，不要求与外部环境交互；ReAct 的核心是“思考—行动—观察”的闭环。它也不同于 MCP：MCP 规定 Host、Client、Server 如何发现和调用能力，ReAct 规定模型如何在任务轨迹中决定下一步；一个 ReAct Agent 可以通过 MCP 调用工具。

## 局限与实践建议

模型可能产生冗余思考、错误工具参数或无限循环；外部网页还可能包含提示注入，诱导 Agent 越权。不要把 Thought 文本当作安全审计的唯一依据，应在执行器层做 schema 校验、权限隔离、域名白名单、超时和幂等控制。评估时分开记录任务成功率、工具调用准确率、平均步数、失败恢复率、成本和尾延迟。对高风险动作，采用“只读探索—用户确认—最小写入”的阶段式策略。

## 为什么现在值得关注

ReAct 论文发表于 2022-10-07。如今 Agent 从单轮问答走向多工具工作流，交替轨迹仍是理解规划、工具调用和错误恢复的基础抽象。具体框架可能隐藏或改写思考内容，但“基于观察再决策”的原则依然适用。
