# 今日知识点：Query2doc：用伪文档扩展查询，改善 RAG 的召回

> 一句话：让模型先写一段“可能相关的文档”，再用它扩展检索词，缓解短问题和真实资料的表述错位。

**分类**：检索与知识　**难度**：3　**资料截至**：2026-09-05

## 它解决什么问题

RAG 的第一步常常决定了回答上限：用户只问一句“某产品能否离线使用”，知识库里的权威资料却写着“本地部署”“网络断连”“缓存策略”。即使两者表达同一意图，关键词或向量表示仍可能不够接近，导致正确资料没有进入后续重排和生成环节。

传统查询扩展会加同义词或伪相关反馈词，但面对新产品、专业术语和自然语言问题时，扩展词很难覆盖文档的语气、实体和关系。Query2doc 提出的思路是：不要只补几个词，而是让大语言模型生成一篇简短的“伪文档”，把它与原问题一起作为检索查询。

## 工作机制

流程分三步：

1. 输入用户问题 q，并要求 LLM 写出一段看起来会回答该问题的文档 d′。它不要求 d′ 必然为真，也不把它直接交给用户。
2. 将 q 和 d′ 拼接或组合为扩展查询 q′。
3. 用 q′ 到真实语料库检索；后续 RAG 只以检索到的真实文档为证据生成回答。

直观上，伪文档充当“语言桥梁”。它会把短问句展开成更接近知识库写作方式的实体、属性和因果描述，使 BM25 等词法检索器能匹配更多术语，也可能给稠密检索器补充语义线索。重要的是，伪文档是**查询侧的假设**，不是事实来源；它的价值在于改变召回候选，而不是替代检索。

## 一个具体例子

问题：`怎样降低长对话的 LLM 成本？`

伪文档可能出现“上下文窗口、历史摘要、KV cache、令牌预算、检索式记忆”等表达。检索查询变成“原问题 + 这段伪文档”。真实文档因此更可能包含“conversation summarization”或“context compression”等原本不会出现在中文短问句中的术语。

实现时可以把生成长度限制在一小段，并对同一问题采样 1–3 个候选后合并结果；然后用重排序器筛掉仅与伪文档表面相似、却没有回答原问题的内容。最终回答仍必须逐条引用真实检索结果。

## 它和什么容易混淆

Query2doc 与“先让 LLM 直接回答问题”不同：直接回答会把模型自己的内容当证据，容易出现幻觉；Query2doc 只把生成文本用于找资料。它也不同于 HyDE（Hypothetical Document Embeddings）：HyDE 典型做法是将假设文档编码为稠密向量做检索，而 Query2doc 的原始思路是将伪文档作为文本扩展查询，因此可与稀疏检索或其他检索器组合。两者都在利用“假设文档”，但表示和接入点不同。

## 局限与实践建议

伪文档可能带入错误实体或偏见，把检索拉向错误主题；在专有名词、日期、版本或合规问答中尤其要谨慎。它还增加一次 LLM 调用，带来延迟与成本。实践上应保留原问题，限制扩展长度，记录生成版本，并对“只用原查询”和“原查询 + 伪文档”分别测量 Recall@k、最终答案的引用正确性和延迟。高风险场景不要让伪文档绕过文档权限，也不要把它当成可引用证据。

## 为什么现在值得关注

Query2doc 论文发布于 2023-03-14。随着 RAG 被用于产品文档、内部知识库和多语言问答，查询侧改写往往比盲目增加向量库规模更直接地影响“能否先找到正确资料”。它适合被视为可评测的检索策略，而不是默认必须开启的生成步骤。
