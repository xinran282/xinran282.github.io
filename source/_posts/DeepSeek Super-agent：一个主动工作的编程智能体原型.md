# DeepSeek Super-agent：一个主动工作的编程智能体原型

DeepSeek 的“Super-agent”更准确地说是 [dsh-superagent 研究原型](https://github.com/deepseek-ai/dsh-superagent-prototype)，不是已经面向所有人交付的正式产品。它试着把编程智能体从“等人打开对话框、交代一次任务”推进到团队的日常协作里：接收 GitHub（可选飞书）中的请求，判断能不能接、该不该接，再在独立会话和目录中做事，把结果带回原来的讨论。仓库 README 明确提醒：公开代码仅供研究参考，可能有错误，与内部实现和设计文章所述系统也并不完全相同。

## 它到底替人做什么

设想一条 GitHub 讨论里有人请智能体修复问题。系统先识别消息来自哪个会话、发起人有没有权限，以及是否已有相关工作；确认接单后建立工作项，交给执行会话处理。执行者可以读代码、修改文件、运行命令和测试，最后报告结果，必要时提交可供审查的 Pull Request。遇到设计决定或权限边界，就停下来问人，而不是假装已经完成。[项目 README](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/README.md)描述了这条基本路径。

这里的“主动”不等于随意巡查仓库、自动开一堆 PR。项目的[设计原则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/000-philosophy.md)规定：有人明确提出请求，或者团队事先写下允许主动工作的规则，才能行动；未经请求的工作先以只记录拟执行动作的方式观察。它也要求智能体在确认接单后尽量安静，只有结果可用、需要人决策或任务失败时才再次打扰团队。

## 为什么要有路由和执行两层

一个持续接收消息的智能体，不能把每条评论都当作新任务。这个原型把外部事件整理成 Trigger，再按会话和已有工作项判断：忽略、附到现有任务、停止，还是接受为新任务。主会话负责这类分流与协调；具体编码落在各自的执行会话。项目的[架构文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md)把事件接入、评估、工作项、执行和回复拆成不同部件，并用状态与记录串起它们。

可以把它理解成一个值班的协调者和若干按任务工作的执行者。协调者不该被一次漫长的测试阻塞；执行者也不该拿着一条评论就越过授权边界对外发言。这样的分工是对长期运行、多个请求同时到来这一问题的工程回答，不是“模型自己变得无所不能”的证据。

## 与 DeepSeek Harness 是什么关系

[DeepSeek Harness](https://www.deepseek.com/en/harness/)是公开预览中的开源智能体运行环境，支持桌面和 Web 使用，并通过插件扩展能力。dsh-superagent 则是装在这套环境里的一个面向单个 GitHub 仓库的编程协作原型。两者不能混称：前者是运行平台，后者是具体的研究项目；后者也并非 DeepSeek 官方已经推出的正式 Super-agent 产品。

如果想试用，仓库提供 [SETUP.md](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/SETUP.md)，但部署涉及账号、来源、权限与环境配置。更稳妥的顺序是先在小范围授权名单和低风险仓库里观察它会接什么任务、会发什么消息，再逐步开放主动执行。项目自己也建议从窄范围开始，并由操作者对智能体以团队账号发出的内容负责。

## 真正值得关注的地方

这个原型有意思的地方，不是给一次性代码生成换了个更响亮的名字，而是把“何时接活、谁有权提出请求、何时需要人介入、怎样回到原会话”作为系统的一部分。对团队来说，节省注意力可能比增加任务数量更重要。

但这仍是设计方向和研究代码。公开资料能说明它的意图与实现轮廓，不能证明它在任意仓库都可靠，更不能据此推断已经具备无人监管的生产级自治能力。读它时，先看授权、工作项状态和回复规则，再看智能体能写多少代码，可能更接近项目真正想解决的问题。
