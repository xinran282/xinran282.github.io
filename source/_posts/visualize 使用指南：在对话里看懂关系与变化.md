遇到需要比较方案、观察变量变化或理解空间关系的问题，可以让 AI 把解释变成一张图。`visualize` 是面向这类需求的技能：在支持它的对话环境中，生成图表、交互演示或界面草图，帮助读者看清关系，也能亲手调整条件。

使用时，先说清楚自己要判断什么，再决定是否需要交互。一个能回答问题的小图，通常比塞满指标的面板更有用。

## 什么问题值得画出来

文字适合表达定义、前提和理由。涉及多项比较，或一个条件改变后多个结果跟着变化时，图形往往更容易读。

例如，比较两个订阅方案，可以画出费用随使用量变化的曲线；理解排队现象，可以调整到达速度，观察队列如何积累。前者帮助找到价格交点，后者帮助观察系统随时间发生的变化。

界面讨论也适合先做小范围演示。假设团队正在争论筛选按钮放在哪里，可以生成包含真实筛选行为的局部草图，检查操作顺序和反馈是否清楚。此时需要验证的是一个具体设计决定，页面范围可以很小。

只问一个数值，直接回答就够了。只有几行的对照信息，用普通表格通常更省事。

## 静态图与交互图怎么选

选择形式时，可以先看：读者是否需要改变条件，才能理解答案？

| 要解决的问题 | 合适的形式 | 原因 |
| --- | --- | --- |
| 核对几个方案的配置 | Markdown 表格 | 便于逐项查找 |
| 理解审批流程或模块依赖 | Mermaid 结构图 | 节点和连线已经能表达关系 |
| 查看一段时间内的数据趋势 | 折线图 | 时间与数值可以直接对应 |
| 比较不同参数下的结果 | 带输入控件的交互图 | 可以在同一张图里观察变化 |
| 讨论弹窗或移动端操作 | 可交互的界面草图 | 可以检查操作及反馈 |

不必为每张图加滑块。如果读者只需要看一次结论，直接标出数值更清楚。只有当参数调整有助于理解问题时，控件才有必要。

## 提示词要给出目标和规则

“画一个漂亮的图”留下了太多空白。更有效的请求会说明比较对象、计算规则，以及读者需要做出的判断。

下面是一条可用于费用比较的示例提示词，价格均为假设：

> 用 visualize 比较两个假设的 API 套餐。A 套餐每月固定 20 元，每调用一次再收 0.02 元；B 套餐没有固定费用，每次调用收 0.05 元。横轴是每月调用次数，范围为 0 到 2000 次，纵轴是总费用，单位为元。标出两条费用曲线的交点，再加一个调用次数滑块，让我查看所选用量下两个套餐各要多少钱。不要加入其他费用。

这个请求已经明确了问题边界。计算规则是：A 的总费用为 `20 + 0.02 × 调用次数`，B 为 `0.05 × 调用次数`。两者约在每月 667 次调用时相等；如果调用次数只能取整数，666 次时 B 更便宜，667 次时 A 更便宜。

图形应当与这笔计算一致。移动滑块后，所选位置和费用读数也应一起更新。

如果要演示业务数据，还需要提供数据来源、时间范围和单位。缺失值应该标明，示例值应该注明为假设数据。画得再完整，也不能补足没有依据的数据。

## 交付后，先检查能否读懂

看一张图，可以先从几个具体问题入手：坐标轴有没有单位？颜色是否对应明确的类别？重要数值能不能直接找到？手机宽度下，标签会不会挤在一起？

交互图还要检查操作与结果的对应关系。切换某个系列后，曲线和相关读数应保持一致；修改参数后，画面应使用新的输入重新计算。按钮有响应，只能说明按钮能点击，还需要确认它改变了正确的内容。

以费用比较为例，分别查看零调用、交点附近和最大调用量，便能发现不少问题。零调用时，A 应为 20 元，B 应为 0 元；2000 次时，A 为 60 元，B 为 100 元。这些容易手算的位置适合作为核对点。

## 对话演示与分享文章如何配合

`visualize` 适合在对话中探索问题。需要读者拖动参数、切换方案时，可以保留交互演示；需要发布到博客或发送给别人阅读时，还要考虑对方打开内容的环境。

微信公众号文章等发布渠道通常无法运行任意交互脚本。适合的做法是选取有代表性的状态，配上静态图和文字解释。需要完整交互时，再单独准备可在浏览器中打开的页面。

使用 `share-page` 整理文章时，可以把问题背景、图中结论和成立条件写进正文。关键结论应当在不操作图形的情况下也能读懂。独立网页则需要检查脚本、资源路径，以及是否使用了仅在原对话环境中可用的能力。

## 从一个可核对的问题开始

初次使用，可以选一个规则清楚、结果容易手算的问题，例如上面的套餐比较。先确认图画对了，再调整展示方式。

等问题变复杂，再逐步加入必要的数据和操作。每加一个控件，都应能说清楚：它让读者看到了什么变化，或者帮助读者做出了什么判断。
