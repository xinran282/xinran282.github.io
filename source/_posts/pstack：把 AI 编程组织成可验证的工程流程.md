# pstack：把 AI 编程组织成可验证的工程流程

AI 很快写出一个补丁，测试也绿了，你却仍然拿不准：它修复了原来的问题吗？有没有为了绕开报错，悄悄改变接口语义？到了第二个任务，它还会遵守刚才约定的检查步骤吗？

[pstack](https://github.com/backnotprop/pstack) 尝试把这些要求写成智能体可以反复执行的工程流程：先理解系统，再选择设计，完成修改后拿出验证证据。它把技能、任务剧本和工程原则组合起来，让编码智能体在不同任务中采用相应的工作方法。

对使用者来说，值得关注的是它如何界定“完成”：原始问题能够复现，修改后的行为能被检查，结论有可重跑的证据。本文根据项目文档和代表性技能源码解释这套方法，未进行安装实测。

## 先区分独立镜像与上游项目

用户提供的 `backnotprop/pstack` 是一个独立镜像。仓库 README 明确说明，上游来自 Poteto 的 [cursor/plugins/pstack](https://github.com/cursor/plugins/tree/main/pstack)，镜像保留上游内容，并加入面向不同宿主工具的改写和社区修复。

这一区分影响安装和使用：

| 来源 | 安装入口与用途 |
| --- | --- |
| `backnotprop/pstack` 独立镜像 | 通过 `skills` CLI 选择技能，安装到相应智能体工具 |
| `cursor/plugins` 上游插件 | 使用 Cursor 或 Claude Code 的插件机制加载 pstack |

镜像说明中提到，它改写了部分 Cursor 专属指令，使技能可以在其他宿主中使用。不过，README 中保留的上游使用指南仍有 Cursor 名称和路径，读到示例时需要确认其适用环境。

pstack 的主体是 `skills/<name>/SKILL.md` 形式的 Agent Skills，还包括参考资料、脚本和子智能体定义。它的运行能力依赖宿主提供的文件访问、命令执行、子智能体和其他工具。复制技能文本，不会自动获得新的模型访问权或云端运行环境。

## 技能、任务剧本和原则怎样配合

理解 pstack，可以先看三个层次。

技能处理一种具体工作。例如，`how` 用于理解系统怎样运行，`architect` 先设计接口与模块结构，`interrogate` 用对抗式审查寻找可证明的问题。

任务剧本把技能组织成一个完整流程。修 bug、开发功能、性能调查和准备合并 PR，需要的步骤不同，项目分别为它们提供 playbook。

工程原则约束执行中的选择。例如，优先解决根因、用类型表达约束、验证实际行为、把大任务拆成可检查的小单元。这些原则有对应的技能文件，供具体流程引用。

主要入口是 `poteto-mode`。按照源码，它读取任务后匹配 playbook，把步骤放入待办列表，再在需要时调用其他技能。可以把调用关系概括为：

```text
目标与验收条件
      ↓
poteto-mode 匹配任务剧本
      ↓
理解系统 → 设计或调查 → 实现 → 验证 → 整理交付
              各阶段调用相应技能
```

这减少了每次重复编写长提示词的需要。使用者仍要说明目标，尤其是怎样判断结果正确。

## 从一个重复导出的 bug 看流程

假设一个导出任务在重试时偶尔写入重复行。一个可检查的任务描述是：

```text
/poteto-mode 导出任务在重试发生于执行中途时会写入重复行。
先复现，再查根因并修复。验证同一批数据在该重试条件下只输出一次，
给出修复前后的命令与结果。
```

这是使用示例，并非本文已经运行的测试。

项目的 [Bug fix 剧本](https://github.com/backnotprop/pstack/blob/4ae1636abe217c7215774bf6b2265916a5c5f648/skills/poteto-mode/playbooks/bug-fix.md)要求先在相应运行界面复现问题，再用运行证据逐步排除假设，确认错误发生的机制后才规划修复。修改完成后，要回到相同界面验证原来的触发条件。

如果有便宜、明确的本地测试路径，它还会使用 TDD 的失败测试先行节奏。对昂贵、依赖复杂或路径不明确的情况，剧本允许跳过这一步，并不要求所有缺陷都机械地套用同一种测试方式。

对这个导出问题，检查代码里有没有去重逻辑，只能说明实现中存在某种处理。真正需要验证的是：在原来会触发重复写入的重试时序下，输出是否仍然只有一份。项目反复要求验证“相同界面”，就是为了避免用另一个较容易通过的检查替代原始问题。

## 多智能体分别承担什么角色

pstack 使用多智能体进行探索、实现与审查，但不同技能的分工并不相同。

| 技能 | 主要工作 |
| --- | --- |
| `arena` | 对同一问题尝试不同方案，再比较和综合 |
| `swarm` | 覆盖不同任务切片或检查范围，汇总结果 |
| `architect` | 先理解现有系统，通过 arena 比较设计草图，再进入实现 |
| `interrogate` | 尝试打破修改或设计，保留有运行证据的发现 |

`architect` 的源码要求至少比较两种结构上不同的候选设计，并考察接口是否能把复杂性藏在较小的公共表面之后。它默认在综合设计后继续实现；只有调用者明确要求检查点，才停下来等待确认。

`interrogate` 的要求更适合说明 pstack 对证据的态度。审查者要给出真实代码上的测试、复现脚本或命令输出；汇总者还要重跑并确认发现确实违背任务意图。它也接受“没有经过验证的发现”这一结果。该技能负责报告问题，不直接应用修复。

这些安排可以增加方案的差异、分开实现与评判，但不会自动消除错误。多个模型可能共享同一个错误前提，运行检查也可能覆盖不足。是否可信，最终仍取决于执行过什么检查，以及检查与目标的关系。

## 验证要产出可以检查的东西

pstack 的验证指南建议，在任务开始时就说明完成条件。不同修改需要不同证据：

- CLI 增加 JSON 输出，应运行真实命令，检查 JSON 能否解析，并比较原文本输出。
- UI 修改，应在运行中的应用里走一遍相关流程；需要视觉一致时，再比较基准截图。
- 性能优化，应保存前后测量和 profiling 结果，并确认测到的是目标工作。
- 存储修改，应读回写入后的值，检查实际状态。

项目还提供 `create-verification-skill`，为具体代码库整理可重复的验证方法；已有方法发生漂移时，由相应的维护技能更新。

对并发、重试、状态机等较难覆盖的问题，它提供形式化验证相关技能。这里需要保留范围：验证的是所建模型或验证工具所覆盖的性质，模型还必须与代码对应。一次检查通过，不能据此声称整个产品没有缺陷。

实际采用时，可以先要求智能体交付一条你能重跑的命令，以及预期输出。等这条路径可靠后，再扩大自动化范围。

## 安装时，先选你需要的流程

独立镜像给出的安装命令是：

```bash
npx skills add backnotprop/pstack
```

根据 README，CLI 会展示技能列表，让使用者选择要安装的技能和目标智能体。本文仅列出官方入口，没有执行安装。

选择时要检查技能之间的依赖。例如，README 列出 `teach` 需要 `how` 和 `why`，`technical-writing` 需要 `unslop`，`architect` 需要 `arena` 和 `how`。`poteto-mode` 则依赖原则技能及大量其他技能。

依赖表也要与技能正文一起看：当前镜像 README 把 `interrogate` 列为可单独工作的技能，但它的源码明确要求复用 `arena` 的若干阶段。按源码执行这套审查流程时，需要同时具备 arena。这也说明，安装成功与工作流完整是两项检查。

如果选择 Claude Code 的上游插件路径，README 给出的命令是：

```text
/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins
```

通过这条路径安装后，命令带有插件前缀，例如 `/pstack:setup-pstack` 和 `/pstack:poteto-mode`。不要把插件命令前缀套用到所有独立技能安装方式上。

## 跨工具适配与运行成本

镜像提供了宿主适配说明。以 Claude Code 为例，文档映射了子智能体类型、文件路径和模型配置；对于不支持的模型名称，需要按适配规则处理。Cursor 的自动化、云端智能体或其他专属能力，也不会因为安装了技能就出现在另一个工具里。

项目 README 还列出未随 pstack 捆绑的能力，包括 `cursor-team-kit` 中的 `deslop`、`control-cli` 和 `control-ui`。完整流程是否可运行，取决于宿主是否提供对应工具或可用替代方式。

多智能体、候选设计和额外审查都会消耗 token 与时间。设置指南允许调整推理预算、角色模型和评审面板规模，并建议把 `poteto-mode` 留给需要严谨处理的工作。一次明显的文案修改，通常不需要完整设计评审流程。

对第一次试用，我更建议选一个规模可控、已有复现条件的真实缺陷：记录原来的耗时，观察新流程有没有减少重复调查，最终证据是否更容易复核。这样才能判断额外步骤是否值得。

## 值得带回自己项目的做法

pstack 提供了一套比较明确的协作约定：任务要有可检查的结束条件，设计要显露取舍，修复要回到原来的触发条件，交付要带上证据。

即使只采用其中一部分，也可以先把“完成”写得具体一点。例如，将“优化导出逻辑”改为“在固定样本上重放执行中途重试，输出行数与唯一键集合都保持正确，并保存修复前后的结果”。智能体得到明确的检查路径，你也更容易判断它交付了什么。

如果同一类错误反复出现，再把规则写进类型、lint、测试或可重跑的脚本。pstack 的 `correct` 和工程原则都鼓励这种处理：让后续工作有实际约束可依，而不是继续累积提醒。
