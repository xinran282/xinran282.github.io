# ReAct 介绍：让模型边想边做

普通的问答模型只需要生成一段文字。遇到需要查资料、调用接口或执行命令的问题，它就需要先判断下一步该做什么，执行动作，再根据结果继续处理。ReAct 解决的正是这类任务：让模型在推理和行动之间交替进行，直到得到足够的信息再回答用户。

ReAct 不是一个模型名称，也不是某个特定的 Agent 产品。它更像一种组织模型行为的工作流模式。模型负责决定下一步，外部工具负责提供事实或执行动作，系统再把工具结果交回模型。

## ReAct 是什么

ReAct 这个名字来自 Reasoning and Acting，也就是推理与行动。它的基本循环可以写成：

```text
用户问题
  -> 推理：下一步需要什么信息或动作？
  -> 行动：调用搜索、数据库、代码执行器等工具
  -> 观察：读取工具返回结果
  -> 推理：结果是否足够？下一步做什么？
  -> 最终回答
```

这个循环和只让模型“一次性想完再回答”有一个区别：模型可以根据真实的外部结果调整后续动作。工具返回错误时，它可以修正参数；查到的信息不够时，它可以继续检索；条件已经满足时，它应该停止调用工具。

## 一个最小例子

假设用户问：“帮我查一下订单状态，并告诉我预计什么时候送达。”系统可以给模型提供 `get_order` 工具。

一次典型的流程可能是：

```text
问题：查询订单 A1001 的状态和预计送达时间

决策：需要先调用订单查询工具
行动：get_order({"order_id": "A1001"})
观察：状态为运输中，预计明天送达

决策：工具已经返回状态和时间，可以直接回答
最终回答：订单 A1001 正在运输中，预计明天送达。
```

这里的重点不是让模型写出一段漂亮的“思考作文”，而是让每个动作都建立在上一轮得到的结果上。

## ReAct 的核心组成

### 推理

推理负责判断当前信息是否足够、该选哪个工具，以及工具返回后如何继续。它可以是对用户可见的简短理由，也可以只保留结构化的决策结果。

生产系统不应默认把模型的完整内部思考直接展示给用户。对外展示“正在查询订单”或“根据查询结果整理答案”通常已经足够；系统内部可以记录必要的决策摘要、工具名称和参数，方便审计和排查。

### 行动

行动就是实际执行的工具调用。工具可以是：

- 搜索接口或知识库检索。
- 数据库查询。
- 文件读取和代码执行。
- 订单、支付或业务系统 API。
- 发送消息、创建任务等外部操作。

模型只应该从系统明确提供的工具中选择，不能把一段自然语言当成已经执行成功的动作。

### 观察

观察是工具真实返回的结果，包括成功数据、错误信息、权限拒绝和超时。它必须由执行系统注入上下文，不能让模型自己想象一个工具结果。

如果工具返回“订单不存在”，模型就应该据此处理，而不是继续编造订单状态。工具结果和模型生成内容之间要有清楚的边界。

## ReAct 的提示词结构

传统 ReAct 示例常用 `Thought`、`Action`、`Observation` 这样的文本标记：

```text
Question: 用户的问题
Thought: 判断下一步需要什么
Action: 要调用的工具
Action Input: 工具参数
Observation: 工具真实返回的结果
Thought: 根据结果判断是否继续
Final Answer: 给用户的最终回答
```

这是一种容易理解的教学格式，但生产系统未必需要把所有内容拼成纯文本。更稳妥的实现可以让模型输出结构化数据：

```json
{
  "type": "tool_call",
  "tool": "get_order",
  "arguments": {
    "order_id": "A1001"
  },
  "reason": "需要查询订单的实时状态"
}
```

执行器验证工具名和参数后再执行，并把结果作为新的消息返回给模型。这样比从自由文本中用正则表达式截取工具名和参数更可靠。

## ReAct 和其他方法有什么区别

### 和普通 Prompt 的区别

普通 Prompt 通常要求模型直接生成答案。ReAct 增加了一个可以暂停生成、调用外部能力、再继续判断的循环。

如果问题只需要模型已有知识，ReAct 反而可能增加延迟和成本。它适合需要外部信息或实际操作的任务，不是所有请求都要经过 Agent 循环。

### 和思维链的区别

思维链主要关注如何分解问题和逐步推理，通常不涉及外部工具。ReAct 在推理过程中加入了行动和观察，因此可以处理实时数据和环境反馈。

两者也可以结合：模型先分析问题，再决定是否调用工具；但“需要调用工具”不代表必须公开完整思维过程。

### 和函数调用的区别

函数调用是一种模型与工具之间的接口能力，规定模型如何表达工具名称和参数。ReAct 是更高层的工作流，规定模型什么时候行动、如何读取结果、是否继续循环。

一个 ReAct Agent 可以使用函数调用来执行每一步行动。二者不是互相替代的关系。

### 和 Plan-and-Execute 的区别

Plan-and-Execute 通常先生成一份相对完整的计划，再按计划执行；ReAct 则更强调每一步根据最新观察动态调整。

任务路径比较稳定时，预先规划有助于控制节奏；环境变化多、工具结果不确定时，ReAct 更灵活。实际系统也可以先生成粗略计划，再在每个步骤中采用 ReAct 循环。

## 一个完整的执行循环

一个最小执行器通常需要完成这些工作：

1. 把用户问题、历史上下文和可用工具说明交给模型。
2. 判断模型返回的是最终答案还是工具调用。
3. 如果是工具调用，校验工具名称、参数类型和权限。
4. 执行工具，并记录调用结果、耗时和错误。
5. 把结果追加到上下文，再次请求模型。
6. 达到终止条件后返回最终答案。

伪代码可以写成：

```text
for step in 1..max_steps:
    response = model(messages, tools)

    if response.type == "final":
        return response.content

    if response.type != "tool_call":
        return handle_invalid_response(response)

    call = validate_tool_call(response)
    result = execute_tool(call)
    messages.append(response)
    messages.append(tool_result(result))

return stop_with_limit_message()
```

真正的系统还需要处理超时、重试、取消、并发、幂等和权限，但这段循环已经表达了 ReAct 的核心。

## 工程上必须加的限制

### 设置最大步数

没有步数上限时，模型可能在工具错误、信息不足或目标漂移后不断调用工具。`max_steps` 是最基本的保护措施。

达到上限后，系统应该明确告诉用户任务没有完成，或者转交人工，而不是假装已经得出结论。

### 控制工具权限

查询天气和删除数据不应该拥有相同的执行权限。工具应按读写、影响范围和风险等级进行区分。

高风险写操作可以要求用户确认，或者先生成预览，再执行真正的变更。

### 校验参数和返回值

模型生成的参数即使符合 JSON 格式，也不代表业务上有效。执行前还应检查 ID 是否属于当前用户、数值是否在范围内、路径是否允许访问。

工具结果也需要限制大小和格式，避免异常响应撑爆上下文或把不可信内容直接当成系统指令。

### 处理提示词注入

搜索结果、网页内容和文件内容都可能包含“忽略之前指令”之类的文本。外部数据应该作为不可信观察结果处理，不能自动获得更高优先级。

执行器要把系统指令、用户输入、工具说明和外部数据分开标记，并在高风险动作前再次检查权限和用户意图。

### 记录完整轨迹

至少记录任务 ID、步骤编号、模型响应、工具名、经过脱敏的参数、结果摘要、耗时和错误。日志不只是为了调试，也用于评估 Agent 是否经常选错工具、重复调用或在失败后继续编造。

## ReAct 的常见问题

### 工具调用太多

模型可能为了确认一个简单事实连续查询多个来源。可以通过工具描述、调用预算、重复调用检测和缓存来限制这类行为。

### 观察结果太长

把整页网页或完整日志原样塞回上下文，会让模型更难找到关键内容。执行器可以先做截断、字段筛选或摘要，同时保留原始结果供审计。

### 工具失败后仍然给出肯定答案

这是比“调用失败”更危险的问题。工具失败应成为明确的状态，最终回答必须区分“已经确认”和“推测”。

### 只用最终答案评测

只看最终文字，很难判断 Agent 是否选对工具、是否正确使用返回结果。评测时还应检查工具选择、参数、调用次数、失败处理和最终结论之间是否一致。

## 什么时候适合使用 ReAct

适合使用 ReAct 的任务通常有这些特征：

- 需要访问模型之外的实时信息。
- 需要根据中间结果决定下一步。
- 工具可能成功、失败或返回不同分支。
- 任务需要多个步骤才能完成。

如果任务只是改写一段文字、翻译短句或回答稳定的基础概念，直接调用模型通常更简单。多一个 Agent 循环，就多一层延迟、成本和故障面。

## 最后

ReAct 的核心不是让模型“多想几步”，而是让推理、工具行动和真实观察形成可控的反馈循环。要把它用于生产，关键在执行器：校验工具调用，限制步数和权限，区分真实结果与模型生成内容，并为每一步留下可审计的轨迹。

当任务确实需要外部信息和动态决策时，ReAct 能把一个只会生成文字的模型，接入到可以查询、判断和执行的工作流中。
