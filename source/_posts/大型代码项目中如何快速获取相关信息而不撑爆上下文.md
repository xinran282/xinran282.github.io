# 大型代码项目中，如何快速获取相关信息而不撑爆上下文

面对一个庞大的代码项目，最慢的做法往往是从头读代码。文件越看越多，真正影响修改的几条调用链反而被淹没。把整个仓库塞给 AI 也有同样的问题：上下文变长了，注意力却变散了。

更有效的方法是建立一个逐层收窄的信息漏斗。先确定项目边界，再定位变更入口，随后只沿着真实依赖向外扩展。每读一份材料，都应该回答一个具体问题；回答不了，就暂时不要读。

## 先区分“可能相关”和“已经证实相关”

大型项目里，文件名相似、目录相邻，不代表它们会影响同一个行为。相关性需要证据。

证据通常来自这些地方：

- 目标符号的定义与引用
- 请求、事件或数据的调用链
- 配置、路由和依赖注入关系
- 覆盖该行为的测试
- 最近修改过同一功能的提交

搜索结果只是候选集合。只有进入调用链、数据流或测试范围的内容，才应进入当前工作上下文。

## 第一层：用项目地图确定边界

开始时不要读实现细节，先用几分钟回答四个问题：

1. 项目由哪些模块、服务或包组成？
2. 构建、测试和启动入口在哪里？
3. 当前需求属于哪个模块？
4. 这个模块与外部系统通过什么接口通信？

优先查看根目录文件、模块清单、构建配置和项目级说明，例如 `README.md`、`AGENTS.md`、`package.json`、工作区配置或服务部署文件。目录太多时，先列两层，不要直接递归输出全部文件。

```powershell
rg --files -g "README*" -g "AGENTS.md" -g "package.json" -g "*.csproj" -g "pom.xml"
```

这一层的产物不是完整架构文档，而是一张很小的地图：目标模块、相邻模块、测试位置和主要入口。

## 第二层：从变更入口开始搜索

需求通常会给出至少一个入口：错误信息、接口路径、类名、配置项、页面文案、数据库字段或日志关键字。先搜索最独特的字符串。

```powershell
rg -n "PaymentTimeout|/api/orders|order_expired" src tests
```

如果结果太多，增加目录、文件类型或上下文限制；如果结果为空，再逐步放宽关键词。不要一开始就搜索“service”“manager”之类的通用词。

找到入口后，先读命中位置附近几十行，判断它是定义、调用、测试还是生成文件。通常没有必要立刻打开整个文件。

## 第三层：沿调用链和数据流扩展

入口文件只能说明“在哪里出现”，不能说明“修改会影响什么”。下一步要追踪行为链。

对于后端请求，可以按这个顺序追踪：

```text
路由或消息入口 -> 参数校验 -> 业务服务 -> 数据访问或外部调用 -> 返回值与副作用
```

对于前端交互，则常见为：

```text
用户操作 -> 组件事件 -> 状态更新 -> API 请求 -> 渲染结果
```

使用语言服务器的“转到定义”“查找引用”和调用层级，比纯文本搜索更准确。文本搜索适合找到入口，符号工具适合确认引用关系。两者结合，通常只需打开少量文件。

每向外走一层，都问一次：这段代码会改变目标行为吗？如果只是类型声明、通用工具或无关调用，就记录名称，不把完整内容带入上下文。

## 第四层：用测试确认行为边界

测试往往比实现更快地说明系统承诺了什么。找到目标类、接口或错误码对应的测试，重点看：

- 正常路径和失败路径
- 边界输入
- 对外部依赖的模拟方式
- 断言中的业务结果和副作用

```powershell
rg -n "PaymentService|PaymentTimeout" tests
```

如果没有直接测试，查找同一模块中相似功能的测试。它能告诉你仓库习惯使用什么测试层级、夹具和命名方式。

测试还有一个作用：帮助划定修改范围。如果现有测试表明某个行为属于公共契约，那么看似局部的改动也可能影响多个调用方。

## 第五层：让 Git 解释“为什么这样写”

代码只能展示当前状态，提交历史常常保存设计原因。遇到奇怪的分支、重复逻辑或不敢删除的兼容代码时，查对应行和相关提交。

```powershell
git log --oneline -- path/to/file
git blame -L 80,120 path/to/file
git show <commit>
```

不要通读几年的提交记录。先用文件、符号或需求关键词过滤，只查看改变过当前行为的提交。提交说明、关联问题和当时新增的测试，往往能解释代码里的隐含约束。

## 如何控制 AI 的上下文

给 AI 的材料应当是“最小充分证据”，而不是搜索结果的全集。一次任务通常只需要以下内容：

| 信息 | 建议形式 |
|---|---|
| 项目边界 | 几行目录摘要和构建方式 |
| 当前目标 | 一句话说明预期行为与限制 |
| 核心实现 | 目标函数及直接依赖的相关片段 |
| 行为证据 | 相关测试、错误日志或接口契约 |
| 历史约束 | 一两条真正相关的提交结论 |
| 未确认事项 | 简短列出假设和待查问题 |

长文件不要整份粘贴。先给出符号位置和局部片段，只有当局部内容引用了未知状态时，再补充定义。日志也只保留错误前后的关键区间，重复堆栈和无关请求可以删掉。

让 AI 先输出“已知、推断、未知”也很有用。这样能及时发现它把猜测当成事实，避免在错误前提上继续消耗上下文。

## 用外部笔记保存结论，不依赖对话记忆

长任务会经历多轮搜索、修改和验证。把关键结论写入一个简短的任务笔记，比反复把旧对话带回上下文更稳定。

笔记可以只包含这些内容：

```markdown
## 目标
修改什么行为，不改变什么行为。

## 已确认
- 入口：...
- 调用链：...
- 相关测试：...
- 兼容约束：...

## 待确认
- ...

## 验证命令
- ...
```

每得到新证据就更新结论，淘汰已经被推翻的假设。下一轮工作只需要读取这份摘要和当前代码，而不是重新加载全部探索过程。

## 一套可以直接执行的流程

面对新增或修改需求，可以按以下顺序推进：

1. 用两三分钟查看仓库结构和项目说明，确定目标模块。
2. 从需求里的独特关键词搜索入口，只读命中附近内容。
3. 使用定义、引用和调用层级追踪一条完整行为链。
4. 找到相关测试，确认公共行为、边界条件和仓库惯例。
5. 对不理解的设计查 Git 历史，不做无目的考古。
6. 写下最小任务摘要，明确已知、未知和修改边界。
7. 制定变更方案，只打开方案涉及的文件。
8. 修改后运行最小相关测试，再根据影响范围扩大验证。

这套流程不是固定要求。如果第一轮测试暴露出跨模块影响，就回到调用链继续扩展；如果证据已经足够，就停止搜索，进入实现。

## 判断上下文是否已经足够

当你能清楚回答下面几个问题时，通常可以开始修改：

- 行为从哪里进入？
- 核心状态在哪里改变？
- 谁依赖这个结果？
- 哪些测试定义了现有行为？
- 这次明确不改什么？
- 修改后用什么命令验证？

如果其中某一项答不上来，就补查那一项，而不是继续泛读仓库。

大型项目中的效率，不取决于一次能读多少代码，而取决于能否快速排除无关信息。先广后窄，沿证据扩展，及时把结论压缩到外部笔记里。这样既能保持全局判断，也不会让上下文被项目体量拖垮。
