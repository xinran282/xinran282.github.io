# Multica：把多个 AI 编码智能体放进同一块任务看板

同时使用 Codex、Claude Code、Cursor Agent 是什么体验？开始时像多了几名帮手，过一阵往往变成一排终端窗口：任务在哪个窗口里，谁改过哪些文件，哪个智能体卡住了，都要人自己记。

Multica 想处理的正是这一层问题。

它不是新的大模型，也不替代编码智能体。它是一个面向人和 AI 智能体的协作工作区：任务放进看板，分配给某个智能体，由智能体在指定机器上执行；进度、命令、错误、Token 用量和代码变更继续挂在同一个任务下面，完成后进入人工审核。

一句话概括：**Codex、Claude Code 负责干活，Multica 负责派活、留痕和验收。**

## 它解决什么问题

单独使用一个编码智能体时，聊天记录和终端通常还能应付。智能体数量增加后，管理成本开始冒出来：

- 每个智能体待在自己的会话里，任务状态分散；
- 换会话或换工具时，需要重新交代项目背景；
- 人要反复查看执行进度，判断它是在工作还是已经卡住；
- 一次运行用了哪些工具、执行了什么命令，事后不容易完整追溯；
- 团队成员很难共享同一套任务上下文和审核流程。

Multica 把编码智能体包装成工作区里的“成员”。你可以给它起名字、选择提供方和运行机器，再像分配普通任务一样把 issue 指派给它。智能体接手后会汇报进度；遇到需要决策的事情，可以提出阻塞；完成的结果先进入审核，而不是直接进入主分支。

这套思路的重点不在于让某个模型变聪明，而是让多智能体工作变得可见、可追踪。

## 一次任务如何流转

Multica 的基本流程可以拆成四步。

### 1. 建立运行时

运行时是智能体实际工作的电脑，可以是开发者的笔记本，也可以是云主机。Multica 的 daemon 运行在这台机器上，检测已经安装的智能体 CLI，并接收服务端下发的任务。

### 2. 创建智能体

在工作区里创建一个智能体，选择运行时和提供方，例如 Codex、Claude Code 或 Cursor Agent。Multica 本身不附带模型，也不代替你安装或登录这些 CLI。

### 3. 分配任务

创建 issue，把智能体设为负责人。任务可以关联代码仓库和文档，减少每次执行时重新解释上下文。

### 4. 查看执行并审核

智能体在运行时中拉起对应 CLI。执行过程持续写回任务，包括评论、工具调用、命令、错误和 Token 用量。完成后，任务进入审核环节，由人决定是否接受变更。

这里有个很实际的边界：Multica 负责调度和记录，具体代码质量仍由底层智能体、任务描述和项目测试共同决定。看板不会自动把一个模糊需求变清楚。

## 它目前提供哪些能力

根据项目 README，Multica 支持 20 种智能体 CLI，包括 Codex、Claude Code、Cursor Agent、GitHub Copilot CLI、Kimi、OpenCode 和 Qwen Code 等。切换提供方不需要迁移整个工作区，但对应 CLI 仍需在运行机器上安装并完成认证。

围绕任务管理，它提供了这些功能：

- issue 分配、任务状态和人工审核；
- 带时间戳的执行日志、错误记录和 Token 用量；
- 失败重试、超时和阻塞提醒；
- 项目、工作区、成员角色和智能体使用权限；
- 可复用的 Skills，以及按 cron 运行的 Autopilots；
- GitHub、GitLab、Gitea、Forgejo 等 Git 服务集成；
- Slack、飞书、钉钉和企业微信等消息渠道；
- Web、桌面端、CLI、API，以及需要自行编译的 iOS 客户端。

这些能力组合起来，更像“AI 工程团队的任务系统”，而不是代码编辑器。

## 它是怎么搭起来的

Multica 前端使用 Next.js，桌面端基于 Electron，后端使用 Go，数据存储是 PostgreSQL 17 和 pgvector。后端通过 WebSocket 把任务发给运行在用户机器上的 daemon，再由 daemon 拉起对应的编码智能体 CLI。

这套架构把管理面和执行面分开：

- 管理面保存任务、成员、日志和状态；
- 执行面靠近代码，实际命令在接入的运行机器上执行。

项目将“代码不离开运行时”列为卖点，但这句话需要结合底层工具理解。daemon 可以在本机运行，编码智能体自身是否把代码或上下文发送给外部模型服务，仍取决于该智能体及其提供方的配置和条款。自托管 Multica 不等于整条 AI 调用链都在本地。

## 云端、桌面端和自托管

最快的体验方式是注册 Multica 云服务，或安装 Windows、macOS、Linux 桌面端。桌面端会把当前电脑注册为运行时，并检测本机已有的智能体 CLI。

需要掌握数据和服务端部署时，可以选择自托管。官方方案使用 Docker Compose 或 Helm。基础自托管栈包括 Web 前端、Go 后端和 PostgreSQL；每个需要执行智能体的成员，还要在自己的机器上运行 CLI 与 daemon。

自托管并不等于零运维。团队仍需处理数据库、认证邮件、密钥、网络入口、升级和备份。项目 README 也说明 `main` 分支更新很快，生产环境更适合固定发布版本，而不是直接追踪最新提交。

## 适合哪些团队

Multica 对以下情况比较有吸引力：

- 团队已经同时使用两种以上编码智能体；
- 希望把智能体任务从个人终端搬到共享看板；
- 需要知道智能体执行过哪些命令、花了多少 Token；
- 想让任务定时运行，同时保留人工审核；
- 代码必须在指定开发机或自有云主机上执行；
- 团队希望保留不同模型和 CLI 的选择权。

如果只是个人偶尔让 Codex 修一个 bug，直接使用原工具通常更简单。Multica 增加了一层服务、daemon、权限和任务管理，只有当协调成本已经出现时，这一层才开始划算。

## 使用前要看清三件事

### 权限边界

daemon 会在接入机器上启动编码智能体。要限制它能访问哪些仓库、密钥和命令，不能只看 Multica 的角色设置，还要同时配置操作系统账户、容器或虚拟机隔离，以及底层智能体的审批策略。

### 人工审核不是自动安全

任务进入审核状态，只表示流程上留了一道门。团队还需要明确谁看 diff、跑哪些测试、什么条件下允许合并。否则审核很容易变成点一下按钮。

### 许可证不是标准 Apache 2.0

项目称自己为开源、可自托管，源代码也公开可见；但仓库使用的是自定义 **Multica License**。该许可证包含 Apache License 2.0 全文，同时添加了托管服务、商业嵌入和品牌使用等条件。GitHub API 因此把许可证识别为 `NOASSERTION`，而不是 Apache-2.0。

个人试用和内部部署可以先阅读许可证原文；如果准备向客户提供托管服务、把 Multica 嵌入商业产品，或进行品牌替换，应在实施前确认授权范围。这不是法律意见，准确权利与限制以仓库中的 LICENSE 为准。

## 怎么判断它值不值得引入

可以先用一个小项目做两周试验，不必一上来迁移所有工作：

1. 接入一台隔离的运行机器和一种已在使用的编码智能体；
2. 选择十个可验证的小任务，写清测试命令和禁止修改的范围；
3. 记录人工追问次数、失败恢复时间和审核耗时；
4. 再接入第二种智能体，看统一看板是否真的减少了上下文切换；
5. 检查日志、权限和成本数据能否满足团队要求。

如果引入后只是把“看终端”变成“看另一个看板”，收益有限。若它让任务交接、异常提醒和审核记录明显变清楚，才说明团队确实需要一个智能体协调层。

## 最后的判断

Multica 押注的不是某个模型，而是一种工作方式：编码智能体会越来越多，人需要一个地方安排它们、观察它们，也要在最后做决定。

它当前最清晰的价值，是把分散在多个终端里的智能体执行过程收回到同一条任务记录中。它也带来新的系统复杂度，权限设计和许可证都值得在正式采用前仔细检查。

把它理解成“编码智能体的 Jira + 运行调度 + 审计日志”，会比把它当成另一个 AI 编程工具更准确。
