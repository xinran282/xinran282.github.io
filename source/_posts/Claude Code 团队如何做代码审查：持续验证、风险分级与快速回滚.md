代码由智能体大量生成之后，人工逐行阅读很容易成为交付瓶颈。Claude Code 团队的做法是把审查分散到开发、合并和发布的全过程：机器负责大部分代码阅读，人根据风险参与决策，发布后仍保留明确的责任人和快速恢复手段。

他们衡量这套流程的标准很实际：每次变更消耗的人工时间能否下降，同时不增加回滚和事故。少花时间审批，如果换来更多时间救火，就没有节省成本。

在 2026 年 10 月发布的文章中，团队报告：6 月至 9 月，Claude Code 代码库合并的拉取请求（PR）数量增长超过一倍，需要撤销的 PR 占比下降超过 40%。这是团队对自身流程的观察，不能单凭这组数据断定某个审查工具带来了全部改善。

## 审查从提交 PR 之前开始

传统流程往往是写完代码、打开 PR，再等同事检查。Claude Code 团队把不少检查提前到了本地开发阶段。

工程师会给 Claude 可以执行的验证方式，例如测试、构建命令，或用来对照设计的截图，并要求它展示执行结果。随后，让另一个拥有全新上下文的智能体审阅 diff，避免审查完全沿用编写者的思路。

不少成员还会运行内部技能，分别查找缺陷、简化改动、验证端到端行为；界面变更还要对照设计规范。这里的基础是可检查的证据：跑了什么、结果是什么，读者能据此判断验证覆盖了哪些行为。

反复出现的问题则被写回规则或工具中。能用 lint 规则解决的，就不必每次重新解释。项目说明与审查说明也各有用途：

| 文件 | 主要内容 |
| --- | --- |
| `CLAUDE.md` | 技术栈、项目约定、目标与非目标；保持简短，需要时链接到其他文档 |
| `REVIEW.md` | 某个模块最怕出现的失败、跳过哪些路径、如何限制琐碎意见，以及问题应提供什么证据 |

原文给出的例子很具体：文档的失败可能是“说了假话”，配置的失败可能是“把请求路由错了”。这样的描述比泛泛要求“关注质量”更容易指导审查。团队还会单独检查审查器是否真的遵守了 `REVIEW.md`。

## 一个 PR 要经过哪些检查

每个 PR 在交给人之前都会接受 Claude 审查。审查器结合整个仓库和 PR 声明的意图阅读改动，检查它是否解决了问题、是否适合现有系统，以及是否破坏其他行为。修复缺陷时，还会追问是否处理了根因。

多个智能体并行查找问题，另一组智能体再验证候选发现。只有获得足够认可的发现才会发布。团队会过滤只涉及风格、诊断信息或清理工作的候选项，并把留下的意见按严重程度排列，区分重要问题、细枝末节和已有问题，避免把旧缺陷算到当前作者头上。

每条发现都必须得到回应：修复，或者说明理由后关闭讨论。独立的自动安全审查也有同样的约束；缺陷审查或安全审查中仍有未关闭的问题，PR 就不能合并。

这些语义检查之外，lint、类型检查、跨平台测试、构建和打包仍是硬性门槛。PR 模板还要求说明如何测试、如何撤销，由发起变更的人确认。合并队列则在最新主分支上应用改动后重新运行检查，降低两个分别通过的 PR 合并后发生冲突或回归的风险。

这条路径可以概括为：

> 本地验证与独立审查 → PR 自动审查、安全审查和 CI → 按风险决定人工批准 → 合并队列 → 内部试用与分阶段发布 → 监测和恢复。

每一层都有遗漏的可能，后续环节负责补上前面没有发现的问题。

## 人工批准的数量随风险变化

文案修改和自动更新器的改动，出错代价不同。团队按变更内容分级，而不是给所有 PR 分配同样的人工审查。

| 风险等级 | 原文示例 | 人工批准要求 |
| --- | --- | --- |
| 低 | 文档、文案、仅内部使用的功能、受功能开关保护的增量变更 | 满足适用条件且自动审查与安全检查通过后，可不要求人工批准 |
| 中 | 普通产品改动，以及缓存、自动更新器、系统提示词等敏感区域的改动 | 一人 |
| 高 | 风险最高的代码，以及明确规定需要双人批准的路径 | 两人 |

分类器读取变更并选择风险等级，第二个分类器再判断这次具体改动是否仍需额外的人参与。敏感路径和 CI 工作流文件等还受强制人工要求约束。

较宽松的路径只适用于仓库信任名单中的作者，主要是负责该仓库的团队。其他作者仍需第二个人批准。智能体的批准不能充当任何必需的人工批准；在智能体编写的 PR 中，指挥它的人可以算作一名所需的人工审查者，也必须承担相应责任。

批准还绑定到具体提交。若新增了系统无法为其担保的提交，例如智能体后续推送或手工解决冲突，原有批准就需要重新取得。

这里需要区分内部流程和产品能力：原文说明，对外的 Code Review 产品发布审查发现，并不代替人作出批准决定。允许部分低风险变更仅凭自动检查合并，是团队内部仓库采用的额外策略。

## 自动审查也需要知道何时停止

智能体编写、智能体审查，很容易形成反复修改的循环。团队曾遇到一个 CLI PR 在一夜之间经历超过 50 轮审查和修复，最后由作者叫停。

追踪被反复指出的代码后，他们发现，约 59% 从审查器第一轮检查时就已经存在。后续轮次常常是在继续挖掘此前没报出的旧问题。

于是团队调整了复审方式：三轮之后要求作者退一步重新考虑方案；前几轮之后只审新增 diff；一次指出一类缺陷，让作者检查同类实例；已经发布的发现不再重复。已有代码中的缺陷则另有夜间扫描处理。

原文报告了调整前后的内部数据：

| 指标 | 调整前 | 调整后 |
| --- | --- | --- |
| 一轮审查及修复后通过的比例 | 65% | 78% |
| 需要五轮或更多的比例 | 8.9% | 1.5% |
| 通过所需的平均审查次数 | 2.08 | 1.32 |

减少误报也影响交付效率。人可能几秒钟就能略过无关紧要的建议，智能体却可能认真修改，再触发一次提交和审查。因此，团队同时关注真实缺陷的检出能力和通过所需轮次。

## 用真实事故改进审查器

审查器自身也需要评估。团队收集曾经引发事故的 PR，以及后续修复和撤销记录，由熟悉代码的工程师确认缺陷及其位置，再组成每天运行的评测集。

修改提示词、工具或模型之后，都要在这套案例上重新打分。线上遗漏由此进入下一次审查器改进的验证范围。

团队还根据作者如何回应评论来观察噪声：接受并修复、判断为误报、说明行为有意如此，或认为不值得修改。他们也会在已知干净的 PR 上运行审查器，检查它是否提出可能诱导有害修改的建议。

发布之后，新行为通常先藏在功能开关后，供内部员工使用；公开发布先进入 `latest` 通道，`stable` 随后跟进。问题出现时，可以关闭开关、追加修复或撤销变更。作者和值班工程师共同关注回归，事故复盘则追问本应由哪一层发现问题。

这套机制也还有缺口：原文明确说，团队当时尚无根据回滚率、事故率自动收紧批准要求的熔断机制。进一步扩大零人工合并范围之前，他们希望补上这一环。

## 人仍然负责方向、证据和后果

人工投入更多集中在是否值得做、范围是否合适、架构是否会形成错误范式，以及高风险代码是否安全。审查者还得阅读验证证据，并判断现有检查会漏掉什么；如果说不清，就应该进行真正的审查，而不是快速点一下批准。

代码审查原本还承担传播知识的作用。减少人工阅读 diff 后，团队会按需让 Claude 为即将修改的模块生成讲解，有时制作可视化材料。公开工作频道也帮助成员了解彼此正在做什么。不过，团队承认这方面尚无正式流程，不能把自动生成讲解当作知识共享已经解决的证据。

每次上线仍有具体的人负责。小型或中型变更引发问题，通常由提交它的人修复，因为他掌握最多上下文；事故复盘关注系统如何漏检。小改动、功能开关和快速撤销，让这份责任更容易落实。

## 普通团队可以从哪里开始

原文建议先选择一个仓库试用 AI 审查，花几周调整 `REVIEW.md`，再扩大范围。比直接开放自动合并更早需要准备好的，是可执行验证、必须通过的 CI，以及 PR 中明确的测试、风险和撤销说明。

风险规则应先严格，再根据证据放宽。认证、计费、CI、发布流程和安装器等敏感区域，可以通过 CODEOWNERS 和分支保护保留人工要求。必需的人工批准不能由机器人顶替，新增提交也应重新审视原有批准。

随后再逐步补齐合并队列、分阶段发布、监测和便捷回滚，把真实事故纳入评测。衡量成效时同时看审批等待、人工评论与批准次数，以及回滚和事故：只有前者下降、后者没有恶化，减少人工审查才有实际收益。

对于准备采用这套流程的团队，最先要回答的问题是：这次变更可能怎样出错，谁或哪项检查能发现，漏过之后又能多快恢复。回答越具体，人工审查该放在哪里就越清楚。
