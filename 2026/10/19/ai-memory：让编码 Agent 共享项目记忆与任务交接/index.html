ai-memory：让编码 Agent 共享项目记忆与任务交接

发表于 2026-10-19 分类于 AI 工程

用 Claude Code 查了半天问题，换一个编码助手后，又得解释项目结构、失败过的方案和接下来要做什么。即使各个工具都有记忆功能，这些信息也未必能跟着你一起换过去。

ai-memory 为这类场景提供了一套自托管的共享记忆服务：通过客户端的生命周期 hooks 采集工作记录，整理成 Git 管理的 Markdown wiki，再让编码 Agent 通过 MCP 等接口检索。项目知识可以跨工具、跨机器复用，未完成任务则通过交接记录延续。

它最值得关注的设计是：wiki 页面是知识的权威来源，SQLite 承担检索等索引工作；默认核心路径无需调用 LLM，也不要求配置云端 API key。更深入的会话接续和模型辅助整理，则有各自的启用条件。

本文依据 2026 年 10 月 19 日核对的仓库文档，固定参考提交为 b18f22a。以下是文档解读，未在本机安装或实测；主分支描述的能力也需要与实际安装版本对照。

一、它保存哪些信息

理解 ai-memory，可以先分清项目规则、经验和任务状态。

信息 示例 应怎样使用
项目指令 测试命令、代码规范、禁止改动的目录 继续由项目指令文件明确约束
项目知识 模块职责、架构决策、已确认的坑 整理成可检索、可维护的 wiki 页面
任务交接 做到了哪里、试过什么、还有哪些疑问 传给接手的下一次会话
原生会话历史 某次讨论和工具调用的具体细节 在支持的受管启动流程中按需补读

假设你在处理数据库迁移：已经发现旧版本不支持某个语法，排除了一个方案，还剩回滚测试没跑。下一位 Agent 既需要知道数据库版本这个长期事实，也需要知道本次任务停在哪里。

ai-memory 同时处理这两类信息。项目知识可以让团队检索，个人交接则保留所属人的边界。交接采用有所有者、单次认领的协议，避免同一条记录被重复领取。

这些记录仍然属于历史资料。当前用户要求、项目指令和工作区实际代码决定本次任务应该怎么做；旧记忆中的命令不能自动变成新的执行授权。

二、从工作记录到下一次会话

仓库把基本流程概括为：

Hooks 是客户端在会话开始、用户提交提示、工具调用等时点触发的接入点。ai-memory 利用这些事件记录工作过程，减少用户手动要求“记住这件事”的负担。具体能采到哪些事件，取决于客户端的 hooks 能力和安装配置。

服务端会对输入做清理，再将记录纳入存储。在真正的会话结束事件到来时，默认可以用规则生成会话摘要页面和交接，不需要先调用一个模型来写总结。配置 LLM 后，系统还能进一步整理出概念、决策、注意事项等页面。

读回时也不会把整个知识库塞进提示词。系统通过交接、受配置控制的项目简报提供有长度预算的上下文，Agent 再检索或打开相关页面。这样能控制启动时的上下文用量，但也意味着：信息保存成功，并不保证每次任务都能自动拿到全部细节。

三、Markdown wiki 为什么重要

ai-memory 用一个 Rust 二进制提供 MCP/HTTP 服务，管理一个数据目录。文档列出的主要布局如下：

wiki 是知识页面的权威来源。你可以直接阅读、搜索或编辑这些文件，用 Git 查看修改历史，也可以用熟悉的 Markdown 工具维护它们。

检索层在页面之上组合全文搜索、实体匹配和链接邻居等结果；启用向量能力时，还可以加入向量检索。各路结果通过排序融合合并，因此系统不依赖一套必须另行维护的向量数据库才能工作。

这里有个容易误解的地方：页面索引可以从 wiki 重建，不代表整个数据库都只是可随手丢弃的缓存。SQLite 还保存会话、观察记录、交接和审计等状态。备份可阅读的知识页面与备份完整服务，范围不同。

四、共享记忆与完整接续相差多远

只接入 hooks 和 MCP，已经可以共享知识、检索旧经验和传递交接。直接启动原来的编码助手，会继续使用这些已有接入能力。

如果希望同一条工作线在不同客户端之间继续，仓库还提供可选的 ai-memory run 启动器：

启动器维护逻辑工作流与各客户端原生会话之间的对应关系。同一种客户端可以恢复其原生会话；切换客户端时，则提供可移交的工作流上下文。

在同一台机器上，如果上一客户端的会话存储可读且适配器支持，启动器还能把可见历史转换成私有的临时 Markdown 文件，供接手的 Agent 补查摘要没覆盖的细节。文档明确说明，这个临时文件的路径和正文不会发送给远程 ai-memory 服务端，也不包含隐藏推理。

这项能力有实际边界：原生历史接续需要 3.1.0 或更新的主机客户端；如果历史文件不在本机、不可读或超过安全读取限制，就退回到可移交的工作流记录与交接。换机器后仍能使用服务端保存的共享知识，但不能假定另一台机器上的原生聊天历史也会自动出现。

五、“无需 LLM”具体意味着什么

默认采集、规则化摘要、搜索和交接可以不调用 LLM。对于已有 Agent 的用户，这意味着记忆服务的核心流程无需额外配置一个云端大模型账号；编码助手自身的模型调用费用仍按原来的方式产生。

可选能力需要分开看：

能力 作用与条件
LLM 整理 将会话材料整理成更丰富的知识页面，需要配置相应提供方
向量检索 补充语义召回，数据流向取决于使用的嵌入提供方
LLM 重排序 将查询及受限的标题、片段交给模型重新排序，需显式开启
“dream” 后台整理 空闲时合并整理冷记忆，属于默认关闭的可选功能

配置 LLM 也会改变维护行为。当前架构文档写明：配置提供方后，自动改进调度器会审阅新结束的会话，经过验证的提案默认可自动批准。管理员可以关闭调度，或设置 require_approval = true，让提案等待人工审核。

因此，试用时可以先观察无需 LLM 的采集和检索是否够用，再决定哪些整理工作值得交给模型。

六、接入之前，先看支持层级

“支持某个 Agent”可能意味着 MCP 查询可用，也可能意味着采集、启动注入和受管会话恢复都已接通。这些能力不能互相替代。

接入层级 能做什么 需要核对什么
MCP-only Agent 可以调用记忆工具 不代表自动采集工作过程或注入交接
Hooks-only 可以采集部分生命周期事件 不代表同时提供 MCP 检索接入
MCP 与 hooks 同时具备查询和采集入口 启动注入、会话结束等事件仍有客户端差异
Managed workstreams 通过 ai-memory run 管理接续 只覆盖文档列出的客户端与版本

仓库列出了二十多种客户端的接入方式，Claude Code、Codex、Cursor、Gemini CLI、OpenCode、OMP 等都在其中。选择时应查看完整支持矩阵，尤其是会话结束和交接注入的限制。

平台方面，Linux、macOS 和 WSL2 标为支持；原生 Windows 仍标为实验性。Windows 用户应根据编码助手实际运行在 Windows 还是 WSL2 中，选择相应安装路径。

七、怎样判断它是否适合自己的项目

ai-memory 比较适合反复遇到交接成本的人：同一仓库会轮换使用多个编码助手，工作在不同机器间切换，或团队希望共享排错和架构经验。

如果项目规模很小、一直使用同一个助手，现有项目指令和少量手写笔记已经够用，那么再维护服务、客户端接入和数据备份，未必划算。

决定试用后，可以先按安装文档完成安装，再检查接入计划：

文档说明，setup 会展示计划并要求选择；配置后需要重启客户端。一次有用的试验可以很小：完成一段排错工作，结束会话，然后换一个已接入的 Agent，检查它能否准确说出已排除的方案、未完成事项和对应依据。

比起问“你记住了吗”，这种具体任务更容易检验系统是否真的减少了重复解释。

八、团队共享时，数据边界要一起设计

跨机器使用通常是把客户端连到同一个服务端，数据最终保存在服务端所在机器。项目知识可以按项目共享，个人交接和用户归属则有单独的规则；一个数据目录只能由一个服务端管理。

仓库提供输入清理、采集排除规则和认证能力，但脱敏属于尽力处理，不能保证识别所有敏感内容。配置云端 LLM 或嵌入提供方后，相应材料可能离开自托管服务端。团队应把这些配置与采集范围一起确认。

记忆也需要维护。旧决策会失效，失败方案可能因为依赖升级重新可用。Git 版本历史便于追踪变化，却不等于任何删除都可无限期撤销；清理、保留与备份应按实际配置检查。

我更看重 ai-memory 把经验变成可检查页面的做法。遇到错误记忆时，能找到原文、纠正页面，再验证下一次检索是否改正，比单纯增加历史记录更有用。是否采用它，最终可以用一个标准衡量：下一次接手项目时，重复解释有没有减少，错误的历史结论有没有被及时纠正。
