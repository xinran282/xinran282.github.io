Claude Code 团队如何审查 AI 生成的代码

发表于 2026-10-22 分类于 软件工程

当 AI 写代码的速度超过人逐行阅读的速度，团队该怎样保证质量？Claude Code 团队的做法是：让自动验证和 AI 审查覆盖大部分常规问题，按变更风险安排人工审批，再用渐进发布和快速回滚处理漏网之鱼。

他们优化的是每次变更消耗的人工时间，同时要求回滚和事故不能增加。这个时间账既包括审查，也包括出了问题后的修复；少看几分钟代码，却多花几小时救火，不能算提高效率。

本文根据 Addy Osmani、Morgan Westlee Lunt 和 Qing Wang 于 2026 年 10 月 15 日发表的 《How the Claude Code team does code review》 整理。文中的运行数据来自团队自述，不能直接当作其他团队采用同一流程后的效果承诺。

代码增长之后，审查要回答什么问题

原文称，Claude 编写了 Claude Code 自身约 90% 的代码。2026 年 6 月到 9 月，Claude Code 代码库合并的拉取请求（PR）数量增长超过一倍，需要回滚的 PR 占比下降超过 40%。这是回滚占比的变化，不能读成回滚次数减少了 40%。

另一个数字来自 Anthropic 的 monorepo：每日落地的变更从当年 5 月约 2,500 个增至 9 月超过 30,000 个。Claude Code 使用独立仓库，这个数字只能说明公司整体面临的规模压力。

在这种速度下，“有没有人读过每一行”很难完整衡量审查质量。团队转而问：这次变更可能怎样出错，哪种检查最适合发现它？

这个问题也改变了审查的时机。审查从提交 PR 后等待同事的一个环节，逐渐前移到编写过程。等人开始看时，代码通常已经经过至少一轮 Claude 审查和修复。

从本地验证到上线，检查分布在整条路径上

各层检查都有遗漏。团队把它们串起来，并为上线后的恢复保留手段。

阶段 主要动作 作用
提交 PR 前 运行测试、构建、lint，由新上下文中的另一个 agent 审查 diff 先消化常规错误，提供可检查的结果
PR 阶段 必需 CI、AI 代码审查、独立安全审查 检查行为、系统影响和安全问题
审批阶段 分类器判断风险，敏感路径设硬规则 决定是否需要人工，以及需要几人
合并阶段 合并队列在最新主分支上重新检查 发现多个变更组合后的冲突
发布阶段 功能开关、内部试用、分渠道发布 限制问题影响的范围
上线之后 作者和值班工程师观察，关闭开关、修复或回滚 尽快发现并恢复异常

先要求 agent 给出验证结果

团队会给 Claude 能实际运行的检查，例如测试、构建，或用于比对设计的界面截图，并要求展示输出。这样，完成声明就有了可核验的依据。

随后，由另一个处于新上下文中的 agent 审查 diff。原文还提到，一些工程师会在提交前运行查 bug、简化改动和端到端验证的内部技能；界面变更还会核对设计规范。

反复出现的审查意见，会被写回工具和规则。适合机械判断的问题加入 lint；项目背景与约定写入 CLAUDE.md；某个模块的审查重点写入 REVIEW.md。

这两类文档各有用途。CLAUDE.md 介绍技术栈、目标和约定，保持简短，复杂内容链接到其他文档。由代码负责人维护的 REVIEW.md 则说明本模块怎样才算出错：文档可能陈述失实，配置可能把请求路由到错误位置。它还应限制琐碎意见，列明可跳过的路径，要求审查意见给出文件和行号证据。

让 AI 审查意见也接受核验

每个 PR 都会先经过 Claude 审查。审查会结合仓库和 PR 声明的意图，判断改动是否解决问题、是否适合现有系统，以及是否破坏其他功能。修 bug 时，还要检查是否触及根因。

多个 agent 会并行找问题，再由另一组 agent 对发现进行核验和投票。只有达到认可门槛的发现才会发布。纯风格、诊断类或清理类意见会被过滤，保留下来的意见按严重程度排列，并标注 Important、Nit 或 Pre-existing，避免把原有问题算到本次改动头上。

团队报告，研究预览推出后，收到实质性审查意见的内部 PR 占比从 16% 升至 54%。这个指标说明更多 PR 得到了具体反馈，单凭它还无法判断发现的准确率或实际减少的事故数量。

每条发现都要处理：修复，或者给出理由后关闭讨论。安全审查单独执行。代码审查或安全审查中还有未关闭的发现时，PR 就不能合并。允许说明理由后关闭，也给误报留下了处理出口。

CI 则承担确定性的检查：lint、类型、多平台测试、构建和打包。PR 模板要求说明如何测试、如何撤销；Claude 可以填写，但发起变更的人需要确认。

人工审批按风险分配，责任落到具体的人

团队的目标是让多数 PR 在最多一名人类参与的情况下合并，这个人可以是作者。具体审批数量取决于变更风险。

风险 原文中的例子 人工审批要求
低 文档、文案、仅供内部使用的功能、藏在功能开关后的新增行为 自动审查和安全检查通过后，可不要求人工审批
中 常规产品变更，以及缓存、自动更新器、系统提示等敏感区域的改动 一人
高 最高风险代码，以及明确要求双人审批的路径 两人

分类器读取变更并确定风险等级。第二个分类器还会检查：即使所属等级允许减少人工，这次具体改动是否仍需要另一个人参与。代码负责人指定的敏感路径和 CI 工作流文件，始终需要人工。

这套较宽松的审批路径只开放给仓库信任名单内的作者，主要是负责该仓库的团队成员；其他作者需要第二个人批准。Agent 的批准不能占用要求由人完成的审批名额。

如果代码由 agent 编写，指挥它的人可以计入所需的人工审查人数，也承担变更责任。审批对应的是某一个具体提交。出现系统无法担保的新提交，例如 agent 后续推送或人工解决合并冲突后，需要重新批准。

因此，低风险 PR 可以没有人工审批，并不代表这次变更没有人负责。

人仍要判断是否值得做、范围是否合适，审查高风险代码和会被后续开发沿用的架构选择，并阅读测试输出、截图及审查发现。若说不清现有检查会漏掉什么，就应安排一次实质审查。

AI 之间反复修改，也会拖垮流程

自动审查有一种容易低估的成本：作者 agent 会认真执行那些人类看一眼就会忽略的琐碎建议。每次修改又产生新提交，触发下一轮审查。

原文记录，一个 CLI PR 曾在一夜之间经历超过 50 轮审查和修复，最后由作者叫停。团队用 git blame 检查反复被指出的代码，发现约 59% 在审查器第一轮运行时就已存在。后续轮次往往是在原有代码里继续挖出零星问题。

团队此前习惯默认多跑几轮，因为每一轮似乎都能找到东西。对高风险改动，这可能有价值；推广到每个 PR，就容易让审查迟迟无法结束。

他们调整了规则：

  • 三轮之后，请作者退一步重新考虑实现方案。
  • 前几轮过后，只重新审查新增的 diff。
  • 指出一类错误，让作者一次修正同类实例。
  • 不重复发布已经提出的发现。

调整前后的内部数据如下：

指标 调整前 调整后
一轮审查和修复后通过的比例 65% 78%
需要至少五轮的比例 8.9% 1.5%
平均通过所需审查次数 2.08 1.32

这些是流程调整前后的观察结果。原文没有提供足以把全部改善归因于某一条规则的实验细节。它给出的工程提醒仍然明确：除了发现问题的能力，还要衡量审查需要多少轮才能结束。

用真实事故校准审查器

想让审查器找到更多 bug，很容易走向“多报一些总没错”。但误报也消耗人工时间，甚至会诱导作者把正确代码改坏。

团队把过去造成事故的 PR，以及对应的后续修复和回滚，整理成评测集。熟悉代码的工程师确认 bug 和位置后，审查器每天在这套案例上运行。提示词、工具或模型发生变化时，也要用这些案例衡量效果。

噪声则通过人们如何回应审查意见来观察：修复了、认为判断错误、说明行为符合预期，还是觉得不值得改。团队还会让审查器检查已知没有问题的 PR，统计它是否提出了会导致有害修改的建议。

他们写下的优先级是先抓到真实 bug，再减少审查轮次。两者要一起看：为了少跑一轮漏掉严重错误，或者为了多找一个小问题反复折腾，都可能增加总成本。

原有代码的检查也有单独安排。审查 agent 每晚会扫描既有代码，减少把历史问题都挤到当前 PR 中处理的压力。

快速恢复，是减少人工审批的前提之一

合并队列会把 PR 应用到最新主分支后重新运行检查，防止两个各自通过的变更组合后破坏主分支。

新行为通常先放在功能开关后，供 Anthropic 员工使用，再进入公开发布。公开版本先到 latest 渠道，stable 渠道随后跟进。功能开关可以无需重新部署就关闭；小变更也更容易定位和回滚。

作者和值班工程师仍然需要观察问题。团队有每周轮换的值班机制，事故复盘会问哪一层原本应该发现这个问题。

这里也有尚未补齐的部分。原文明确说，他们还没有在回滚率或事故指标上升时自动收紧审批的熔断机制；在让更多代码进入零人工合并路径之前，工程师希望补上它。

这说明，减少审批依赖持续观察和恢复能力。只有一个会评论 PR 的 AI，还不足以支撑原文描述的整套流程。

少读日常 diff 后，团队怎样理解代码

代码审查还承担知识传播的作用。少读同事的 diff，团队会不会逐渐不了解代码库？

原文没有给出正式的知识传递制度。团队成员需要理解某个模块时，会让 Claude 针对那一部分生成解释，有人还会要求制作可视化讲解。公开的 Slack 工作频道则让其他人能看到正在开发的内容，并尽早提出方向上的异议。

这是他们目前的实践，尚不能据此判断它能否长期补足架构知识传承。可以借鉴的具体做法是：围绕即将修改的模块主动学习，同时让产品方向和设计讨论尽早发生。代码写得很快，也允许团队在发现方向不对时关闭或重做 PR。

其他团队可以从哪里开始

原文建议先把基础检查建立起来，再依据证据逐步放宽审批。实际采用时，可以按以下顺序推进：

  1. 把测试、构建、lint 等验证命令写清楚，让 agent 提供运行结果。PR 模板加入测试方法、风险和撤销方式。
  2. 在一个仓库试用 AI 审查和独立安全审查，持续修订简短的 REVIEW.md。重复出现的问题转成规则或自动检查。
  3. 限制审查轮次，后续重点检查新 diff。对已确认正确的变更也做评测，观察误报是否会诱发有害修改。
  4. 明确风险等级，用 CODEOWNERS 和分支保护守住认证、计费、CI、发布流程及安装器等敏感路径，保留必要的人工审批。
  5. 建立合并队列、功能开关和渐进发布能力，确认能快速撤销，再考虑放宽低风险变更的审批。

判断流程是否有效，需要同时看人工审批数的中位数和第 95 百分位、人工评论数量、等待人的时间，以及回滚和事故指标。过去的事故还要持续进入评测集，检查审查器的下一次调整究竟有没有用。

最后还需区分产品与内部实践：按原文发表时的说明，公开的 Code Review 产品发布审查发现，不替人批准 PR。低风险变更依赖自动检查合并，是 Claude Code 团队内部仓库在风险规则和责任机制下的进一步实践。

对准备采用这套方法的团队，更实际的起点是检查现有验证究竟能发现什么、漏掉什么，以及遗漏发生后多久能恢复。这些答案清楚了，减少多少人工审批才有依据。
