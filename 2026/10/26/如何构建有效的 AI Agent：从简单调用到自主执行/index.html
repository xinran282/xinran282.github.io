如何构建有效的 AI Agent：从简单调用到自主执行

发表于 2026-10-26 分类于 人工智能
根据 Anthropic《Building effective agents》整理，解释工作流与 Agent 的区别、五种工作流模式，以及用环境反馈和工具设计提高系统可靠性的方法。

构建 AI 应用时，先让最简单的方案达到要求，再考虑增加步骤和自主性。Anthropic 在《Building effective agents》中给出的建议是：如果一次模型调用配合检索和示例就能完成任务，就先用这个方案；只有评估表明它不够用时，才引入工作流或自主 Agent。

这个选择直接影响成本、等待时间和排查问题的难度。模型调用越多，系统就越需要解释：多出来的步骤究竟改善了什么？

本文根据 Anthropic 的原文整理并加入解释性示例，并非逐句翻译。原文首发于 2024 年 12 月 19 日，当前页面已更新部分工具与模型名称，并提示工具生态已有变化。下面着重讨论其中的架构方法，不把它当作最新产品选型清单。

先分清工作流与 Agent

“Agent”经常被用来泛指能调用工具的 AI 系统。Anthropic 为讨论架构，把这类系统进一步分为工作流和 Agent，区别在于谁控制执行过程。

工作流由代码预先规定路径。模型可以负责分类、生成或判断，但它在什么环节运行、结果交给谁，已有明确安排。例如，系统先提取合同条款，再检查缺失项，最后生成摘要。

Agent 则由模型根据任务和执行结果，动态决定下一步操作。用户要求修复一个程序问题后，模型可能先读代码、运行测试，再根据报错修改文件；接下来查什么、改哪里，要等反馈出现后才能确定。

比较项 工作流 Agent
执行路径 代码预先规定主要结构 模型根据反馈动态选择
适用任务 步骤清晰、可稳定拆分 步骤难以预知、需要探索
主要优势 行为更可预测，便于逐步检查 能随任务变化调整行动
主要代价 需要预先设计分支与流程 成本更难预估，错误可能累积

判断自己的系统属于哪一种，可以先看一个问题：下一步要做什么，主要由预设程序决定，还是由模型结合现场信息决定？

实际系统可以混合使用两者。一个客服系统可以先用固定流程识别问题类型，再把少数需要调查的工单交给 Agent。

从增强后的单次调用开始

原文把“增强型大语言模型”作为基本组件：模型可以使用检索、工具和记忆，获取上下文、执行操作，并保留需要的信息。

例如，回答某笔订单的配送状态，需要读取订单数据；解释企业内部规定，需要检索对应文档。这些能力能让模型获得完成任务所需的材料，但接入工具本身并不意味着必须建立自主循环。

此时应先检查两个方面：这些能力是否符合任务需要，模型是否能看懂并正确使用它们。接入很多工具，却没有写清参数、返回值和使用边界，会增加选择错误的机会。

原文提到 MCP 是连接外部能力的一种方式。它解决的是接入问题；任务应该按固定流程执行，还是交给模型动态安排，仍然需要单独设计。

如果单次调用效果不够稳定，先定位原因。缺资料就改善检索，输出格式不合格就增加结构约束，要求不清楚就补充示例。只有问题确实来自任务需要多个阶段，增加调用才有明确理由。

五种工作流，各自解决什么问题

原文介绍的五种模式可以单独使用，也可以组合。选择依据是任务结构，不必依次升级。

提示链：把固定步骤拆开

提示链让一次调用的输出成为下一次调用的输入。比如，先拟定文章提纲，检查是否包含必要内容，再根据通过检查的提纲写正文。

这里的价值是降低每次调用的任务难度。中间还可以加入程序检查：必填字段是否齐全、长度是否超限、格式是否符合要求。发现问题后，可以停止或重试当前环节。

它适合能清晰拆成固定子任务的工作，代价是多轮调用带来的等待。如果某一步根本不依赖前一步，就可以考虑并行处理。

路由：把不同输入交给合适的处理方式

路由先识别输入类别，再选择对应流程、提示词或模型。客服问题可以分为常见咨询、退款申请和技术支持；简单问题与需要复杂分析的问题，也可以使用不同能力和成本的模型。

这样可以为每类任务编写更有针对性的指令，减少一套通用提示词承担过多职责的情况。

前提是分类足够可靠。实际实现还需要考虑分错类时怎么办。例如，可以让无法确定类别的请求进入通用处理流程。这是基于原文模式的实现建议。

并行化：独立处理，最后汇总

原文把并行化分为两种：拆分任务，以及对同一任务进行多次独立尝试。

拆分任务适用于彼此独立的检查。例如，分别评估回答的事实依据和格式要求，再由程序汇总结果。每次调用能专注于一个方面，也有机会缩短总等待时间。

多次独立尝试则适合需要多个判断视角的场景。原文举例，让不同提示词分别检查代码漏洞，再按规则汇总发现。

多次调用会增加成本，而且相同模型可能重复犯同一种错误。汇总规则也要服务于目标：任何一个检查器报出问题就进入人工复核，与多数检查器同意才拦截，会产生不同的漏报和误报。调用数量本身不能保证结果正确。

编排器与工作者：根据当前任务拆分工作

这种模式由一个模型分析任务，动态决定需要哪些子任务，再交给其他模型处理，最后汇总结果。

它与固定并行任务的区别在于：子任务要等看见具体输入后才能确定。修改一个软件功能时，可能只涉及一个文件，也可能需要同时处理接口、页面和测试，难以事先列出适用于所有请求的固定分工。

原文仍把它列为工作流模式。这里动态变化的是拆分结果，而整体仍围绕“拆分、分派、汇总”的结构运行。它也说明，工作流内部可以包含模型决策。

使用时需要留意整合结果的成本。子任务做完后，仍可能出现重复工作、接口不一致或遗漏，需要由编排环节检查。

评估器与优化器：按明确标准反复修改

这种模式让一个模型生成结果，另一个模型评估并给出反馈，然后继续修改。例如，翻译模型完成初稿后，评估模型指出术语或语气问题，再据此修订。

原文给出两个适用信号：人类提出具体反馈后，结果确实能够改善；模型也有能力提出类似的有效反馈。

评价标准越含糊，循环越容易变成反复改写。实现时应明确什么算达标，并设置停止条件，例如达到标准、达到次数上限，或继续修改已没有可识别的收益。这些停止条件是对模式的工程化补充。

什么时候需要自主 Agent

如果执行步骤难以预先确定，而且后续行动必须依赖前一步的结果，就有理由考虑 Agent。

以修复代码为例：模型先定位相关文件，运行测试后发现失败原因与最初猜测不同，于是调整调查方向。这里需要的是持续根据新信息决策。

原文对 Agent 的描述并不复杂：模型循环使用工具，根据环境反馈继续行动，直到完成任务、遇到阻碍，或触发停止条件。

执行过程可以概括为：

  1. 明确目标，必要时向用户澄清。
  2. 选择行动并调用工具。
  3. 读取工具结果，判断进展。
  4. 继续行动，或完成、停止、请求人类介入。

其中容易被忽视的是第三步。模型说“已经修好了”，只是一个陈述；修改后的测试结果、程序运行输出或真实环境状态，才是判断是否成功的依据。

原文称这种依据为来自环境的“ground truth”。这不意味着每个工具返回值都绝对可靠，而是要求 Agent 用可观察的执行结果检验自己的判断，避免只靠先前生成的文字继续推断。

自主执行也会放大错误。一开始理解偏了，后续操作可能都围绕错误目标展开。原文因此建议在沙箱中充分测试，设置合适的约束，并在检查点或遇到阻碍时引入人类反馈。最大迭代次数也是常见的停止条件。

工具接口值得花多少精力

原文附录提出，工具定义应得到与整体提示词同等的设计关注。模型的计划即使合理，也可能因为工具难用而执行失败。

同一个文件修改操作，可以要求模型输出完整文件，也可以要求输出差异补丁。两者对模型的要求不同：补丁可能需要准确的行数信息；把代码放进 JSON 字符串，则需要额外处理引号和换行转义。

选择工具格式时，需要考虑模型能否稳定生成，而不只是人类程序员觉得哪一种更紧凑。

好的工具说明应让模型看清：

  • 工具能做什么，以及与相似工具的区别。
  • 参数需要什么格式，哪些值是合法的。
  • 返回结果如何理解，常见错误如何处理。
  • 有代表性的调用示例和边界情况。

原文给了一个具体案例：在构建 SWE-bench Agent 时，模型离开项目根目录后，会在使用相对路径的工具上犯错。团队把工具参数改为必须使用绝对路径，解决了这一类问题。

这体现了防错设计的作用。与其反复要求模型记住当前目录，不如让接口减少歧义。原文也提到，该项目花在优化工具上的时间，实际上超过了优化整体提示词的时间。

客服与编码为什么适合这种执行方式

原文用客服和编码说明 Agent 的实际价值。两者都有对话之外的行动，也都有能够返回结果的外部环境。

客服系统可以查询订单、读取知识库、更新工单，按业务规则处理退款。对话提供目标，工具完成操作，后续状态则帮助判断问题有没有解决。具体操作仍需要符合业务权限，并在适当环节保留人工介入。

编码任务的反馈通常更直接：编译报错、测试结果和运行日志，都能帮助模型调整修改。原文报告了其 Agent 在 SWE-bench Verified 上处理真实 GitHub 问题的实践，但没有在这篇文章中给出可据以比较不同系统的完整成绩数据。

测试通过也不能覆盖所有要求。修改是否符合整体架构、是否满足用户真正需要，仍需要更广的检查和人类审阅。

从这两个案例可以归纳出一个选择依据：任务有明确目标、可执行的工具和可观察的反馈时，Agent 才更容易形成有效的行动循环。这个归纳是对案例的解释，不是适用于所有任务的保证。

用评估决定下一步增加什么

可以把原文的方法落实成以下决策表：

当前遇到的问题 优先考虑的方案
缺少资料或示例 改善检索、上下文与单次调用
固定任务一次做不好 提示链，并检查中间结果
输入类别差异很大 路由到专门处理方式
子任务彼此独立 并行处理并汇总
子任务需要临时确定 编排器与工作者
有明确评价标准，反馈能改善结果 评估器与优化器
后续步骤依赖不断出现的环境反馈 自主 Agent

框架可以减少模型调用、工具解析和流程连接的重复工作，但也可能隐藏提示词、响应和执行细节。Anthropic 建议先理解底层行为，许多模式可以直接通过模型 API 实现；采用框架时，也要能够追踪实际执行过程。

实践中，可以先为简单方案建立评估基线，记录完成质量、耗时和成本。增加一个环节后，用相同任务重新比较。若提升无法观察，就需要重新判断这一步是否值得保留。

这些指标是对原文“测量表现并迭代”建议的具体化。它们帮助回答一个实际问题：当前系统究竟还缺少信息、固定步骤、检查，还是根据反馈自由行动的能力？

原文来源

Anthropic：《Building effective agents》，作者 Erik S. 与 Barry Zhang，首发于 2024 年 12 月 19 日。
