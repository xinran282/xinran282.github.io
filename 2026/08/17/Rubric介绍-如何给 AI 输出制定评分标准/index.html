Rubric 介绍：如何给 AI 输出制定可执行的评分标准

发表于 2026-08-17 分类于 人工智能
介绍 Rubric 在 AI 评测中的作用，以及如何把模糊的质量要求拆成可执行、可复现的评分标准。

Rubric 介绍：如何给 AI 输出制定可执行的评分标准

评测 AI 输出时，最容易出现的问题不是没有分数，而是大家不知道“什么样的答案才算好”。有人看准确性，有人看表达，有人只看结果能不能直接使用。标准不一致，最后得到的分数也很难比较。

Rubric 就是用来解决这个问题的。它把“好答案”的要求拆成若干评分维度，并为每个维度写出清楚的等级描述。这样，人工评审、模型评审和自动测试才有机会对着同一套标准工作。

Rubric 是什么

Rubric 可以理解为一份结构化评分规则。它通常包含四部分：

  • 评测对象：要评估的回答、代码、摘要或工具调用结果。
  • 评分维度：准确性、完整性、格式、语气、安全性等。
  • 等级描述：每个分数对应什么表现。
  • 评审依据：评审时应该查哪些事实、字段或行为。

例如，评估一个技术问答时，可以设置“事实准确性”这一维度：

分数 描述
0 核心结论错误，或包含会误导用户的内容
1 结论基本正确，但遗漏了关键限制条件
2 结论正确，解释完整，并明确了适用边界

关键不在于分成几档，而在于每一档都能让不同评审者作出相近判断。

为什么需要 Rubric

把“感觉不错”变成可以讨论的标准

“回答得不错”不是一个可执行的要求。它至少可以继续拆成：事实是否正确，是否回答了问题，是否遵守格式，是否给出了下一步。

拆开以后，评审者可以指出具体问题，而不是只给出一个受个人偏好影响的总分。

让不同版本可以比较

比较两个 Prompt、两个模型或两个 Agent 工作流时，不能只看某一次输出。固定 Rubric 后，可以让它们处理同一批样本，再逐项比较得分和失败原因。

帮助定位改进方向

总分下降只能说明结果变差了，却不能说明哪里变差。分维度记录后，可以看出问题是在事实、格式、工具选择，还是在回答过于冗长。

怎样设计一份 Rubric

先定义任务目标

先写清楚评测要回答什么问题：

  • 这个 Prompt 是否减少了事实错误？
  • 这个 Agent 是否正确选择了工具？
  • 生成的摘要是否覆盖了原文的主要信息？
  • 代码是否满足需求并能通过测试？

目标不同，评分维度也不同。不要拿一份通用评分表套所有任务。

选择少量真正重要的维度

可以从任务结果倒推维度。客服回答常见的维度是事实准确性、问题解决程度和语气；代码生成更关心行为正确性、测试通过情况和改动范围；工具调用则需要检查工具选择、参数、权限和结果处理。

维度过多会增加评审成本，也会让每个维度的边界变模糊。优先保留会影响任务成败的项目。

为每个等级写可观察的描述

不要只写“优秀、良好、一般、较差”。这些词没有告诉评审者应该观察什么。

更好的写法是描述具体行为：

  • 是否给出了正确结论。
  • 是否遗漏用户明确要求的字段。
  • 是否调用了不必要的工具。
  • 是否在没有证据时明确说明不确定性。
  • 是否修改了任务范围之外的内容。

描述应尽量使用能被检查的事实，而不是“看起来专业”这样的主观表达。

明确硬性失败条件

有些问题不能靠其他维度的高分抵消。例如，安全策略被绕过、代码无法运行、工具调用修改了错误对象，这些都可以设置为直接失败或设置上限分。

硬性失败条件要单独写出来，否则总分可能掩盖严重问题。

Rubric 如何用于实际评测

准备有代表性的样本

样本不能只覆盖最容易的问题。应包含正常输入、边界情况、历史上失败过的案例，以及容易混淆的相似问题。

如果要比较两个版本，两个版本必须处理同一批样本。更换样本集以后，得分变化就不能简单归因于 Prompt 或模型本身。

先做独立评审

评审时尽量不要让评审者先知道输出来自哪个版本。否则，版本名称、模型偏好或先入印象都可能影响判断。

对于高风险任务，保留评审理由和原始输出，只记录一个总分是不够的。后续排查需要知道分数为什么这样给。

检查评审者之间的差异

如果两位评审者经常对同一答案给出完全不同的分数，通常说明 Rubric 的描述不够清楚，或者样本本身缺少必要上下文。

这时应先讨论分歧案例，修改评分描述，再重新评测。不要直接用平均分把分歧隐藏起来。

同时记录成本和失败率

质量分数不是唯一指标。一个版本可能只提高了一点平均分，却增加了大量 Token 消耗、响应延迟或工具调用次数。实际选择时，还应记录：

  • 通过率和关键失败率。
  • 平均延迟和 Token 成本。
  • 人工复核比例。
  • 工具调用次数和副作用。

Rubric 负责描述质量，但最终判断还要结合系统的工程约束。

人工评审、模型评审和自动测试

三种方式各有适用范围：

  • 自动测试适合检查格式、字段、数值、编译结果和确定性规则。
  • 人工评审适合判断复杂意图、事实边界和真实可用性。
  • 模型评审适合处理规模较大的开放式输出，但必须用人工样本校准，不能把评审模型当成绝对可靠的裁判。

更稳妥的做法是组合使用：先用自动规则筛掉明显失败，再让模型评审处理大部分样本，最后由人工复核高风险和有争议的案例。

常见问题

把 Rubric 写成 Prompt

Rubric 是评测标准，Prompt 是给模型的指令。评审模型可以在 Prompt 中读取 Rubric，但两者的职责不同。把评分标准混入业务 Prompt，容易让生产逻辑变得难以维护。

维度互相重复

“准确性”“专业性”“可信度”可能都在评价事实是否正确。如果它们没有清楚区分，同一个问题会被重复扣分或重复加分。

只看平均分

平均分可能掩盖少量但严重的失败。安全违规、错误工具调用和关键事实错误都应该单独统计。

频繁修改评分标准

Rubric 变了，历史分数就不再完全可比。修改时要记录版本、修改原因，并保留一小组固定样本做回归测试。

最后

Rubric 的价值不在于把回答变成一个漂亮的数字，而在于把“什么算好”说清楚。先明确任务目标，再选择少量关键维度，为每个等级写出可观察的行为，同时保留失败案例和评审理由，评分结果才有机会指导下一轮改进。
