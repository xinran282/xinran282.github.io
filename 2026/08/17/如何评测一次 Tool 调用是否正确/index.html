如何评测一次 Tool 调用是否正确

发表于 2026-08-17 分类于 人工智能
一套评估 Tool 调用是否真正正确的判断框架，覆盖意图、参数、时机、副作用、结果验证和失败处理。

如何评测一次 Tool 调用是否正确

评测一次 Tool 调用，不能只看它有没有返回成功，也不能只看模型有没有“用工具”。更可靠的判断是：这次调用是否在正确的时机，用正确的工具、正确的参数，对正确的对象做了正确范围内的操作，并把结果用于后续决策。

换句话说，Tool 调用的正确性不是单点判断，而是一条链路。链路上任何一环错了，最终都可能表现成“工具没坏，但任务做错了”。

先看任务是否真的需要调用工具

第一步不是检查参数，而是检查调用本身有没有必要。

有些问题可以直接回答，调用工具反而增加噪声。比如用户只问“解释这个概念”，模型却去搜文件或联网，通常不是好调用。相反，如果用户问的是本地代码、当前价格、最新政策、具体文件内容、网页状态，模型不调用工具就直接回答，风险也很高。

可以用三个问题判断：

  • 用户的请求是否依赖外部状态、本地状态或实时状态？
  • 模型记忆中的答案是否可能过期、不完整或不可验证？
  • 工具返回的信息是否会改变最终答案？

如果三个问题都是否定，工具调用未必必要。如果至少一个是肯定，就要看模型是否选择了合适的工具。

再看工具选择是否匹配意图

正确的工具选择，要能贴近用户真正要完成的事。

用户要找代码里的调用点，优先用搜索工具；用户要修改文件，才进入编辑工具；用户要验证页面视觉效果，就该打开浏览器或截图；用户要查最新信息，就需要联网或权威数据源。工具的名称相近不代表用途相同，能返回结果也不代表它适合当前任务。

一个常见误判是“工具调用成功，所以选择正确”。比如用全文搜索去理解一个结构化配置文件，可能能搜到关键词，但漏掉继承、默认值和解析规则。又比如用网页搜索回答某个仓库里的实现细节，往往绕远了，甚至把外部资料误当成本地事实。

评测时要问：如果换成更贴近任务的工具，结果会不会更完整、更可验证、更少副作用？如果答案是会，那原调用就不算理想。

参数是否精确、完整、不过度

工具选对之后，参数决定调用质量。

好的参数通常有三个特征：范围明确、对象准确、约束充分。搜索代码时，查询词不能太泛；打开文件时，路径要对；调用 API 时，分页、过滤条件、时间范围、权限范围要符合任务。参数不足会漏信息，参数过宽会带来噪声，参数过强则可能排除正确答案。

可以把参数错误分成四类：

  • 对象错：查错文件、点错链接、请求错接口。
  • 范围错：本该查整个项目，却只查了一个目录；本该限制日期，却查了全部历史。
  • 格式错：参数类型、编码、路径转义、时间格式不符合工具要求。
  • 约束错：用户只要求查看，模型却传入会修改状态的选项。

评测参数时，不要只看“工具有没有报错”。很多错误参数不会报错，只会返回一个看似合理但不完整的结果。

调用时机是否合理

Tool 调用还有时机问题。

太早调用，模型可能还没理解任务，查了一堆无关信息。太晚调用，模型可能已经基于猜测形成结论，只把工具结果当作装饰。正确的时机通常是在模型明确了待验证的问题之后，在下结论之前。

对于多步任务，还要看调用顺序。先读项目结构，再改代码；先确认现有风格，再加组件；先获取最新事实，再做建议。这些顺序不是形式主义，而是为了降低误判和返工。

如果一次调用发生在错误的前提之后，即使调用本身参数无误，它服务的也是错误目标。

是否尊重权限、成本和副作用

有些工具只是读信息，有些工具会写文件、发请求、启动服务、删除资源、创建外部对象。评测这类调用时，必须把副作用纳入正确性。

一次正确的 Tool 调用应该满足：

  • 没有越过用户授权的边界。
  • 没有对无关文件或外部系统产生修改。
  • 对高风险操作有确认或保护。
  • 成本与收益相称，不为小问题做大范围扫描或昂贵请求。
  • 在可恢复性上有基本考虑，比如修改前知道目标文件是什么。

“完成任务”不能抵消不必要的副作用。一个命令生成了正确结果，但顺手改了无关文件，仍然是不正确的调用。

返回结果是否被正确解释

很多 Tool 调用的错误不发生在调用时，而发生在解释结果时。

搜索没有结果，不等于事实不存在；接口返回空列表，可能是权限、分页、过滤条件或时间范围的问题；命令退出码为 0，也不表示业务验证通过；网页打开成功，也不表示页面内容加载完成。

评测时要看模型有没有区分这些层次：

  • 工具执行是否成功。
  • 返回数据是否覆盖了问题范围。
  • 结果是否需要二次验证。
  • 结果中的不确定性有没有被保留。
  • 后续回答是否忠实反映了工具输出。

如果模型把部分证据说成完整证据，把推断说成事实，把失败调用包装成确定结论，这次调用链路就是错的。

是否把结果用于下一步

工具不是表演动作。一次调用是否正确，还要看返回结果有没有进入后续推理。

如果模型调用了搜索工具，却没有引用搜索到的文件；运行了测试，却没有根据失败信息修改判断；打开了网页，却继续复述调用前的猜测，这些都说明工具结果没有真正被使用。

好的调用会改变模型的状态：缩小范围、确认假设、推翻猜测、生成下一步操作，或让最终回答更具体。评测时可以问一句：删除这次 Tool 调用，最终答案会不会几乎不变？如果不会变，它可能只是无效调用。

失败处理也是正确性的一部分

工具失败并不自动意味着调用错误。网络断开、权限不足、文件不存在、服务未启动，都可能是环境问题。关键在于失败后怎么处理。

合理的失败处理包括：

  • 说明失败发生在哪一步。
  • 判断失败是参数问题、权限问题、环境问题，还是工具本身问题。
  • 在安全范围内尝试替代路径。
  • 不把失败结果当成事实结论。
  • 必要时向用户请求授权或补充信息。

不合理的失败处理包括反复执行同一个无效调用、静默跳过关键验证、编造结果，或者在未确认风险时升级到有副作用的操作。

一个实用评分表

可以用 10 分制快速评估一次 Tool 调用：

维度 低分表现 高分表现
必要性 不需要工具却调用，或需要工具却没调用 调用正好补足模型无法可靠知道的信息
工具选择 工具与任务不匹配 工具直接对应任务目标
参数质量 对象、范围、格式或约束错误 参数精确、完整、不过度
时机顺序 基于错误前提调用，或调用顺序颠倒 在下结论前验证关键事实
副作用控制 越权、误改、成本过高 权限、范围和风险都受控
结果解释 把空结果、部分结果或失败结果误读成事实 区分事实、推断和不确定性
后续使用 调了工具但没有影响答案 工具结果明确推动下一步
失败处理 静默失败、重复失败或编造结果 诊断原因，尝试安全替代路径

如果要做更正式的评测，可以给每个维度 0 到 2 分：0 表示明显错误，1 表示可接受但有缺口，2 表示可靠。总分 16 分里，低于 10 分通常需要人工复核；低于 8 分，基本不能算一次正确调用。

最终判断

一次 Tool 调用正确，不等于它成功返回；成功返回，也不等于任务完成。

更稳的判断标准是：它是否减少了不确定性，是否保持在用户授权和任务范围内，是否让后续答案更接近事实。如果一次调用满足这些条件，即使中途遇到失败并诚实处理，也可以算正确。反过来，如果它只是制造了一个看起来可靠的结果，却没有服务于真实问题，那就只是一次漂亮但错误的调用。
