Agent 跑飞了：如何定位和兜底

发表于 2026-08-10 更新于 2026-08-17 分类于 人工智能
从止损、定位、预算、权限和复盘五个角度，整理智能体偏离任务后的排查与兜底方法。

Agent 跑飞了：如何定位和兜底

Agent 跑飞，通常不是模型突然“失控”，而是系统允许一个不够可靠的决策器，在反馈不足、边界模糊的情况下连续行动。

它可能反复调用同一个工具，不断偏离原始任务，也可能修改了不该碰的文件、生成大量无用内容，甚至把一次小错误传播到后续几十个步骤。处理这类问题，不能只靠改提示词。真正有效的方法是：先限制损失，再保存现场，定位第一次偏离，最后把约束下沉到执行系统。

一、什么叫 Agent 跑飞

“跑飞”不是一个精确的技术术语。工程上，它通常指 Agent 的行动已经不再稳定地服务于用户目标，却仍在继续消耗资源或改变外部状态。

常见表现可以分成五类。

1. 目标漂移

用户只要求修复一个接口，Agent 却开始重构整个模块；要求整理文档，它却自行改变产品设计。每一步单独看似乎有理由，连起来却偏离了任务。

2. 循环调用

Agent 反复搜索同一批文件、重试同一个失败命令，或者在“修改、测试、撤回、再修改”之间循环。它没有形成新信息，却持续消耗时间和 token。

3. 错误扩散

一次错误判断被写进计划或记忆，后续步骤都把它当成事实。例如 Agent 误判数据库字段含义，随后同时修改接口、前端和测试，造成更大的返工面。

4. 权限越界

Agent 修改任务范围外的文件、访问不相关的数据、对外发送内容，或者执行删除、发布、付款等高风险操作。

5. 资源失控

任务没有明显进展，但模型调用次数、工具调用次数、运行时间和费用持续上升。系统最后可能完成了任务，也可能没有；无论哪种情况，执行过程都不可接受。

二、事故发生时，先止损

看到 Agent 行为异常后，第一件事不是继续追问它“为什么这么做”，而是阻止它继续改变环境。

建议按以下顺序处理：

  1. 暂停新的模型和工具调用，保留当前运行状态。
  2. 撤销尚未执行的异步任务，包括队列任务、定时器和后台子 Agent。
  3. 冻结写权限，把系统切换到只读或审批模式。
  4. 隔离外部副作用，暂停发布、通知、转账、删除等动作。
  5. 保存现场，不要急着清理日志、临时文件和中间状态。

如果工具调用无法中断，至少要在执行层设置超时和租约。租约到期后，Agent 即使仍想继续，也无法获得新的执行权限。

止损时要区分“可逆”和“不可逆”操作。读取文件、搜索代码通常风险较低；提交代码、修改线上数据、向客户发消息则需要更严格的控制。对不可逆动作，系统不应等到发现跑飞后才拦截，而应提前要求人工确认。

三、定位问题，不要从最后一条错误开始

Agent 最后表现出来的异常，往往只是前面某次偏离的结果。定位时应该寻找第一次失去依据的决策。

一条完整执行轨迹至少需要记录：

  • 用户原始目标和系统指令；
  • 每轮模型输入、输出和使用的模型版本；
  • Agent 当时的计划、状态和剩余预算；
  • 每次工具调用的参数、结果、耗时与错误；
  • 检索到的文档、记忆及其来源；
  • 文件、数据库和外部系统的变更摘要；
  • 审批、重试、超时和异常信息。

只记录最终回答远远不够。没有中间轨迹，就很难判断是模型推理错误、上下文缺失、工具返回异常，还是编排器把旧状态重复送进了下一轮。

四、沿着执行链寻找第一个偏离点

排查时，可以按六个问题向前追溯。

1. Agent 当时理解的目标是什么

比较用户原始要求、系统目标和 Agent 自己生成的计划。如果计划已经扩大了任务范围，问题出在目标解析或规划阶段。

目标最好写成可以检查的完成条件，例如“只修改 auth 模块，使三个指定测试通过”，而不是“优化登录体验”。后者给 Agent 留下了太大的解释空间。

2. 它依据了哪些信息

检查上下文是否缺页、过期或互相矛盾。还要确认检索系统有没有返回貌似相关、实际属于另一个项目的资料。

如果一条结论没有来源，或者来源无法支持结论，就应该把这里标记为候选偏离点。

3. 工具是否如实返回结果

工具层经常制造假象：命令退出码异常但文件其实已经生成，接口超时但服务端已经完成写入，日志被截断后看起来像执行成功。Agent 若只依据一句摘要继续行动，很容易重复执行或得出错误结论。

工具返回应包含明确的状态、结构化结果和副作用标识。对写操作，还要返回幂等键、变更对象和可验证的最终状态。

4. 状态有没有被错误继承

多轮执行中，旧计划、失败步骤、缓存结果或历史记忆可能继续污染后续判断。检查状态机是否允许失败步骤被当作已完成，也要检查重试时是否重复使用了过期上下文。

5. 是否出现了“没有进展的重试”

连续两次行动使用相同参数、得到相同错误，又没有引入新证据，第三次重试通常不会带来变化。此时系统应该停止自动循环，转而换方案或请求人工介入。

6. 哪个保护条件本应阻止它

如果 Agent 已经修改了任务范围外的文件，除了追究模型为什么这样做，还要追问：为什么执行层允许它这样做？定位的终点不是找到一句糟糕的模型输出，而是找到缺失或失效的控制措施。

五、用四类预算限制损失

最简单有效的兜底，是给一次任务设置明确预算。

步数预算

限制模型决策轮数、工具调用总数和同类工具的连续调用次数。达到阈值后，Agent 必须总结进展并停止，不能自行追加预算。

时间预算

为整个任务和单次工具调用分别设置超时。长任务可以使用租约续期：只有检测到有效进展时，系统才延长执行时间。

成本预算

限制 token、模型费用、搜索请求和其他计费资源。预算应由编排器计算，不能依赖 Agent 自己估算。

影响范围预算

限制可读取的数据域、可修改的文件数量、单次数据库变更行数和外部通知人数。例如任务只涉及一个模块，就把写入范围限定在该目录，而不是开放整个仓库。

预算耗尽不等于任务失败。系统可以输出已完成步骤、未完成原因、现场状态和建议的下一步，让人工决定是否继续。

六、把权限控制放在模型之外

提示词中的“不要删除文件”只是一条软约束。真正的权限边界必须由工具和运行环境执行。

可以把工具分成三个等级：

  • 自动允许：只读查询、静态分析、无副作用计算；
  • 受限允许：在沙箱内修改文件、运行测试、写入临时环境；
  • 人工确认：删除数据、发布上线、发送消息、修改权限和产生费用的操作。

每个工具还应校验具体参数。允许“修改文件”不代表可以修改任意路径；允许“执行 SQL”也不代表可以运行没有行数限制的 DELETE。

对于高风险操作，可以采用“计划与执行分离”：Agent 只生成结构化操作计划，独立校验器检查范围、权限和前置条件，通过后才由执行器完成动作。

七、让每个写操作都可恢复

兜底不仅是阻止错误，也要让已经发生的错误能够恢复。

代码修改应在独立分支或临时工作区中进行；数据库更新应使用事务、版本号或变更日志；外部请求应携带幂等键，防止超时重试造成重复扣款或重复通知。

对于无法真正撤销的操作，例如邮件已经发送，系统应采用两阶段流程：先生成草稿和收件人列表，确认后再发送。所谓回滚，不能只写在设计文档里，必须通过演练确认它真的可用。

八、建立“有进展”判定

许多循环并非因为 Agent 不知道停止，而是系统没有定义什么叫进展。

可以为任务设置可测量的进展信号：

  • 新发现了与目标相关的信息；
  • 某个未完成条件已经满足；
  • 测试失败数量减少；
  • 不确定性得到澄清；
  • 产生了可验证的环境变化。

如果连续若干步没有任何进展，系统应触发熔断。熔断后的输出需要说明：尝试了什么、为什么没有推进、当前有哪些证据、恢复执行还缺什么。

还要防止 Agent 用“改写计划”伪装进展。计划文本发生变化，不代表任务状态发生变化。

九、何时必须交给人

人工介入不应被视为失败。有些条件本来就不适合自动决策：

  • 用户目标存在两种代价明显不同的解释；
  • 关键事实互相矛盾，且无法从可靠来源验证；
  • 即将执行不可逆或高影响操作；
  • 自动重试已达到上限；
  • 任务需要扩大权限、预算或影响范围；
  • 监控检测到异常成本、越权倾向或持续无进展。

交接信息要足够简洁。不要把几万行日志直接扔给审批人，而应提供原始目标、当前计划、已完成事项、待确认决策、风险和相关证据链接。

十、事故后怎样复盘

复盘不能停在“模型不够聪明”或“提示词写得不好”。这些结论无法直接转化为稳定的防护。

一次有效复盘至少回答四个问题：

  1. 第一个无依据或越界的动作是什么？
  2. 当时有哪些信号能够提前发现它？
  3. 哪个系统约束本应阻止它，却没有生效？
  4. 如何用自动测试复现这次事故？

修复措施也应分层。提示词可以澄清目标；检索层要改善来源和隔离；编排器要增加状态检查与预算；执行层要收紧权限并支持回滚。只修改其中一层，类似事故往往还会换一种形式出现。

十一、一个最小可用的防跑飞方案

如果系统还处于早期阶段，可以先实现以下组合：

  1. 每个任务都有明确目标、允许范围和完成条件。
  2. 保存模型、工具、检索和状态变化的完整执行轨迹。
  3. 设置最大步数、总时长、费用和写入范围。
  4. 连续两次相同失败后停止自动重试。
  5. 所有高风险动作都要求人工确认。
  6. 写操作使用沙箱、事务、幂等键或版本控制。
  7. 结束时验证结果，而不是相信 Agent 自己宣布“已完成”。

这套方案不复杂，却能挡住大部分常见事故。等系统积累了真实运行数据，再增加异常检测、自动重排、策略模型和更细的风险评分。

结语

Agent 跑飞很少由单个原因造成。模糊目标、错误上下文、不可靠工具、宽松权限和无限重试叠加在一起，才让一次普通误判演变成事故。

定位时，寻找第一次失去依据的决策；兜底时，把限制放到模型无法绕过的执行层。一个值得信任的 Agent，不是从不犯错，而是错误能够被及时发现，损失有上限，过程可追溯，结果可恢复。
