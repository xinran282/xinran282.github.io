LangChain 介绍：从模型调用到 Agent 应用

发表于 2026-08-18 分类于 人工智能
介绍 LangChain 的定位、核心组件、RAG 和 Agent 用法，以及它与模型 SDK、LangGraph 和 Harness 的关系。

LangChain 介绍：从模型调用到 Agent 应用

调用一次大语言模型并不难。真正复杂的是把模型接入文档、数据库、搜索、代码执行器和业务 API，再让它在多步骤任务中保持上下文、处理错误并验证结果。

LangChain 就是为这类应用提供的一套开发框架。它不是 GPT 或 Claude 这样的模型，也不是一个开箱即用的个人助手。更准确地说，LangChain 提供了连接模型、数据、工具和流程的组件，帮助开发者构建聊天应用、RAG 系统和 Agent。

可以把 LangChain 放在三层结构里理解：

模型负责理解和生成内容。LangChain 负责把模型和应用能力连接起来。运行层则负责让整个系统在真实环境中可控地运行。

因此，LangChain 更像一个 LLM 应用开发工具箱，而不是一个具体业务应用。

它解决什么问题

统一模型调用方式

不同模型供应商的接口、消息格式和工具调用参数并不完全相同。LangChain 为常见模型提供统一的调用抽象，让应用代码不必把所有逻辑都绑定在某一家模型服务上。

这不意味着切换模型完全没有成本。模型的上下文长度、工具调用能力、结构化输出和价格仍然不同，抽象层只能减少接口差异，不能消除能力差异。

组织 Prompt 和消息

Prompt 模板、系统指令、用户输入、历史消息和检索内容经常需要组合。把这些内容散落在字符串拼接里，后续很难维护和测试。

LangChain 提供消息和 Prompt 模板相关组件，让输入结构更清楚，也更容易把模板作为独立配置进行测试。

连接外部数据

模型本身不知道企业内部文档、最新订单或当前代码。LangChain 可以把文档加载、切分、Embedding、向量检索和模型调用组织成一条 RAG 流程。

连接工具

搜索、数据库、文件系统、代码执行器和业务 API 都可以包装成工具，让 Agent 根据任务选择调用。工具的执行仍然需要由应用侧负责权限校验和副作用控制。

编排多步骤流程

一个请求可能要经历检索、判断、调用接口、整理结果和验证。LangChain 的链式组合和 Agent 组件可以帮助开发者表达这些步骤。

LangChain 的核心概念

Model

Model 是对聊天模型或文本模型的调用封装。应用通过它发送消息，得到模型返回的文本、结构化结果或工具调用请求。

模型只负责提出结果或行动建议。它不会因为被 LangChain 包装，就自动获得访问数据库和执行命令的权限。

Prompt 和 Message

Prompt 用于组织输入模板，Message 则表示系统消息、用户消息、模型消息和工具结果。对于多轮对话和 Agent 循环，明确区分这些消息很重要。

Output Parser

模型输出通常是文本，但应用可能需要 JSON、列表、分类结果或固定字段。Output Parser 可以帮助应用把输出转换成预期结构，并在格式不正确时触发修复或报错。

解析器不能替代业务校验。JSON 格式正确，不代表字段的值合法，也不代表模型完成了用户要求。

Retriever

Retriever 负责根据问题找到相关内容。它可以连接向量数据库、关键词搜索、数据库或自定义检索服务。

Retriever 只负责“找什么”，不负责最终答案是否正确。RAG 系统还需要检查召回内容的权限、来源、时间和覆盖范围。

Tool

Tool 是 Agent 可以调用的外部能力。一个工具通常包含名称、描述、输入参数、返回结构和执行函数。

工具描述会影响模型选择。get_order_status 比 query_data 更明确；参数描述写清楚类型和范围，也比只写“订单编号”更容易减少错误调用。

LangChain 如何用于 RAG

一个典型的 RAG 流程可以拆成两部分。

离线阶段

  1. 加载 PDF、Markdown、网页或数据库内容。
  2. 把长文档切成适合检索的片段。
  3. 为片段生成 Embedding。
  4. 将向量和原文元数据保存到向量数据库。

在线阶段

  1. 接收用户问题。
  2. 检索相关文档片段。
  3. 把片段、来源和问题放入 Prompt。
  4. 调用模型生成回答。
  5. 返回答案和引用，或在证据不足时说明无法确认。

LangChain 可以串起这些组件，但检索质量仍然取决于切分策略、Embedding、召回参数、权限过滤和文档更新机制。用了 LangChain，不代表 RAG 自动变准。

LangChain 和 Agent

如果流程是固定的，例如“提取文本 -> 调用模型 -> 解析 JSON”，使用 Chain 往往足够。

如果下一步取决于模型对当前结果的判断，例如“先查订单，发现异常再查物流，最后决定是否转人工”，就可以考虑 Agent。

Agent 适合处理：

  • 需要多个工具协同的任务。
  • 执行路径不能完全预先写死的任务。
  • 需要根据工具结果动态调整的任务。

Agent 不适合替代所有流程。固定流程用状态机或普通函数通常更便宜、更容易测试；把简单的字符串转换也交给 Agent，只会增加不必要的不确定性。

LangChain 和 LangGraph 的关系

LangChain 更像组件和应用开发框架，适合组织模型、Prompt、Retriever、Tool 和简单 Agent。

LangGraph 更关注有状态的 Agent 工作流，例如节点、边、循环、分支、检查点、暂停和恢复。当任务需要明确控制执行图，或者需要长时间运行和人工介入时，LangGraph 更合适。

二者可以一起使用：LangChain 提供模型和工具组件，LangGraph 负责把它们编排成有状态的执行流程。

LangChain 和 Harness 的关系

LangChain 可以帮助构建 Harness，但它本身不等于完整 Harness。

LangChain 解决“如何把模型应用搭出来”。Harness 还要解决“如何让这个应用在受控环境中长期运行”。

使用 LangChain 时要注意什么

抽象层会带来额外复杂度

简单调用模型时，直接使用官方 SDK 可能更容易理解。引入 LangChain 后，需要理解它的消息、Runnable、工具和回调抽象。项目规模还没有达到需要这些能力时，框架反而可能增加排查成本。

版本变化需要锁定

LLM 生态变化很快。模型集成、Agent API 和包结构可能调整，项目应锁定依赖版本，保留最小可运行示例，并为关键流程写回归测试。

不要把安全交给 Prompt

Prompt 可以告诉模型“不要访问敏感数据”，但它不能代替服务端权限。文件路径、数据库字段、网络地址和写操作都需要在工具执行层再次校验。

记录每一步行为

Agent 出错时，只看最终答案很难定位原因。至少应记录模型请求、工具名称、参数摘要、返回状态、耗时、重试次数和最终结果，并对敏感内容做脱敏。

评估成本和延迟

Agent 可能多次调用模型和工具。评测时除了质量，还要记录 Token、延迟、工具次数、失败率和人工接管比例。一次回答更好，不代表整个系统更适合生产。

什么时候适合使用 LangChain

LangChain 比较适合：

  • 需要同时连接模型、工具和外部数据。
  • 需要搭建 RAG 或 Agent 原型。
  • 需要统一多个模型供应商的调用方式。
  • 需要对 Prompt、工具和执行链进行组合和追踪。
  • 需要把实验代码逐步发展成完整应用。

以下情况可以先不用：

  • 只有一次简单模型调用。
  • 应用只需要少量固定 Prompt。
  • 团队还没有确定是否需要 Agent 或 RAG。
  • 引入框架的抽象成本高于它带来的收益。

最后

LangChain 是构建 LLM 应用的框架和组件库。它把模型、Prompt、检索器、工具和 Agent 流程连接起来，但不会自动替你解决权限、状态、监控和业务正确性。

理解它的最好方式，不是把它看成一个“会做事的个人助手”，而是看成一套搭建助手的开发工具。模型负责理解和生成，LangChain 负责组织应用逻辑，执行器和 Harness 负责让整个系统在真实环境中可控地工作。
