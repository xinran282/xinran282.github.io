让 AI Agent 连续做几个小时的项目，难点在于每次换一个上下文窗口，它都要重新弄清楚项目状态。上一轮改了什么、哪些功能真的能用、还有什么没做，如果没有留下可靠记录，下一轮就得重新调查，甚至把半成品当成已完成的项目。

Anthropic 在《Effective harnesses for long-running agents》中给出的办法，是把跨会话工作组织成可交接的开发过程：第一轮建立环境和功能清单，后续每轮只推进一个功能，完成验证后留下代码记录和进度说明。

这篇文章发布于 2025 年 11 月 26 日，作者为 Justin Young。本文按问题、方案和执行过程重新组织原文，并在实现建议处注明补充内容。原文主要讨论全栈 Web 应用开发，其结论需要放在这一实践范围内理解。

上下文压缩之后，为什么还会失去进度

原文把长期运行的 Agent 比作轮班工作的工程师：新一班接手时，如果不知道上一班做了什么，即使有足够的能力，也得花时间恢复现场。

上下文压缩可以帮助会话继续运行，但压缩后的信息未必足够清楚。开发者只给出“做一个类似 claude.ai 的应用”这样的高层要求，然后让模型跨多个窗口循环执行，仍然容易出现两种失败。

第一种是一次做得太多。模型试图在一轮里实现整个应用，做到一半上下文就不够了。下一轮面对未完成的代码，又缺少明确说明，只能猜测设计意图，先花时间把基本功能修回来。

第二种是过早宣布完成。项目已经有页面、有几个功能，新会话检查后觉得“差不多做好了”，却没有系统核对原始需求中尚未实现的部分。

这两种失败指向同一个缺口：项目需要一套可持续读取的状态记录。它必须让后续会话分清“目标是什么”“当前代码是什么状态”和“哪些结果已经验证”。聊天摘要可以提供线索，但不能独自承担这些职责。

Harness 要负责哪些事情

这里的 harness 可以理解为模型周围的执行与管理机制，包括工具、上下文管理、环境启动方式，以及每轮工作的约束。它决定模型每次接手时能得到哪些信息，也决定本轮结束前需要留下什么。

原文提出了两类角色：

角色运行阶段主要职责
初始化 Agent第一次会话建立环境、功能清单、进度文件和初始 Git 提交
编码 Agent后续会话恢复现场、增量实现、验证结果、更新交接记录

原文脚注特别说明，这里的两个 Agent 只是采用不同的初始用户提示词；系统提示词、工具集合和整体 harness 都相同。这套方案不要求两个模型并行工作，也没有证明多智能体架构更好。

它首先解决的是职责安排：初始化阶段把后续工作的基础准备好，开发阶段遵守一套稳定的接手与交接规则。

第一轮先把验收依据写出来

高层需求通常不足以指导连续多轮开发。“做一个聊天应用”没有清楚说明什么才算完成，模型也就容易根据已经出现的界面判断进度。

原文让初始化 Agent 把需求展开成结构化的功能清单。在复刻 claude.ai 的例子中，清单包含两百多项功能，每项都有可观察的操作步骤，初始状态全部标为未通过。

下面保留原文示例的结构，将描述改写为中文：

{
  "category": "functional",
  "description": "点击新建聊天按钮后创建一个新会话",
  "steps": [
    "进入主界面",
    "点击新建聊天按钮",
    "确认创建了新会话",
    "确认聊天区域显示欢迎状态",
    "确认侧栏出现新会话"
  ],
  "passes": false
}

这里的 passes: false 表示尚未通过验证，不能简单等同于“没有写代码”。即使已经实现，如果没有完成规定的检查，也不能据此把状态改成通过。

清单还承担了防止任务缩水的作用。原文要求后续编码 Agent 只能更改 passes 状态，不能删除或修改验收条目，避免通过降低要求制造“全部完成”的结果。

团队最终采用 JSON，是因为他们在实验中发现，相比 Markdown，模型更少不恰当地修改或覆盖 JSON 文件。这是一次实现经验，不代表 JSON 自带防篡改能力。若要在工程上强制执行，可以额外校验清单结构及允许修改的字段；这是对原文方案的补充。

两百多项也不是通用配额。清单的粒度应当让一轮工作能够实现并验证一个具体行为。项目需要多少条，要由需求决定。

用几份持久文件降低接手成本

原文让初始化 Agent 准备启动脚本、进度文件和初始 Git 提交，再配合功能清单，构成后续会话的接手材料。

材料回答的问题
功能清单需要做什么，哪些功能尚未通过验证？
init.sh如何启动开发环境？
claude-progress.txt最近完成了什么，下一轮需要注意什么？
Git 历史代码具体发生了哪些变化，有哪些可追踪的工作状态？

这些材料各有用途。提交历史能展示差异，但未必能解释为什么暂停某项工作；进度说明能交代意图，却不能证明代码真的发生了对应变化。后续会话需要结合两者，再通过运行程序确认当前状态。

init.sh 的作用是把反复摸索启动方法的过程固定下来。在其他技术环境中，也可以采用等效的启动命令或脚本。重要的是让每轮会话能可靠地复现环境，而不是要求所有项目使用相同文件名。

每轮只推进一个功能，并留在可接手的状态

环境准备好以后，原文要求编码 Agent 一次只处理一个功能。这能限制模型试图一口气完成整个应用的倾向，也让本轮的目标和验收范围更清楚。

“一个功能”可以涉及多个文件。例如，新建聊天可能同时需要页面交互、状态更新和后端接口。划分依据是一个可验证的用户行为，而不是文件数量。

本轮结束时，还应让代码处于原文所说的“干净状态”：没有明显的重大缺陷，代码有条理、必要说明齐全，下一位开发者能够开始新功能，无须先清理无关的混乱。

这个要求比“工作区里没有未提交文件”更严格。把半成品提交到 Git，并不自动说明它已经适合交接。

原文采用的做法是：完成增量工作后，以清楚的提交信息记录代码，再向进度文件写入摘要。Git 提供可追踪的版本，也帮助 Agent 在出错时恢复工作状态。

进度摘要可以写明本轮完成的功能、使用的验证方式、验证结果和已知问题。对于因外部依赖而无法完成验证的情况，应如实保留未验证状态。这些字段是基于原文交接目标的实现建议。

写完代码，还需要从用户路径验证

Anthropic 观察到的另一类失败，是模型没有充分测试，就把功能标为完成。有时模型已经运行单元测试，或用 curl 请求了开发服务器，但功能从用户界面走一遍仍然不可用。

对于 Web 应用，接口成功只是部分证据。例如，请求能返回数据，页面仍可能没有正确显示；页面能显示内容，刷新后状态却可能丢失。

原文明确要求模型使用浏览器自动化工具，按真实用户的操作方式做端到端验证。团队报告说，这明显改善了表现，帮助模型发现仅靠代码检查难以察觉的问题。

因此，完成状态应当与验收步骤对应。以新建聊天为例，需要实际打开页面、点击按钮、检查聊天区域和侧栏，确认所描述的行为发生后，才能把该条目标为通过。

浏览器自动化也有覆盖边界。原文提到，当时使用的 Puppeteer MCP 无法让 Claude 看见浏览器原生 alert 弹窗，依赖这些弹窗的功能更容易出现问题。这个例子提醒我们，测试工具没有报告失败，未必代表它观察到了所有相关行为。

新会话先恢复现场，再开始开发

原文给出的接手过程包含一些很基础的动作，却能减少重复探索和错误叠加：

  1. 1. 确认当前工作目录。
  2. 2. 阅读进度文件和近期 Git 提交，了解上轮工作。
  3. 3. 阅读功能清单，确定尚未完成的高优先级功能。
  4. 4. 查看启动脚本，运行开发环境。
  5. 5. 先检查已有的基础用户流程。
  6. 6. 确认基础功能可用后，再实现选定的新功能。

在原文的聊天应用示例里，基础检查包括新建聊天、发送消息并收到回复。它的作用是确认这轮接手的应用仍能正常工作。

如果基础流程已经损坏，就应该先调查并修复。直接在损坏的环境上追加功能，会让旧故障与新改动混在一起，增加定位难度。

每轮开始时的检查和结束时的记录形成了连续交接：上一轮写下的进度，成为下一轮调查的起点；下一轮再用实际运行结果核实它，而不是无条件相信记录。

四类失败，对应四种约束

失败表现初始化阶段的准备后续会话的执行要求
做了部分功能就宣布项目完成从需求建立完整功能清单读取清单，选择一项未完成的功能
留下有缺陷的环境或不明进度建立 Git 仓库和进度文件接手时检查基础功能，结束时提交并更新进度
未充分测试就标为完成写出可检查的功能步骤认真验证后再更改通过状态
每轮重新寻找启动方法建立启动脚本接手时阅读并使用脚本

这套设计把“继续完成任务”转成了具体行动。模型不必每次重新发明工作方式，也更难只凭表面进展判断项目已经结束。

哪些结论仍需要验证

原文展示的是一套可行的长任务 harness 实践，主要围绕全栈 Web 应用。它没有给出足以比较所有替代架构的完整定量结果，也没有证明这套流程适用于所有长期任务。

作者留下的一个开放问题是：跨上下文使用一个通用编码 Agent，与让测试、质量检查、代码清理等专门 Agent 分工，哪种方式更有效？文章提出了研究方向，没有给出定论。

科学研究、金融建模等任务是否同样受益，也需要进一步检验。它们的验证依据不同：Web 应用可以检查按钮、接口和页面状态，研究任务则可能需要检查证据来源、实验记录与推导是否成立。

从这篇文章中可以直接借鉴的是交接方式：把验收条件、运行方法、已验证进度和代码变化保存在工作环境里，让新会话能够据此恢复任务。至于具体测试、角色分工和功能粒度，仍应根据项目调整。

如果准备在自己的项目中试用，可以先观察后续会话是否减少了重复调查，是否更少误报完成，以及基础功能是否保持可用。这些是基于原文问题归纳出的评估方向；它们比单纯记录 Agent 连续运行了多久，更能说明系统是否在持续取得进展。
