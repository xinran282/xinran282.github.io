LangSmith 是 LangChain 团队提供的 AI 应用开发与运维平台。它记录模型和工具如何执行，帮助开发者定位错误、评估不同版本，并管理提示词与上下文。平台还提供智能体部署能力；新推出的 Fine-Tuning 则把经过筛选的执行轨迹接入模型微调流程。

对刚开始做 AI 应用的人，最值得先用的是追踪和评估：一次回答为什么错了？改完之后，是否真的更好？这两个问题比“换个更强的模型试试”更具体，也更容易验证。

为什么 AI 应用需要这样的工具

假设你做了一个客服智能体。用户问：“这笔订单还能退货吗？”系统需要检索退货政策、查询订单，再生成回答。

如果最终回答错了，只看输入和输出，很难判断问题出在哪里：检索到了旧政策，订单工具查错了编号，模型误读了返回结果，还是提示词根本没要求检查时间限制？

普通日志也能记录这些信息，但你需要自己组织调用关系、关联多轮对话，再把错误样本整理成测试数据。LangSmith 提供了围绕这些工作的一套工具。它能帮助你找到问题发生的环节，却不会自动保证回答正确。

LangSmith、LangChain 和 LangGraph 分别做什么

这三个名字经常一起出现，但用途不同。

名称主要用途在应用中的位置
LangChain开源框架，提供模型、工具等组件的集成与智能体开发接口编写应用逻辑
LangGraph开源智能体编排框架，处理状态、执行流程和持久化执行等问题组织复杂工作流
LangSmith追踪、评估、提示词与上下文管理，以及部署等平台能力检查、比较和运维应用

LangSmith 的可观测性不要求应用使用 LangChain 或 LangGraph。官方文档列出了 OpenAI、Anthropic、CrewAI、Vercel AI SDK、Pydantic AI 等集成，也支持通过 SDK 给自定义函数添加追踪。

因此，即使你用模型服务商的原生 SDK 写应用，也可以接入 LangSmith。反过来，使用 LangChain 或 LangGraph，也不意味着必须使用 LangSmith。

追踪：看清一次请求发生了什么

LangSmith 中几个常见概念需要分开理解。

一次运行单元通常称为 run，可以是一段应用函数、一次模型调用或一次工具调用。相关运行组成一次端到端的 trace，展示一项请求的执行过程。thread 用来关联多轮交互，而 trajectory 按顺序组织消息、工具调用与工具结果，更适合查看智能体每一轮实际经历了什么。

前面的客服例子，可以得到类似下面的执行结构。这是说明概念的示意，并非真实运行记录。

客服请求
  检索退货政策
  查询订单状态
  调用模型生成答复

打开对应的追踪记录，可以检查各步骤的输入、输出、耗时和错误，以及模型调用的消息内容。Token 用量及成本信息是否完整，还取决于集成上报的数据和价格配置。

调试时，可以先找第一个偏离预期的步骤。如果检索结果已经错了，应先修检索；如果工具返回正确而回答错误，再检查模型收到的上下文和指令。这样能减少无依据地修改提示词。

记录本身也有边界。没有接入追踪的函数或外部系统，不会因为安装了 SDK 就自动变得可见。接入时应确认：你真正关心的检索、工具和模型调用，是否都出现在记录里。

评估：证明修改是否有效

追踪解释一次执行，评估比较一批执行。

LangSmith 的离线评估通常围绕数据集、评估器和实验展开。数据集保存测试输入，也可以包含参考输出；评估器按既定标准打分；实验记录某个应用版本在这批数据上的表现。

例如，客服智能体可以检查：

  • • 是否查询了正确订单。
  • • 是否依据适用的退货政策回答。
  • • 是否在缺少依据时避免编造结论。
  • • 是否满足响应时间和成本要求。

不同标准需要不同评估方法。订单编号、输出格式这类明确规则，可以用代码检查；政策解释是否准确，可能需要人工审查或模型评判。LangSmith 支持人工、代码、LLM-as-judge 和成对比较等方式，但评分标准仍然需要你定义。

模型评判也会出错。比较重要版本前，最好用人工标注样本检查评判器是否符合业务要求。一次总分上涨，可能掩盖某类问题的退步；查看具体失败样本，往往比只看平均分更有用。

离线评估适合上线前比较版本。在线评估则对生产环境的真实交互进行检查，通常没有逐条准备好的参考答案，可以采用格式规则、安全检查或无需参考答案的模型评判，并通过筛选和采样控制成本。

一个实用做法是：把线上发现的错误整理进回归测试集。以后每次改提示词、工具或模型，都重新跑这些样本，检查旧问题有没有回来。用于调试的样本与最终测试集应适当分开，避免只把应用调到擅长已见过的题目。

提示词管理与部署，是另外两类工作

提示词和检索上下文往往比代码改得更频繁。LangSmith 的 Prompt & Context Hub 可以保存提示词版本，以及包含指令和工具等内容的上下文包。Playground 用来测试提示词和模型配置。

版本管理的好处是能追溯：某次实验用了哪个提示词，线上应用拉取的是哪个版本，修改是谁做的。应用需要显式接入拉取逻辑；在平台里修改提示词，不会自动改变所有运行中的程序。

LangSmith Deployment 则负责智能体的生产运行，包括持久化执行、流式响应和扩展等能力。官方提供 LangGraph 等框架的部署路径，以及其他框架的适配方式。

应用运行在哪里，与追踪数据存在哪里，是两个不同问题。你可以让应用继续运行在现有服务器上，只接入 LangSmith 的追踪和评估，而不迁移到它的部署服务。

Fine-Tuning：把优质轨迹用于训练

你刚才阅读的 LangSmith Fine-Tuning 发布文章，介绍了命令行工具 smithtune。发布文章将这一功能列为公开测试版，并说明当前支持监督微调（SFT）。

SFT 用表现良好的输入、输出示例更新模型权重，让模型学习这些行为。对于智能体，训练样本除了最终回答，还可能包含工具调用，以及作出该动作时的上下文。

这正是轨迹数据的用途。在长任务中，可用工具可能逐轮变化。只导出最终消息列表，可能无法准确还原模型当时看到了哪些工具和信息。LangSmith 的轨迹格式为这类训练保留每一轮的上下文。

按照发布文章，smithtune 的流程包括筛选轨迹、准备数据集、在 Fireworks 或 Baseten 上训练、通过 LangSmith 比较结果，再部署微调模型。CLI 的 deploy 步骤用于提供微调模型的推理服务，和前面提到的智能体应用部署不是同一件事。

微调不应是接入后的第一步。先检查工作流、工具定义和上下文是否合理；只有在任务反复出现、仍有稳定的行为错误，而且具备足够的优质示例时，才值得考虑 SFT。如果错误来自过期政策或失效接口，应先修数据和工具。

发布文章还提到，早期筛选不够严格的训练集曾让代码审查模型的 F1 分数下降。这个例子说明，保存了大量轨迹，不等于拥有大量适合训练的数据。文中的内部实验结果也不能直接推导为所有应用都能获得相同收益。

初次使用，先做一个小范围接入

建议先选一条容易出错、又能人工判断对错的业务流程，接入追踪，积累失败样本，再建立一个小型评估集。暂时不必把提示词管理、部署和微调全部用上。

官方快速入门使用以下环境变量启用追踪。下面是 PowerShell 写法，密钥只是占位符：

$env:LANGSMITH_TRACING = "true"
$env:LANGSMITH_API_KEY = "<your-langsmith-api-key>"
$env:LANGSMITH_PROJECT = "customer-support-dev"

这些变量只是配置。应用还需要安装相应 SDK，并通过框架集成、模型客户端包装器或 traceable 包装函数产生追踪数据。LangSmith API Key 与模型服务商的 API Key 也不同，前者用于上传和管理追踪，后者用于调用模型。

如果账户所在区域不是默认区域，还应按官方文档设置对应的 LANGSMITH_ENDPOINT。完整接入步骤见 Tracing quickstart。

接入前，先检查输入、输出和工具结果里有没有个人信息、商业机密或凭证。需要脱敏的数据应在上报前处理。追踪存储、数据保留、评估模型调用和训练服务也可能分别产生费用，应按实际套餐与使用量核算。

对于只有几次手动调用的实验脚本，普通日志可能已经够用。当工具调用、多轮对话和版本迭代增多，你开始需要反复回答“哪里错了”和“是否修好了”，LangSmith 的追踪与评估才更容易体现价值。
