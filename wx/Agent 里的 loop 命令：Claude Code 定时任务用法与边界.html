提到 Agent 里的“lopp 命令”，这里按 loop 的笔误理解，并以 Claude Code 的 /loop 为例。不同 Agent 产品的命令并不通用。

/loop 可以让 Claude Code 在会话中反复执行一段提示词。 例如，每隔几分钟检查部署状态，发现部署完成后再通知你。它解决的是“过一会儿再检查”的问题；一轮任务能否做好，仍取决于提示词、工具权限和验证方法。

Agent 执行任务时，通常会反复经历“判断下一步、调用工具、读取结果、继续或结束”。这个过程常被称为 agent loop，是运行机制。

Claude Code 的 /loop 则是用户可以输入的命令入口。它安排后续执行：到下一次触发时，再让 Agent 处理指定提示词。每次执行内部，又可能包含多次工具调用。

可以把两者放在同一个例子里理解：

你让 Agent 检查部署。它先查询状态，再读日志，最后判断还在构建，这是一次任务内部的工作循环。你希望五分钟后再查一次，就可以使用 /loop。

因此，增加执行次数不会自动补足权限、提供缺失数据，或让没有验收标准的任务变得清晰。

最容易上手的写法

在 Claude Code 的会话输入框中输入：

/loop 5m 检查当前部署状态；只有状态变化、部署失败或部署完成时才通知我。

这里的 5m 是期望的执行间隔，后面是每次要执行的提示词。这是 Claude Code 中的斜杠命令，不是 PowerShell 或 Bash 命令。

官方文档支持 s、m、h、d，分别代表秒、分钟、小时和天。底层 cron 调度的粒度是分钟，因此秒数会向上取整到分钟。像 7m、90m 这样无法直接映射为规整 cron 步长的间隔，会调整到可表达的间隔；应查看 Claude 最终确认的时间安排和任务 ID。

这也意味着，/loop 适合轮询状态，不能当作精确到秒的计时器。文档还说明调度可能存在时间偏移。

不写间隔、不给提示词，会发生什么

当前官方文档区分以下用法：

输入执行方式
/loop 5m 检查部署状态按固定时间安排执行给定提示词
/loop 检查部署状态Claude 根据每轮观察结果，自行选择下一次等待时间
/loop 15m按固定时间安排执行默认维护提示词
/loop执行默认维护提示词，并动态选择等待时间

自适应模式会在每轮结束时选择一分钟到一小时的等待时间，并说明原因。例如，构建快结束时检查得勤一些，PR 没有新变化时等待更久。

默认维护提示词会优先继续对话中的未完成工作，再处理当前分支 PR 的审查意见、失败的 CI 或合并冲突；没有待办时，才做查找 bug、简化代码等清理。单独输入 /loop，因此可能比“重复检查某个状态”涵盖更多工作。

如果只想盯住一个部署或一条 PR，直接写出对象和检查范围更容易控制。

把循环提示词写成可执行的检查规则

“每五分钟看看项目”没有明确的检查对象。Agent 需要自行猜测重点，也很难判断什么时候可以结束。

一个实用提示词应交代检查对象、变化时的处理方式，以及终止条件。例如：

/loop 5m 检查 PR #123 的 CI 状态和新审查意见。状态没有变化时保持安静；出现新失败时报告失败任务和日志摘要。全部必需检查通过且没有待处理审查意见时，报告结果并取消这个循环。只做读取和报告。

这里的“取消这个循环”是任务要求。运行后仍应检查取消结果，确认定时任务确实从列表中移除。

如果希望它自动修复，可以另行明确允许修改的范围和需要运行的验证。例如，允许修改当前分支代码并运行相关测试，同时约定遇到外部服务故障时停止修改、报告证据。循环能继承会话的工具与权限，也会继承原来存在的限制。

对于持续修复任务，还可以加上具体的退出规则：同一种失败连续出现两轮，就汇报现有证据，等待进一步处理。这个规则是使用建议，可以减少没有新信息的重复尝试。

怎么查看和停止

可以直接对 Claude 说：

列出当前会话的所有定时任务，包含任务 ID 和执行安排。
取消刚才检查 PR #123 的循环。

底层的 CronCreate、CronList、CronDelete 分别负责创建、列出和删除任务。多个任务内容相似时，按任务 ID 取消更明确。

停止方式需要分情况。按当前文档，自适应循环在等待下一轮时可以按 Esc 停止；固定间隔循环应要求 Claude 取消任务。按下 Esc 或 Ctrl+C，不能据此认定固定间隔任务已删除。 取消后再查看任务列表，是更可靠的确认方法。

关闭窗口后还会继续吗

/loop 的执行依赖 Claude Code 会话进程。关闭终端、会话退出后，任务停止触发；将会话转到受支持的后台运行方式，则可以在没有终端窗口的情况下继续执行。

“恢复任务记录”和“持续在后台执行”也要区分：

  • • 使用 --resume 或 --continue 恢复时，尚未过期的 CronCreate 重复任务可以恢复，但不会补跑停机期间错过的次数。
  • • 自适应 /loop 不会随这种会话恢复自动重启，需要重新运行。
  • • 已经错过执行时间的一次性任务不会恢复。

会话忙于响应时，定时提示词会等待当前轮结束。错过多个执行点，也不会为每个执行点分别补跑。重复任务在创建七天后到期，最后执行一次后删除。

这些条件决定了它适合会话期间的部署检查、PR 跟进和临时提醒。需要长期按计划执行的工作，可以考虑官方提供的云端定时任务、Desktop 定时任务，或 GitHub Actions。

什么时候值得用

如果只是提醒一次，直接说“45 分钟后检查集成测试是否通过”，通常比建立重复循环更合适。

如果任务需要等待外部变化，例如 CI 完成、部署结束、PR 出现新评论，/loop 很方便。把提示词写成“检查什么、什么情况下通知、什么时候停止”，往往已经够用。

如果要让 Agent 连续推进一项开发任务，则还需要明确验收条件：哪些测试必须通过、哪些行为需要人工确认、遇到什么阻塞应停下来。/loop 负责安排下一次执行，验收条件负责判断工作是否完成。
