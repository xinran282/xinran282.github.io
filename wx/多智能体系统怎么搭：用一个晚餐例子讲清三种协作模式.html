搭建 AI 系统时，可以先让一个智能体配上合适的工具。只有当任务需要不同的专业分工、可以并行处理，或需要单独评估某个环节时，再考虑拆成多个智能体。

拆分会增加交接，也会增加等待和开销。是否值得，取决于这些分工能不能解决当前系统里的具体问题。

Kadharmoideen Fadurudeen 在《Building a Multi-Agent System: 3 Patterns, Explained Simply》中，用“今晚去哪里吃饭”解释了三种协作模式。下面沿用这个例子，再结合他开发天气助手 Stormwise 的经历，看看这些系统通常在哪里出错。

先判断：这顿晚餐需要几个智能体

用户说：“我在钦奈，晚饭吃什么？”

系统查询位置和天气，再搜索餐厅。雨天可以推荐热茶配当地炸点 vada 或 bajji；炎热的下午，可以考虑酪乳或椰子水。最后还要确认餐厅距离和营业情况。

作者最初的实现只用了一个模型，加上位置、天气和餐厅搜索三个工具，并限制最多执行多少步。这个方案已经能完成任务，他认为当时没有必要再拆分。

这里的智能体，是能调用工具、根据结果决定下一步的模型。多智能体系统则把工作交给多个职责更窄的智能体，让它们交换任务和结果。多个智能体也可以使用同一种底层模型。

对晚餐推荐而言，查询天气、生成菜品建议和寻找餐厅，确实可以分成不同职责。但“可以拆”还不足以说明“值得拆”。应当继续看：

  • • 天气与餐厅查询是否需要差别很大的指令或工具权限？
  • • 有没有相互独立的工作，可以同时执行以缩短等待？
  • • 是否需要单独测试某个环节，例如餐厅营业状态的判断？
  • • 拆分后，收益是否足以抵消额外调用和结果整合的成本？

如果连每个智能体负责什么都说不清，先改善单智能体的工具和输入，通常更容易找到问题。

流水线：顺序能提前写下来

流水线（Pipeline）让每个环节完成固定工作，把结果交给下一环节。

晚餐推荐可以按这个顺序执行：

查天气 → 推荐食物 → 搜索餐厅 → 核对营业状态 → 生成回复

天气环节返回“下雨，26℃”；食物环节据此推荐热饮和炸点；餐厅环节找出附近三家店；检查环节确认这些店还在营业，最后组织成回答。

这种模式适合事前就能列出检查清单的任务。每一步的输入和输出都比较明确，出现问题时，也容易定位是天气过期、推荐不合适，还是餐厅信息失效。

它的限制是路径固定。按照这里讨论的简单流水线，结果只向前传递。如果找到餐厅后才发现用户有饮食禁忌，需要重新生成食物建议，就得增加回退逻辑。类似分支越来越多时，应重新考虑流程结构。

也不必把每个步骤都做成智能体。核对时间戳、检查必填字段、筛选已关门的餐厅，往往可以直接用普通代码完成。这是沿着原文模式可以采用的实现方式。

调度者：分工种类清楚，具体安排临时决定

调度者模式（Orchestrator，也常称编排器与工作者）由一个主智能体理解请求、分派任务，再汇总结果。

它像餐厅里的主厨。天气、餐厅和食物建议各有助手，助手把结果交回主智能体；在本文讨论的结构里，助手之间不直接交谈。

同样是晚餐请求，有人只想知道附近有什么，有人要求素食、低预算，还要避开暴雨区域。需要哪些帮助、先查什么、查到哪里才够，可以由主智能体根据请求决定。

有独立输入的查询可以并行。例如，查询天气与搜索附近餐厅可以同时进行；如果食物建议依赖天气结果，就应该等天气返回后再执行。采用调度者，并不意味着所有工作都能同时开始。

这种模式适合“知道有哪些专业能力，但无法为所有请求预先写死分工”的场景。研究任务也常见类似结构：主智能体拆出不同调查方向，助手分别查资料，最后集中整合。

问题也集中在主智能体。它若误解了目标，助手可能各自完成了任务，却共同偏离用户需求。助手越多，主智能体需要检查和整合的内容也越多。

设计时，可以要求助手交回结果、依据和待确认条件。主智能体据此检查任务是否完成，避免直接采信一句“已完成”。

黑板：下一步取决于刚发现了什么

黑板模式（Blackboard）让多个智能体读写同一份共享状态。这里讨论的版本没有负责统一规划的主智能体，参与者根据黑板上的信息补充发现、提出质疑或继续调查。

在晚餐例子里，天气智能体写下“下雨，26℃”；食物智能体补充“可以考虑热茶和炸点”；餐厅智能体加入三家店；审查智能体发现其中一家快关门，于是其他智能体继续调整建议。

这适合无法事先排好所有步骤的任务。排查程序故障就是典型例子：一个智能体提出原因，另一个寻找日志证据，第三个指出反例。调查方向随着证据变化。

共享状态让探索更灵活，也让控制更困难。两个智能体可能不断推翻彼此的建议，或反复要求对方补充资料。每一步单独看都有理由，整个任务却没有进展。

共享黑板也不等于实现时完全没有调度。程序仍需决定何时触发参与者、怎样处理重复或冲突的信息，以及什么时候停止。这里的“没有主智能体”，不能替代这些执行规则。

三种模式，差别在于谁决定下一步

模式谁决定下一步适合的任务最容易遇到的问题
流水线预先写好的流程步骤稳定、输入输出清楚回退和分支越来越多
调度者主智能体专业分工已知，具体任务需要临时拆解规划错误向所有助手传播
黑板参与者结合共享状态行动，由程序约束执行后续工作依赖新发现循环、冲突和停止条件不清

三者没有必然的升级顺序。选择时，先看任务的依赖关系和决策方式，再决定需要多少自主性。

Stormwise：两个阶段也会出错

Stormwise 是作者基于 Claude 开发的恶劣天气助手。它的核心只有两个阶段：先获取官方预警，再让模型根据预警回答问题。这更接近一个两阶段工作流，案例本身并不能证明多智能体的收益，但它暴露的交接问题同样会出现在多智能体系统里。

作者使用真实的美国国家气象局（NWS）预警构造了 117 个固定案例，其中包括 69 个有预警案例、32 个无预警对照和 16 个美国境外地点案例。实验比较了不同的数据接入和提示词条件。

上游拿错数据，下游可能照单全收

气象服务会发布测试预警。Stormwise 曾把测试消息当成真实预警交给模型，模型随后据此生成回答。

错误发生在数据接入环节。下游模型没有足够依据识别它拿到的是测试数据。

多智能体之间也有类似风险：上游的一次猜测，经过一次转述，就可能在下游变成确定事实。交接时需要检查数据来源、有效时间和状态标记，并保留尚未确认的部分。能用程序验证的字段，应当直接验证。

缺少预警时，提示词无法补回事实

论文把“实际存在预警，回答却让用户以为天气平静”称为错误安抚（false reassurance）。有预警案例中的结果如下：

实验条件出现错误安抚的回答比例
无法访问预警，使用普通提示词26 / 6937.7%
无法访问预警，并要求说明这一信息盲区31 / 6944.9%
接入真实预警，使用普通提示词0 / 690%

在这组实验里，接入真实预警消除了观察到的错误安抚。增加“说明自己看不到预警”的指令，没有改善这一指标。第二行的观察值虽然更高，论文报告该差异未达到统计显著性，不能据此断言这条指令必然有害。

这也不意味着提示词没有作用。论文还发现，在无预警对照中，“真实数据加普通提示词”的条件仍有 87.5% 的回答引发某种警觉，生产提示词条件下则为 0%。数据接入解决了缺少预警事实的问题，提示设计仍影响如何表达风险。

表中的零次错误只适用于这些测试案例，不能解释为上线后绝不会出错。

预算耗尽时，要有完整的退路

作者还遇到过 token 预算在复杂问题上不足的情况。日常问题能顺利完成，需要详细处理的请求反而可能被截断。

系统应提前规定预算用尽后的行为。例如，天气助手可以保留已确认的官方预警和必要行动信息，明确哪些内容没有完成。具体退路取决于产品，但不能等执行中断后再临时决定。

检查器也可能把结论带偏

作者最初使用正则匹配识别错误安抚，结果漏掉了 57 个真实案例中的 53 个，甚至给出了相反方向的结论。最终，他人工标注了全部 342 条有预警案例回答。

这里的自动检查器是规则脚本，并非另一个智能体。经验同样适用于模型审查：接上检查器之后，还需要用人工样本验证它是否真的能发现目标问题。

论文也披露了人工标注由一名评审者完成等方法细节。因此，这些数字适合用于理解该实验中的失败方式，不宜直接外推为所有天气助手的错误率。

从第一天就写进程序的五条约束

作者建议把以下约束放在智能体外部，由程序执行。

  1. 1. 验证每次交接，检查格式、必填字段、数据时效和业务含义。天气记录格式正确，也可能早已过期。
  2. 2. 限制任务转交次数。工作在智能体之间反复来回时，达到上限就停止，按预定方式交给人处理。
  3. 3. 按整个请求记预算，集中跟踪消耗，并提前定义超限后的回复。只给每个智能体单独设限，仍可能让一次请求累积出很高成本。
  4. 4. 记录智能体之间的消息，保留任务、结果和交接关系，便于逐步回放，查清错误最早出现在哪里。
  5. 5. 用真实案例评估，既检查最终回答，也抽查自动评分。复杂案例、错误数据和预算不足都应进入评估集。

成本也需要单独看。作者的晚餐推荐智能体一直有步数限制，没有失控循环，最后仍因 API 费用难以支撑而下线。执行有上限，只说明费用受到约束，并不说明产品负担得起。

选择时，先写清分工和停止条件

可以按下面的顺序判断：

  • • 一个智能体配工具已经够用，就先保留这个方案。
  • • 步骤能够事先列成固定清单，优先考虑流水线。
  • • 专业分工明确，但具体子任务随请求变化，可以考虑调度者。
  • • 下一步依赖调查中的新发现，可以考虑黑板，并明确触发规则和停止条件。

原文还有一个交互演示，可以切换三种模式，注入过期天气数据或来回转交，再比较启用约束前后的行为。它是预设脚本演示，不会实时调用模型，适合观察执行结构，不能用来测量真实模型效果或费用。

动手前，可以先为每个参与者写下：它负责什么、接收哪些信息、交付什么结果、失败后由谁处理。如果这些问题仍然含糊，增加智能体只会让排查更费力。
