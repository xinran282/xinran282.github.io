System 1 决策引擎要解决的不是「写一段像样的回复」，而是：给定当前状态，在你规定好的答案空间里，很快给出一个程序能直接用的判断，并带上概率。

这个名字借自 Kahneman《思考，快与慢》里的 System 1：快、直觉、不逐步推理。TypeSafe 在文档里写明了借用关系，同时把重点收窄成「快、聚焦的判断」。它不是在复现人类认知科学，只是拿这个对比来说明：模型不做慢思考，也不写解释。

产品形态已经有两家能对上看。TypeSafe 把这类模型叫 System One，旗舰是 Jev，走 POST /v1/systemone。Laya 自称非自回归 System 1 决策引擎，协议故意兼容同一套接口。下面按这个共同形状写，不把某一家的延迟数字当成定律。

传统软件把决策写成 if/else。规则清楚时这最稳，也最便宜。一碰到邮件正文、工单、对话记录，规则就开始漏。

常见补法是丢给大模型：「读完这段，用 JSON 告诉我该分给哪个组。」模型会写字。你再解析。字段名会飘，枚举会发明，偶发的一句解释会把解析器弄死。Agent 更进一步，自己决定下一步调什么工具。TypeSafe 把这种架构和「代码掌控流程、模型只在需要常识的地方出现」分开：后者才是它说的 AI-powered software。

System 1 决策引擎站在中间。它懂自然语言，但输出被钉在你给的选项上：

  • • 这段话该给 billing、technical 还是 account
  • • 客户有多着急，落在你定义的几档上
  • • 「有没有明确要求退款」为真的概率是多少

它不写回复，不写代码，不生成推理过程。Jev 目前只吃文本：字符串、JSON、文本数组，不吃图、音频、视频。这是 TypeSafe 文档里的限制，不是我的推断。

和经典分类器的差别在输入侧。分类器通常要你先标一堆数据、固定标签集。这里的问题是运行时用自然语言描述的：instructions 写判断本身，criteria 写选项或量表。标签可以按业务改，不必先训一个新头。代价是：描述写糊了，输出的概率就不好解释；领域一偏，仍然要微调或至少在自己的数据上校准。

三种原语

TypeSafe 和 Laya 用同一套问题类型。选哪种，看你的代码接下来要干什么，不看哪一个听起来更「智能」。

Choice：从无序集合里挑一个。工单分部门、文档类型、编程语言。返回选中项、每项概率、以及描述分布有多尖的 confidence。列表可能盖不住时，自己加 other 或 none。

Score：落在你定义的有序档位上，返回值可以落在两档之间。紧急程度、受挫程度、技能深浅。档位必须能独立读懂，写具体情境，不要只写「低 / 中 / 高」。

Noul：是或否，返回 0 到 1 的 P(true)。有没有要退款、像不像钓鱼、简历有没有写过分布式。Noul 没有单独的 confidence。0.5 表示是和否差不多，不表示「中等强度」。TypeSafe 特意警告：不要用 Noul 去问「这个候选人 Python 强不强」——「强」没定义时，0.5 无法当中级水平用。要程度就用 Score，要是否就写清条件。

同一份 state 上可以一次问很多道，题与题互相看不见答案。这是设计，不是缺陷。你要的是可拆开检查的信号，不是模型在内部把几件事揉成一句「建议」。

问题 ID 只给你的代码用，不会送给模型。判断必须完整写在 instructions 里。state 是结构化对象时，用反引号路径指到字段，例如 `ticket.messages[0].text`。

工作流怎么拆

TypeSafe 的构建指南可以压成几条，和产品无关。

能用代码就算的，不要问模型。逾期天数、订单是否已关闭、金额是否相等，用日期和数字。模型出现的位置应当是：这段非结构化文本在说什么。

state 只放当前这批问题需要的上下文。退款政策、相关交易、客户原话可以放；三年工单历史不要整包塞进去。当前事实来自你的知识库时，不要指望权重里「记得」政策。

问题要窄。TypeSafe 把「把判断拆开」写成指南里最重要的一条。「这是不是垃圾邮件」里面至少叠了：要不要密码、有没有意外奖金、是否制造紧迫、发件人显示名和域名是否冲突。拆开以后，每道题可以单独看错在哪，权重可以在代码里改，不必重写一整段 prompt。

同一份 state 上能一起问的，就一起问。并行几乎不增加等待，多出来的主要是题面 token。可能用得上的题也可以先问，代码按分支决定用哪几个答案——他们叫 speculative fan-out。只有后一步必须先拿到前一步答案才能构造 state、拉证据、或决定下一题的选项时，才发第二次请求。

概率和置信度用来分流，不用来证明「这次一定对」。校准是对一批预测说的，单条没有保证。阈值要在你的数据上对着准确率画，cookbook 里的 0.8 只是例子。Noul 接近 0.5 该升级；Choice 的低置信度也可能只是几个可接受选项把概率摊开了，不一定等于判断失败。

现成实现差在哪

Jev / TypeSafe。 闭源 API。文档写大多数查询大约 100 ms，训练目标是校准过的决策（他们称为 RLCD）。你定义 state 和 questions，代码组合答案。适合已经按 System One 协议写客户端、不想自己伺候编码器的人。价格、配额以 Models 为准，这里不抄可能过期的数字。

Laya。 Apache 2.0，ModernBERT / mmBERT 编码器，一次前向，不生成文本。作者在 T4 上测过单问大约 33 ms。带 Router：非拉丁文字走多语言模型，避免英文权重在高棉语上准确率 0 却自信 0.95 那种事故。HTTP 服务兼容 /v1/systemone。它自己承认：基座在 typed-decisions 上接近随机，0.766 来自微调后的 checkpoint；选项一多、score、英文 noul 都有已知坑。把它当特化基座，不要当开箱裁判。

两者协议能对上，不代表同一道题分数相同。Laya README 里对 Jev 的对比，Jev 一侧来自第三方已发表数字，样本和提示并不相同。

再往外，BERT 分类头、交叉编码器重排、CALM 一类校准分类器，也能承担「快判断」。缺的是运行时用自然语言定义 choice / score / noul、以及和 System One 客户端的那层契约。有没有必要上专用引擎，看你是不是真的在组合很多这类判断，而不是偶尔抽一个字段。

不该交给它的事

需要逐步推理、工具循环、写给用户看的句子，这是 System 2 或普通 LLM 的工作。决策引擎最多提供「要不要升级到那边」的门闩。

选项特别多时，所有选项要挤进同一段上下文预算。Laya 在 Banking77 上默认设置会把每个标签压到三四个 token；Jev 声称开箱能到 255 个选项，仍然不是无限。分层 Choice，或先短名单再精排，是代码的事。

输出类型安全不等于真。模型不会发明列表外的标签，仍可能在列表内选错。领域一偏就要微调或至少做温度校准。Laya 出厂过自信；Jev 文档也写校准不保证单条正确。

当前这一代基本上是文本 in、结构 out。界面截图、语音工单，要先变成字，或等多模态版本。

什么时候值得用

你已经能画出业务流程图，只是某几处必须读懂人话：分诊、是否触发政策、候选证据里选一条、要不要人工。那些节点改成类型化问题，周围仍是普通代码。

你在用大模型抽 JSON，却把大量时间花在修解析和枚举漂移上。换决策引擎，是把「生成再解析」收成「在给定集合上打分布」。

你需要在请求路径里做判断，等不起一轮完整对话。具体毫秒数看部署：托管 API、本地 GPU、CPU 差一截。先测你的 p50，再决定它够不够当同步依赖。

反例也清楚。没有稳定的答案空间，每次问题都在变，那是聊天，不是决策引擎。没有人维护 instructions 和校准数据，上了也会在领域漂移里静默变差。一次只问一件小事、用正则就能做，不必为这个词专门加模型。

结论

System 1 决策引擎是给软件用的快判断层：读状态，在你规定的 Choice / Score / Noul 上返回概率，流程仍由代码收口。名字来自认知科学的快系统，产品承诺的是延迟和可组合的类型，不是「更像人」。

Jev 把这套做成 API。Laya 做成可自托管的编码器。要不要用，看你的痛是不是「非结构化输入上的窄判断」，以及你有没有把判断拆开、用代码组合的意愿。拆不开的大问题，仍然该给会慢慢想的模型，或者给人。
