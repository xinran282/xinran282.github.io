AI 反复犯同一种错误时，先看能否把纠正变成接口约束、lint、类型检查或测试。让下一次错误在检查中暴露，再把需要判断的部分写进规则和 skill。Lauren Tan 在 AI Engineer CODE 2026 的演讲《All Code Is Slop (Except Mine)》围绕这一思路，介绍了团队怎样提高 AI 代码的可靠性。

Lauren 的 GitHub 网名是 [poteto](https://github.com/poteto)，演讲中也自称 Potato。标题可以意译为“代码都是垃圾，除了我的”，是在调侃程序员看别人代码时的常见心态。她随后讨论的是：代码产出大幅增加以后，怎样维持甚至提高质量。

她的路径是持续改进智能体工作的环境，把经验写进接口、架构和自动检查，再用运行结果验证行为。她说，自己花了约六个月建设这套环境，才达到每月交付数千个 PR 的状态。

## 1. 优先把要求变成代码能执行的约束

在约 1:03:27，她用一个倒金字塔说明投入顺序。靠前的是代码库设计与确定性检查，包括 API、架构、重构、lint、类型系统、编译器和测试；再叠加运行时验证与形式化验证；文字规则、skills 和 AGENTS.md 则承载需要判断、难以直接编码的部分。

每次指出智能体的错误，都可以想一想：能否为这种错误写一个检查？能否通过 API 或架构设计，直接消除错误选项？

例如，“不要跨越进程边界导入模块”写在文档里，仍然可能被忽略。把它写成依赖检查，违规代码就无法通过检查。工程师也无需在每个 PR 中重新寻找同一种错误。

可以把这些投入分成几层：

| 投入位置 | 解决什么问题 | 例子 |
| --- | --- | --- |
| API 与架构 | 减少可以选错的实现方式 | 提供受支持的数据访问接口，明确模块边界 |
| 自动检查 | 拒绝已知的错误模式 | 类型检查、依赖检查、lint、测试 |
| 运行与形式化验证 | 检查实际行为和应保持的性质 | 操作应用、审查截图、模型检查 |
| 规则与 skill | 组织流程，处理仍需判断的部分 | 何时加载功能地图、如何收集证据 |

这些层次可以共同使用。例如，skill 负责指导智能体执行验证，CLI 负责操作应用，断言负责检查结果；它们承担的职责不同。

## 2. 代码库会成为下一轮生成的范本

约 1:04:23 起，Tan 提醒听众：代码库是智能体最大的输入之一。仓库中保留的临时补丁、反模式和过时实现，很容易被识别为既有惯例，并复制到新代码里。

她把维护代码库比作园艺。过去一次只来几个 PR，人工还能逐个看；当代码持续涌入时，已有结构和约束会决定新代码如何生长。坏示例扩散得也更快。

因此，清理旧实现会直接影响后续生成质量。只增加规则、却留下大量违反规则的范例，会让智能体面对互相矛盾的输入。她建议先阻止反模式继续增加，再清理已有实例。

## 3. 用框架和目录结构消除整类错误

约 1:06:24，她介绍团队为桌面客户端建设的 Dune 框架，可以粗略理解为面向 Electron 应用、带有团队约束的框架。她强调的价值在于把开发经验编码进去。

第一个例子是 React 的 `useEffect`。这个 API 有合理用途，但正确使用需要不少细节判断。团队选择在产品代码中禁用它，只允许在框架内部的特定位置使用，并提供受支持的实现路径。这样，相关误用就不必反复交给人工审查。

第二个例子是 Electron 的进程边界。她描述了明确命名的 `electron-main` 与 `electron-renderer` 目录，再用依赖图分析和 lint 规则阻止不合适的跨边界导入。目录帮助智能体理解上下文，检查负责执行边界。

这些都是她所在团队的架构选择。不能由此推出“所有 React 项目都该禁用 useEffect”。可迁移的经验是：对经常误用的能力，提供更窄、更容易正确使用的接口，并用机器执行限制。

## 4. 注释可能让临时补丁变成惯例

约 1:08:23，Tan 讲到一种容易忽略的失败：智能体会写下注释和文档，解释为什么某个临时方案是必要的。下一轮智能体读到这些解释，又把它当成经过认可的设计。

她举了用 `setTimeout`、`requestAnimationFrame` 等命令式调度机制修补架构冲突的例子。补丁越来越多，注释却在不断替它们辩护。应用性能变差，错误模式也被保留下来。

她介绍团队对代码注释采取了非常严格的限制。这是一项激进的本地政策，不能直接当成通用的文档规范。更有用的启发是：解释问题存在的原因，并不能阻止问题再次发生。

她更愿意让 lint 报错提供明确的修复方向，要求智能体处理根因；或者改进接口，使那种补丁不再需要。文字可以解释设计意图，自动检查则负责执行限制。

## 5. 审查要看行为，也要看验证证据

约 1:11:04 起，演讲转向验证。Tan 说，她们的审查越来越多地围绕视频、截图、图表和形式化验证结果展开。

最基本的投入，是让智能体能够自己运行应用、使用调试工具。团队还维护从用户视角描述功能的 feature map，相当于功能地图。这样，当需求提到“左侧栏的那个功能”时，人与智能体有共同的词汇，不必完全依赖猜测。

重复操作则封装成可复用的 CLI 和驱动，减少每次重新编排工具的开销，也让这些操作本身可以被测试。

更深入的尝试包括主要用户流程的模型检查、特定算法的证明，以及 UI 的基于性质的测试。她同时说明，这些方法仍在实验中，是额外的验证层。状态图也能帮助人检查产品有哪些状态、允许哪些转换，补充单张截图无法覆盖的信息。

她观察到，自己的大部分 token 消耗用于验证。演讲中的“70%”则来自她引用的另一位开发者的分享，不宜写成她本人或整个团队的精确统计。

她的经济判断是：许多验证方法早就存在，只是人工编写、理解和维护的成本较高。智能体降低了部分成本，让团队有条件做更充分的验证。

## 6. 演讲中的 skill，具体帮忙做什么

演讲直接提到了运行时验证技能，以及约 1:14:25 开始介绍的 `statechart`。前者帮助智能体操作应用、验证功能；后者从用户视角呈现状态机，让人更容易检查流程。

### 运行时验证：让“已经修好”有据可查

Lauren 公开的 [verification-skill-example](https://github.com/poteto/verification-skill-example) 展示了“项目内验证技能 + 功能地图”的组织方式。仓库使用虚构产品和功能，操作驱动脚本有意省略，适合参考结构，需要结合自己的项目实现。

示例把应用拆成约 30 份功能文件。每份文件说明功能是什么、用户从哪里进入、如何通过驱动操作，以及哪些表象容易误导验证。修改某个功能时，智能体只需读取相关文件；全面回归时，再按索引顺序逐项检查。

它描述的验证过程包括：

1. 把改动对应到相关功能文件，确定受影响的用户路径。
2. 检查运行实例是否是当前版本，避免在旧构建上验证新改动。
3. 操作有关入口，覆盖受影响的成功、取消、错误、空状态和持久化路径。
4. 保存截图、DOM 断言、网络结果或重新加载后的状态等证据。

这套技能需要有人维护功能说明和操作驱动。只写一条“请认真测试”，还无法告诉智能体要从哪里进入、如何操作、凭什么判断成功。

### statechart：补上截图里看不到的转换

一张截图能说明界面某一刻是什么样，却很难说明用户取消、失败后重试、关闭窗口再打开时会怎样。`statechart` 的作用，是把这些状态和转换呈现出来。

以“发送消息”为例，下面是用于解释用途的简化模型，并非演讲原图或该技能的真实输出：

| 当前状态 | 事件 | 预期下一状态 |
| --- | --- | --- |
| 编辑中 | 点击发送 | 发送中 |
| 发送中 | 服务端确认 | 已发送 |
| 发送中 | 请求失败 | 失败，可重试 |
| 失败，可重试 | 点击重试 | 发送中 |

有了这个模型，审查者可以继续追问：发送中还能不能再次点击？重试会不会重复发送？窗口关闭后，未确认的消息如何恢复？这些问题很容易被一张成功截图遗漏。

状态图让人和智能体有一份可以共同检查的流程描述。图是否完整、实现是否符合图，仍需要进一步验证；画出图本身不构成正确性证明。

### 她另外公开的两个项目

结合“怎样读懂项目、怎样保留纠错经验”这两个需求，还可以看 Lauren 的另外两个项目。它们属于补充阅读，不是本场演讲逐项介绍的工具清单。

| 项目 | 主要用途 | 适合什么时候看 |
| --- | --- | --- |
| [how](https://github.com/poteto/how) | 解释子系统、功能和执行流程；复杂问题可分角度探索，也支持独立批评者评估架构 | 刚接手仓库，或准备评审一项设计 |
| [brainmaxxing](https://github.com/poteto/brainmaxxing) | 用 Markdown 记忆库保存经验，并提供反思、整理、计划和审查技能 | 希望跨会话保留纠错经验，定期清理矛盾规则 |

`how` 的 README 将其定位为 Cursor 插件。`brainmaxxing` 的使用说明面向 Claude Code，其中 `/reflect` 用于从会话提取值得记住的经验，`/meditate` 用于整理记忆、检查技能与经验之间的矛盾。采用时要留意宿主要求，以及项目指令和 hook 的接入方式。

保存经验以后，还要判断经验该放在哪里。某条提醒如果已经足够明确、稳定，就可以继续尝试将它变成自动检查，减少之后依赖智能体记住并解释它的次数。

## 7. 内层开发循环可靠后，再扩大外层自动化

演讲开头，Tan 自述上个月个人向生产环境交付了约 3,000 个 PR。约 1:14:56 起，她介绍团队上个月约 11,000 个 PR 的产出，稳定版本约每天发布一次，PR 相对回退比例约为 0.5%，并称启动、输入、打开和切换聊天等性能指标有所改善。

这些是演讲者报告的团队结果。PR 数量不等于用户价值，回退率也不等于缺陷率；演讲没有提供能单独证明因果关系的对照实验。因此，这组数据适合说明她们达到了怎样的工作规模，不适合直接作为其他团队的效率目标。

约 1:16:35，她再次强调顺序：先改进代码库、阻止并清理反模式、建设可靠的验证流程，再自动化调用智能体的外层循环。内层循环持续生成低质量代码，外层自动化只会扩大产出和 token 开销。

她在结尾给出的例子是，新版本发布后自动启动项目，对应用进行模糊测试，发现问题后创建修复 PR，并自动合并。她将这种自主程度归因于前面持续建设的工程基础。

## 怎样把这些经验用于自己的项目

下面是根据演讲整理的实施建议，属于本文归纳：

1. 从最近的审查记录中选出一种反复出现的错误，明确它发生的条件。
2. 检查能否用接口或模块边界消除它；暂时做不到时，加入类型、lint 或测试约束，并提供可操作的错误信息。
3. 清理仓库里同类的旧示例，让代码与规则保持一致。
4. 给智能体运行应用和检查结果的工具，要求提交能说明行为的证据。
5. 观察缺陷、回退、性能和审查负担，再逐步扩大自动合并范围。

例如，智能体总把 Electron 主进程代码导入渲染进程，可以先建立依赖检查，再给错误信息补上正确接口，清理旧的违规示例，最后把启动应用、检查交互响应的步骤写进验证技能。这样，一次纠错就有了后续可以重复执行的结果。
