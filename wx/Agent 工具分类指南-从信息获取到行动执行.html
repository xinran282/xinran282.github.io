Agent 工具更适合分成五类：感知、执行、协作、用户沟通和事件触发。

这套分类关注信息与控制在谁之间流动。外部信息进入 Agent，属于感知；Agent 改变外部状态，属于执行；Agent 与其他 Agent 配合，属于协作；Agent 与人交换信息和权限，属于用户沟通；时间或外部事件启动 Agent，属于事件触发。

分类标准明确后，文件读取、Shell、浏览器、子 Agent、审批和定时任务都有了稳定的位置。测试、验证、安全治理仍然重要，但它们不是同一层级的工具类别：测试通常属于执行，权限与审计则覆盖所有类别。

本文采用的是一种工程分类方法，不是统一的行业标准。平台可能使用不同名称，也可能把几类能力放进同一个接口。

工具是 Agent 可以调用的一项外部能力，通常有明确的参数、返回值和权限边界。例如，文件读取工具接收路径并返回内容；命令执行工具接收命令，返回输出和退出码；用户询问工具把一个待确认的问题交给人，收到回答后再继续。

大语言模型负责理解上下文、推理和生成内容。它不会仅凭一段文字真的读取硬盘、提交代码或等待明天上午九点。工具把模型的判断接到运行环境中，工具结果再进入下一轮判断。

一次完整的工具调用通常经历四步：

  1. 1. Agent 选择工具并填写参数。
  2. 2. 运行环境检查参数、权限和审批要求。
  3. 3. 工具执行操作，返回结果或错误。
  4. 4. Agent 根据结果继续、重试、改换方法，或结束任务。

第四步经常被低估。文件写入成功，不等于内容正确；定时任务创建成功，也不等于它触发后一定能完成业务目标。

五类工具的总览

类别信息或控制方向常见工具解决的问题
感知外部世界 → Agent文件读取、代码搜索、网页检索、数据库查询、图像识别现在是什么情况？
执行Agent → 外部世界文件编辑、Shell、浏览器操作、API 写入、制品生成需要改变什么？
协作Agent ↔ Agent 或工作单元子 Agent、任务委派、消息、等待、共享计划谁来做，怎样汇合？
用户沟通Agent ↔ 用户澄清问题、进度更新、审批、结果交付、通知人需要知道或决定什么？
事件触发时间或事件 → Agent定时任务、提醒、Webhook、监控、队列唤醒什么时候开始或继续？

同一底层能力可能出现在不同场景。浏览器读取页面时是感知，点击提交按钮时是执行；消息工具向子 Agent 发送任务时是协作，向用户报告进度时是用户沟通。分类看的是本次调用的作用，不是工具的产品名称。

一、感知工具

感知工具让 Agent 获取环境状态。没有这一步，后面的推理只能依靠用户最初提供的文字，容易遗漏现场信息。

常见的感知对象包括：

  • • 工作区：文件、目录、代码符号、版本差异和终端输出。
  • • 外部信息：网页、搜索结果、API、数据库和知识库。
  • • 应用状态：浏览器页面、表单内容、当前登录账号和界面截图。
  • • 多模态内容：图片、PDF、音频、视频以及扫描文档。

感知不等于搜索。打开指定文件是感知，查询数据库是感知，读取正在运行的测试输出也是感知。它们都在回答同一个问题：Agent 下一步判断所需的事实是什么？

这类工具通常只读，但并非没有风险。读取范围过宽可能泄露隐私或密钥；网页内容可能过期；搜索摘要可能缺少上下文。好的感知结果应保留来源、时间和查询范围。Agent 如果无法确认事实，就应把不确定性说清楚。

常见感知工具

文件与代码工具会列出目录、读取内容、全文搜索或定位符号。网页与浏览器工具负责导航、读取 DOM、截取页面和获取可交互元素。连接器可以读取 GitHub 拉取请求、工单、消息线程或日历。图像和文档解析工具则把非纯文本内容转换为模型能处理的信息。

专用接口通常比通用界面更稳。读取拉取请求时，结构化连接器能直接返回标题、状态和评论；浏览器抓取页面则可能受到布局和加载时序影响。

二、执行工具

执行工具让 Agent 改变环境或产出结果。创建文件、修改代码、运行命令、点击网页按钮、发送 API 请求和生成文档都属于执行。

执行可以再按影响范围理解：

  • • 工作区执行：编辑文件、应用补丁、格式化代码、生成构建产物。
  • • 计算执行：运行 Shell、解释器、测试、编译器和数据处理任务。
  • • 界面执行：点击、输入、上传文件、提交表单。
  • • 外部写入：创建议题、发送消息、更新数据库、部署服务。
  • • 制品生成：创建图片、表格、幻灯片、Word 文档和 PDF。

执行工具要有清楚的边界。局部补丁通常比整文件重写更容易审查；专用 API 比模拟点击更容易判断成功与失败。删除、发布、付款、合并代码和向他人发送消息会产生明显外部影响，执行前应确认目标与权限。

验证为什么不单独分类

测试、静态检查、版本差异和页面渲染都用于验证，但从工具行为看，它们仍是执行：Agent 启动一个检查过程，再感知检查结果。

把验证单独列为顶层工具类型，会混合“工具怎样与外部交互”和“这次调用想达到什么目的”两种标准。更准确的说法是，可靠的执行应带有验证闭环。

例如，Agent 修改代码后运行针对性测试，再读取退出码和失败日志；生成 HTML 后检查文件大小、标题、编码和实际样式。补丁成功或文件存在，只能说明动作发生了，不能说明任务完成了。

三、协作工具

协作工具处理 Agent 与其他 Agent、执行者或工作单元之间的关系。它们负责拆分任务、传递上下文、同步进度和合并结果。

常见能力包括创建子 Agent、发送任务、补充指令、中断工作、等待结果和查询协作者状态。计划与共享状态也属于这一类，因为它们帮助多个工作单元理解当前进度和剩余工作。

协作的难点不是启动更多 Agent，而是划清边界。一个有效的委派至少要说清四件事：输入是什么，允许修改哪些内容，交付物是什么，怎样算完成。边界模糊时，两个 Agent 可能同时改同一文件，也可能都以为对方会做最终验证。

主 Agent 仍然需要收口。子 Agent 返回的结论只是新的输入，主 Agent 要检查冲突、验证改动，并向用户交付一个一致结果。

协作不等于用户沟通

子 Agent 与用户扮演的角色不同。子 Agent 接受委派并返回工作结果；用户拥有任务意图、权限和最终取舍。把两者混成“消息工具”，会让 Agent 忽略一个重要事实：有些问题可以委派，有些决定只能由用户作出。

四、用户沟通工具

用户沟通工具建立 Agent 与人的双向通道。它不只是最终回答，还包括过程中的进度更新、澄清、审批和异常报告。

常见形式有：

  • • 进度更新：说明正在处理什么、已经确认什么，以及下一步是什么。
  • • 澄清问题：缺少的信息会实质改变结果时，请用户作出选择。
  • • 权限审批：下载依赖、访问受限资源或执行高风险操作前请求许可。
  • • 最终交付：报告结果、验证情况、文件路径和仍然存在的限制。
  • • 主动通知：长任务、监控或自动化达到某个状态后提醒用户。

好的用户沟通应当改变任务状态。若 Agent 已经能从工作区找到答案，就不必把调查工作推回给用户；若某个选择会改变数据、费用或对外影响，Agent 也不应擅自替用户决定。

进度消息还有一个实际作用：长时间运行的任务不会像黑箱。用户能及时发现方向偏差，但又不需要阅读每一条命令日志。

五、事件触发工具

普通对话由用户消息启动。事件触发工具让 Agent 在没有新对话消息时开始或继续工作。

触发源通常有四类：

  • • 时间：在固定时刻、间隔或日程条件下启动。
  • • 外部事件：Webhook、代码推送、工单变更、邮件到达或数据更新。
  • • 状态变化：测试完成、部署失败、价格越界或监控指标异常。
  • • 队列与任务：后台工作完成后唤醒原任务，继续下一步。

提醒、定时自动化、监控器、队列消费者和线程唤醒都属于事件触发。它们决定“何时运行”，并不自动定义“运行什么”。触发器需要绑定清楚的目标、上下文和停止条件。

事件触发还要处理重复与延迟。Webhook 可能重发，定时任务可能与上一次重叠，监控条件也可能持续为真。执行部分应尽量幂等，并记录最近一次处理状态。涉及对外写入时，重复发送比一次失败更麻烦。

安全与治理覆盖五类工具

权限、沙箱、审批、审计日志、密钥管理、超时和速率限制不适合与五类工具并列。它们是横切层，约束每一种调用。

感知工具需要限制可读取的数据；执行工具需要控制写入范围；协作工具要避免上下文和权限无意扩散；用户沟通要防止把敏感信息写进消息；事件触发则要设置频率、停止条件和重复处理策略。

可靠的边界由运行环境执行，不能只靠提示词要求 Agent “小心”。一个实用原则是默认只读，按任务授予最小写权限，把不可逆或影响他人的动作放到审批之后。

Tool、Skill、MCP 和插件处在哪一层

五类工具描述的是用途。Tool、Skill、MCP 和插件描述的是能力以什么形式提供，两组概念不要混用。

概念是否直接执行动作作用
Tool是一个可调用能力，带参数和返回值
MCP 工具是通过 Model Context Protocol 暴露给 Agent 的工具
Skill通常不是一套任务步骤、规范和参考资料，指导 Agent 组合工具
Plugin不一定把 Skill、MCP 服务、应用或配置打包在一起
子 Agent间接一个有独立上下文的执行者，可以使用获准的工具

同一个 MCP 服务可以同时提供感知工具和执行工具，例如读取议题与更新议题。一个 Skill 可以规定如何组合五类工具，例如先感知仓库状态，再执行修改，必要时请求用户审批，最后等待 CI 事件并继续处理。

一条完整任务如何穿过五类工具

以“CI 失败后修复代码并通知用户”为例：

  1. 1. 事件触发工具收到 CI 失败事件，唤醒 Agent。
  2. 2. 感知工具读取失败日志、相关代码和最近提交。
  3. 3. 协作工具把最小复现或影响分析交给子 Agent，主 Agent 汇总结果。
  4. 4. 执行工具修改代码并运行测试，再通过感知工具读取测试结果。
  5. 5. 如果需要推送分支或创建拉取请求，用户沟通工具先请求必要审批。
  6. 6. 执行工具完成获准的外部写入，用户沟通工具交付结果和验证信息。

这五类不是固定的线性流水线。执行失败后会回到感知，协作过程中可能需要向用户澄清，事件触发也可能发生在任务中途。分类的价值在于说明每次交互的对象和责任。

设计工具集时检查什么

设计 Agent 工具集时，可以逐类检查：

  • • 感知：Agent 能否读取完成判断所需的最小信息？来源和时间是否可追踪？
  • • 执行：写入范围是否明确？结果能否验证、失败能否恢复？
  • • 协作：任务边界、上下文和汇合方式是否清楚？
  • • 用户沟通：哪些信息要主动报告，哪些决定必须由用户确认？
  • • 事件触发：触发条件、频率、上下文、停止条件和去重策略是否完整？

工具说明本身也要具体。名称应表达动作，参数应有类型和限制，返回值要区分成功、部分成功与失败，副作用不能藏在描述之外。

结语

感知、执行、协作、用户沟通和事件触发，分别对应 Agent 与环境、其他 Agent、用户以及时间和外部事件的关系。这种分类保持了同一层级，也更接近 Agent 实际运行的方式。

判断一个 Agent 系统是否完整，可以拿一条真实任务链逐段检查：它怎样知道发生了什么，怎样采取行动，怎样与其他执行者配合，什么时候让用户介入，又由什么事件启动下一轮工作。缺少的工具会很快暴露出来。
